# Datos de demostración

Al definir `DEMO_DATA=true` en el backend se registra todo lo que necesitan tres ejemplos con aprobación que modifican recursos («lanzar una instancia EC2», «reiniciar un pod de GKE» y «rotar un secreto de Azure Key Vault») en el tenant **Default** creado inicialmente, de modo que hay algo que ejecutar sin registrar cada pieza a mano. El [flujo de trabajo](../guides/workflows.md) en sí no se crea, de forma deliberada: estos registros son los ingredientes a partir de los que se genera, y de eso se encarga el [Recorrido guiado](./walkthrough.mdx).

## Activarlo {#enabling-it}

Añade el indicador a `backend/.env` y reinicia el backend. Con [Docker Compose](./docker-compose.md) ya está activado: `compose.yml` define `DEMO_DATA: ${DEMO_DATA:-true}`.

```env
DEMO_DATA=true
DEMO_PASSWORD=change-me-now-123
DEMO_AWS_ACCESS_KEY_ID=AKIA...
DEMO_AWS_SECRET_ACCESS_KEY=...
DEMO_AWS_REGION=us-east-1
DEMO_GCP_CREDENTIALS_JSON='{"type":"service_account",...}'
DEMO_AZURE_TENANT_ID=...
DEMO_AZURE_CLIENT_ID=...
DEMO_AZURE_CLIENT_SECRET=...
```

- `DEMO_PASSWORD` es común a los once usuarios de demostración y, como `ROOT_PASSWORD` y `ADMIN_PASSWORD`, si no se define se genera y se registra una sola vez. Solo se consulta mientras falte alguna de las cuentas.
- Las credenciales de AWS, la credencial de Google Cloud y las credenciales de Azure son opcionales. Si no se definen, se guarda en su lugar el marcador `REPLACE_ME`, de modo que la demostración queda completa en cuanto a estructura y puedes rellenar los valores reales desde la página [Secretos](../guides/secrets.md).
- `DEMO_AWS_REGION` es la región sobre la que actúan las herramientas del servidor MCP de AWS de la demostración. El valor predeterminado es `us-east-1`.
- `DEMO_GCP_CREDENTIALS_JSON` es un JSON de credencial de Google Cloud en una sola línea: una clave de cuenta de servicio o el JSON authorized-user que escribe `gcloud` tras iniciar sesión una vez con un ID de cliente y un secreto de OAuth. El servidor MCP de GKE genera a partir de él su token de acceso; los servidores MCP de Google no aceptan claves de API. Consulta [Servidores MCP de Google Cloud](../guides/mcp-servers.md#google-cloud-mcp-servers) para saber cómo obtener cualquiera de los dos.
- `DEMO_AZURE_TENANT_ID`, `DEMO_AZURE_CLIENT_ID` y `DEMO_AZURE_CLIENT_SECRET` corresponden a una entidad de servicio de Azure: el tenant, el ID de cliente de la aplicación y uno de sus secretos de cliente, tal como los muestra `az ad sp create-for-rbac`. En el Key Vault donde la demostración deba rotar secretos, concédele un rol personalizado que tenga únicamente las acciones de datos `Microsoft.KeyVault/vaults/secrets/readMetadata/action` y `Microsoft.KeyVault/vaults/secrets/setSecret/action` o, en un Key Vault que use directivas de acceso, solo los permisos de secretos **List** y **Set**. El rol integrado **Key Vault Secrets Officer** también funciona, pero además puede leer el valor de todos los secretos.

⚠️ Los servidores MCP de AWS, GKE y Azure pueden ejecutar operaciones que **modifican** recursos, no solo lecturas. Las credenciales del servidor MCP de AWS pueden crear y eliminar recursos reales de AWS, la identidad del servidor MCP de GKE puede ejecutar el reinicio gradual de una carga de trabajo o eliminar un pod en un clúster real, y la entidad de servicio del servidor MCP de Azure puede escribir secretos de Key Vault: usa cuentas desechables o credenciales de alcance muy limitado para los tres. Para probar cualquiera de ellos sin tocar ningún proveedor real, consulta [Probarlo](#trying-it-out) más abajo.

## Qué se registra {#what-gets-registered}

- **[Skill de agente](../guides/agent-skills.md) `Demo AWS EC2 Launch`** — recopila la configuración de la instancia, obtiene la aprobación explícita de un responsable y, después, lanza la instancia mediante una herramienta MCP. Su repositorio se clona en segundo plano tras el inicio, por lo que la skill aparece como `Clonando` durante un momento antes de poder usarse.
- **[Skill de agente](../guides/agent-skills.md) `Demo GKE Pod Restart`** — acuerda con el usuario el objetivo exacto (proyecto, clúster, espacio de nombres y un nombre de Deployment/StatefulSet o el nombre de un único pod), obtiene la aprobación explícita de un responsable para ese objetivo exacto y, después, de forma predeterminada, reinicia gradualmente la carga de trabajo mediante GKE MCP Server o, cuando el usuario solo quiere eliminar un pod, elimina ese pod para que su controlador propietario lo vuelva a crear, e informa del resultado. Su repositorio se clona de la misma forma, así que al principio también aparece como `Clonando`.
- **[Skill de agente](../guides/agent-skills.md) `Demo Azure Key Vault Secret Rotation`** — acuerda con el usuario el Key Vault y un secreto existente en él, obtiene la aprobación explícita de un responsable para ese secreto exacto y, después, escribe un valor aleatorio recién generado como nueva versión del secreto mediante Azure MCP Server e informa de cuándo se creó la nueva versión. Nunca muestra el valor en el chat. Su repositorio se clona de la misma forma, así que al principio también aparece como `Clonando`.
- **[Servidor MCP](../guides/mcp-servers.md) `AWS MCP Server`** — un servidor `stdio` que accede al AWS MCP Server administrado por AWS, de donde proceden las herramientas de EC2.
- **[Servidor MCP](../guides/mcp-servers.md) `GKE MCP Server`** — un servidor `streamable_http` que accede al servidor MCP administrado de GKE (Google Kubernetes Engine) de Google Cloud, el endpoint completo. Su encabezado `Authorization` es `Bearer ${gcp-token:demo-gcp-credentials/GOOGLE_CREDENTIALS_JSON}`, de modo que cada conexión envía un token de acceso nuevo generado a partir del secreto `demo-gcp-credentials`, y sus herramientas pueden gestionar clústeres y sus recursos de Kubernetes, lo que incluye reiniciar gradualmente una carga de trabajo o eliminar un pod.
- **[Servidor MCP](../guides/mcp-servers.md) `Azure MCP Server`** — un servidor `stdio` que ejecuta el Azure MCP Server de Microsoft, limitado a sus herramientas de Key Vault. Inicia sesión con la entidad de servicio del secreto `demo-azure-credentials`, y sus herramientas pueden enumerar y escribir secretos, claves y certificados de Key Vault. Antes de cada operación sobre un secreto pide consentimiento, y esa pregunta llega al solicitante de la ejecución como una [confirmación en el chat](../guides/workflow-executions.md#mcp-server-confirmations), además de la aprobación de la rotación por parte del responsable. La skill de demostración indica al agente de diseño que marque sus herramientas como herramientas que preguntan, de modo que cada tarea que usa una de ellas espera a que el solicitante la reanude. El nuevo valor del secreto pasa por la conversación del agente de camino a Key Vault, así que trata el chat de una ejecución como tratarías el propio secreto.
- **[Servidor MCP](../guides/mcp-servers.md) `EC2 Cost Estimator`** — un [servidor de script](../guides/mcp-servers.md#writing-a-script) de Python cuyas herramientas estiman el coste mensual bajo demanda de un tipo de instancia EC2 (`estimate_monthly_cost`) y clasifican varios por coste (`compare_instance_types`), con precios que obtiene en directo de la lista de precios de AWS para la región que indiques. Instala `boto3` en **Paquetes** y lee el mismo secreto `demo-aws-credentials`, por lo que probarlo en **Ejecución de prueba** requiere credenciales con permiso para leer la lista de precios de AWS (`pricing:GetProducts`). Solo realiza lecturas.
- **[Servidor MCP](../guides/mcp-servers.md) `Kubernetes Manifest Toolkit`** — un servidor de script de JavaScript cuyas herramientas comprueban si a un manifiesto de Kubernetes le faltan campos obligatorios (`validate_manifest`) y crean el parche que reinicia gradualmente un Deployment, StatefulSet o DaemonSet (`build_restart_patch`). Instala `js-yaml` en **Paquetes**, no necesita credenciales y nunca accede a un clúster, así que funciona directamente en **Ejecución de prueba**.
- **[Servidor MCP](../guides/mcp-servers.md) `Secret Value Generator`** — un servidor de script de JavaScript cuya única herramienta genera un valor de secreto aleatorio criptográficamente seguro (`generate_secret_value`). No instala paquetes, no necesita credenciales y nunca accede a Azure, así que funciona directamente en **Ejecución de prueba**.
- **[Base de conocimiento](../guides/knowledge-bases.md) `AWS EC2 Pricing`** — contiene una fuente, `ec2-on-demand-pricing.pdf`: una hoja de precios con el coste bajo demanda por hora y por mes, las vCPU y la memoria de los diez tipos de instancia que ofrece el [Recorrido guiado](./walkthrough.mdx), en `us-east-1`, `us-east-2` y `us-west-2`, además de los cargos por almacenamiento e IP pública. Las cifras son valores de referencia para la demostración. La fuente se registra como **Sin leer**, por lo que la base de conocimiento no tiene páginas hasta que alguien hace clic en **Leer** en ella; en el Recorrido guiado lo hace el desarrollador de AWS. Vinculada a un flujo de trabajo de lanzamiento de EC2, permite al agente responder cuánto costará la instancia solicitada.
- **[Secreto](../guides/secrets.md) `demo-aws-credentials`** — el ID de clave de acceso y la clave de acceso secreta de AWS que lee AWS MCP Server.
- **[Secreto](../guides/secrets.md) `demo-gcp-credentials`** — el JSON de credencial de Google Cloud a partir del cual GKE MCP Server genera su token de acceso.
- **[Secreto](../guides/secrets.md) `demo-azure-credentials`** — el ID de tenant, el ID de cliente y el secreto de cliente de la entidad de servicio de Azure con los que inicia sesión Azure MCP Server.
- **[Mocks de herramientas](../guides/tool-mocks.md)** — sustitutos de las herramientas con efectos secundarios de la ejecución de demostración: `aws___call_aws` y `aws___run_script` en AWS MCP Server, que devuelven cada uno un lanzamiento correcto; `patch_k8s_resource` y `delete_k8s_resource` en GKE MCP Server, que devuelven un reinicio gradual correcto y una eliminación de pod correcta, respectivamente; `keyvault_secret_get` y `keyvault_secret_create` en Azure MCP Server, que devuelven una lista de los secretos del Key Vault y una nueva versión del secreto, respectivamente; y el `request_approval` integrado, que devuelve aprobado. Al seleccionarlos en el cuadro de diálogo **Ejecutar** de una ejecución de un borrador, cualquiera de los tres flujos de trabajo puede terminar sin tocar AWS, un clúster de GKE real ni un Key Vault real, y sin esperar a un responsable.
- **[Etiquetas](../guides/tags.md)** `AWS`, `GCP` y `Azure` — cada una es una [etiqueta de control de acceso](../guides/tags.md#access-control-tags), de modo que solo los miembros de `Demo AWS Group`, `Demo GCP Group` y `Demo Azure Group` (además de los administradores y los superadministradores) pueden ver los registros anteriores etiquetados de ese proveedor. `EC2 Cost Estimator` y la base de conocimiento `AWS EC2 Pricing` llevan `AWS`, `Kubernetes Manifest Toolkit` lleva `GCP` y `Secret Value Generator` lleva `Azure`, junto con los registros del proveedor a los que ayudan. `Approval Required` es una etiqueta normal que llevan las tres skills de agente y no restringe nada.
- **Usuarios y grupos de demostración:**

| Usuario | Rol | Grupo de control de acceso | Qué hace |
|---|---|---|---|
| `demo-aws-developer` | Desarrollador | `Demo AWS Group` | Genera el flujo de trabajo de lanzamiento de EC2 |
| `demo-aws-reviewer` | Revisor | `Demo AWS Group` | Publica el flujo de trabajo de lanzamiento de EC2 |
| `demo-aws-requester` | Solicitante | `Demo AWS Group` | Ejecuta el flujo de trabajo de lanzamiento de EC2 |
| `demo-gcp-developer` | Desarrollador | `Demo GCP Group` | Genera el flujo de trabajo de reinicio de pods de GKE |
| `demo-gcp-reviewer` | Revisor | `Demo GCP Group` | Publica el flujo de trabajo de reinicio de pods de GKE |
| `demo-gcp-requester` | Solicitante | `Demo GCP Group` | Ejecuta el flujo de trabajo de reinicio de pods de GKE |
| `demo-azure-developer` | Desarrollador | `Demo Azure Group` | Genera el flujo de trabajo de rotación de secretos |
| `demo-azure-reviewer` | Revisor | `Demo Azure Group` | Publica el flujo de trabajo de rotación de secretos |
| `demo-azure-requester` | Solicitante | `Demo Azure Group` | Ejecuta el flujo de trabajo de rotación de secretos |
| `demo-approver-1`, `demo-approver-2` | Aprobador | `Demo Approvers` (las tres etiquetas) | Aprueban el lanzamiento, el reinicio del pod o la rotación |

Ninguno tiene el rol directamente: cada uno lo hereda de un [grupo de usuarios](../guides/users-and-groups.md#user-groups), `Demo Developers`, `Demo Reviewers`, `Demo Requesters` y `Demo Approvers`. Los tríos de AWS, GCP y Azure pertenecen además a un segundo grupo, `Demo AWS Group`, `Demo GCP Group` o `Demo Azure Group`, que no concede ningún rol propio: su único fin es tener la etiqueta de control de acceso correspondiente, para que ese trío pueda ver los registros etiquetados de ese proveedor y nadie más pueda, salvo los administradores (o un superadministrador), que [omiten por completo las etiquetas de control de acceso](../guides/tags.md#access-control-tags) y no necesitan pertenecer a ningún grupo para ello. `Demo Approvers` tiene directamente las etiquetas de control de acceso `AWS`, `GCP` y `Azure`, ya que un aprobador no se limita a un proveedor; esto es también lo que hace que cualquiera de los dos aprobadores de demostración sea un destino válido para una solicitud dirigida a él, sea cual sea el flujo de trabajo de demostración del que proceda.

## Probarlo {#trying-it-out}

El [Recorrido guiado](./walkthrough.mdx) lleva cualquiera de los ejemplos de principio a fin (generar, publicar, ejecutar, aprobar, confirmar) con un único inicio de sesión como `root`, [suplantando](../concepts/impersonation.md) por turnos a cada cuenta de demostración. Iniciar sesión con cada cuenta usando `DEMO_PASSWORD` funciona igual de bien; la tabla anterior indica quién hace qué.

`Demo AWS Group`, `Demo GCP Group` y `Demo Azure Group` solo ven los registros de su propio proveedor, así que `demo-aws-developer` no puede abrir `Demo GKE Pod Restart` y `demo-gcp-developer` no puede abrir `Demo Azure Key Vault Secret Rotation`. Cualquiera de las dos cuentas de aprobador sirve para todos los ejemplos, ya que `Demo Approvers` tiene directamente las tres etiquetas de control de acceso. Una ejecución real de GKE requiere que `DEMO_GCP_CREDENTIALS_JSON` contenga una credencial cuya identidad pueda acceder a un clúster de GKE real, y una rotación real requiere que la entidad de servicio de `DEMO_AZURE_*` tenga acceso de escritura a los secretos de un Key Vault real.

**¿No tienes cuenta de AWS, clúster de GKE ni Key Vault?** No publiques: ejecuta el flujo de trabajo mientras siga en `borrador`. Puede hacerlo, con el rol Desarrollador, la cuenta de desarrollador del proveedor (`demo-aws-developer`, `demo-gcp-developer` o `demo-azure-developer`), y solo el cuadro de diálogo de la ejecución de un borrador ofrece los [mocks de herramientas](../guides/tool-mocks.md) del tenant. En **Herramientas simuladas**, marca los sustitutos creados inicialmente que aparecen en la lista (`aws___call_aws` o `aws___run_script` para el lanzamiento, `patch_k8s_resource` o `delete_k8s_resource` para el reinicio del pod, `keyvault_secret_get` y `keyvault_secret_create` para la rotación, y `request_approval`); así, todo el flujo de trabajo se ejecuta sin acceder a un proveedor real ni esperar a una persona. Con los mocks de la rotación marcados, la lista de secretos del Key Vault también es ficticia: elige `db-password` en ella.

## Eliminarlo {#removing-it}

Al definir `DEMO_DATA=false` (o quitar la línea), **esos registros se eliminan de nuevo** en el siguiente inicio: el indicador es declarativo en ambos sentidos.

Por diseño, hay dos cosas que permanecen: un registro de demostración del que ha llegado a depender otra cosa (por ejemplo, un flujo de trabajo creado sobre la skill de demostración) se conserva y se deja constancia en el registro en lugar de eliminarlo, y un usuario de demostración que ha creado registros se elimina de forma lógica para que su nombre se siga resolviendo en esos registros.
