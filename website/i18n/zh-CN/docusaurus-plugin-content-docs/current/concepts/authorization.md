# 角色与授权

每位用户都持有一组**角色**，决定其可以执行哪些操作。角色之间**相互独立**，没有层级之分，只有一个例外：**超级管理员会绕过所有基于角色的检查**，也正因如此，它与其他所有角色**互斥**。一位用户要么是超级管理员，要么持有其余五种角色的某种组合，绝不会两者兼有。有两项所有权层面的检查是这一绕过规则的有意例外，两者都可以在下方的[会话访问矩阵](./authorization.md#workflow-execution-access)中看到。**完全没有角色**的用户也是有效的：他们仍可管理自己的[账户](../guides/users-and-groups.md#users)（头像和语言），但除此之外什么也做不了。

## 有效角色 {#effective-roles}

用户通过两种途径获得角色，所有授权检查都使用两者的**并集**，即用户的**有效角色**：

- **直接授予**：在[用户](../guides/users-and-groups.md#users)页面上授予到用户记录。
- **继承**：来自用户所属的[用户组](../guides/users-and-groups.md#user-groups)。把角色分配给用户组，就等于授予给所有成员。

![流程图，显示用户记录上直接授予的角色和从用户组继承的角色共同构成用户的有效角色，所有授权检查都使用这一并集。](./img/authorization-effective-roles.svg#gh-light-mode-only)
![流程图，显示用户记录上直接授予的角色和从用户组继承的角色共同构成用户的有效角色，所有授权检查都使用这一并集。](./img/authorization-effective-roles-dark.svg#gh-dark-mode-only)

仅通过用户组持有的角色与直接授予的角色效力完全相同：能通过同样的门禁，使用户有资格成为审批人，也同样保护用户免遭[代理登录](./impersonation.md)。这里没有任何缓存，并集在每个请求上解析，因此把某人加入或移出用户组都会立即生效，无需重新同步。

用户组本身也可以作为对象：[审批](../guides/approvals.md#human-approval)可以发给用户组而不是个人，持有审批人角色的任何成员都可以处理它。

**用户组永远无法授予超级管理员角色**：UI 不提供此选项，API 会拒绝（HTTP 422），数据库的检查约束则为两者提供保障。由于超级管理员是平台级的，而用户组恰好属于一个[租户](./tenants.md)，超级管理员也永远不可能成为用户组的成员。

## 角色 {#the-roles}

| 角色 | 授予的权限 |
|---|---|
| 超级管理员 | 一切权限（绕过所有角色门禁；但**不会**绕过[下方矩阵](./authorization.md#workflow-execution-access)中针对指定审批人的两项检查） |
| 管理员 | 用户 CRUD、密钥 CRUD、删除工作流执行，以及对其租户内所有工作流执行及其任务和聊天历史记录、所有审批的只读可见性（请参阅[工作流执行及其工作流会话](./authorization.md#workflow-execution-access)。除了删除以外，管理员不能驱动执行的代理、更改其任务的状态或处理审批） |
| 开发人员 | 密钥 CRUD、MCP 服务器 CRUD、[工具模拟](../guides/tool-mocks.md) CRUD、代理技能 CRUD、工作流的生成和编辑（包括重新生成工作流由 AI 生成的**生成提示词**，不过只有超级管理员才能直接编辑该字段）、任务模板 CRUD、驱动设计会话的聊天、运行工作流（`POST /workflows/{id}/execute`），包括运行 `草稿` 工作流和 `已修改` 工作流尚未发布的编辑，以便在发布前测试。发布和停用**不**包含在内，那是审阅者的职责 |
| 审阅者 | 发布和停用工作流，即开发人员不再执行的这两项操作。对工作流拥有与开发人员相同的完整读取可见性：`草稿` 工作流、`已修改` 工作流尚未发布的编辑以及设计会话的聊天历史记录，审阅者读到的内容都与开发人员相同。不能编辑工作流及其任务模板，也不能驱动其设计会话 |
| 请求者 | 运行**已发布**（以及 `已修改`）的工作流（`POST /workflows/{id}/execute`），运行的始终是上次发布的设计 |
| 审批人 | 有资格成为工作流审批的指定审批人（以个人身份，或作为审批所发往用户组的成员），并处理自己的审批 |

初始的 **`root`** 用户持有超级管理员角色，属于平台级（没有租户）。在 **Default** 租户内创建的 **`admin`** 用户持有管理员角色，限定在该租户内；其他所有用户一开始都没有角色。

## 角色控制什么 {#what-roles-gate}

**读取保持开放。** 只有写入、工作流执行和审批受角色控制；所有已通过认证的用户都可以 `GET` 这些集合（UI 需要用它们来解析名称、选择审批人和列出工作流）。无论什么角色，API 都不会返回密钥的*值*。

工作流的**提示词**和**生成提示词**（即告诉运行要做什么的文本）只向管理员、开发人员、审阅者或超级管理员显示。其他人读取工作流及其运行时，这些字段都是空的。工作流的[版本历史记录](../guides/workflows.md#version-history)同样仅限这些角色；请求者或审批人无法打开它。工作流的**描述**则对所有能打开该工作流的人可见。

唯一的例外根本不是角色：带有[访问控制标签](../guides/tags.md#access-control-tags)的记录，只有所属用户组合起来带有该记录上全部此类标签的用户才能看到，此外管理员和超级管理员都会绕过这一限制。其他人既看不到记录，也看不到它存在的任何迹象。

角色在[用户](../guides/users-and-groups.md#users)管理页面上分配，也可以在[用户组](../guides/users-and-groups.md#user-groups)页面上批量分配；只有超级管理员才能授予或撤销超级管理员角色。被拒绝的请求返回 HTTP 403（`FORBIDDEN`）。

### UI 隐藏什么 {#what-the-ui-hides}

管理界面会隐藏用户角色不允许的操作和导航项，因此被拒绝的请求通常根本无从发出，而不只是遭到拒绝：

| 界面 | 没有相应角色时 |
|---|---|
| **列表页** | 隐藏添加按钮和每行的操作列，也就是删除，以及 MCP 服务器的“浏览注册表”（它只会进入创建表单） |
| **详情页** | 以**只读**方式呈现：每个字段都显示为内凹的值而不是输入框，保存和删除不会出现，取消变为返回 |
| **创建表单**（`/<section>/new`） | 显示拒绝访问的界面。能到达这里只可能是通过深层链接，因为通往这里的添加按钮已被隐藏 |

由于读取保持开放，没有写入权限的人也可以打开详情页：代理技能、MCP 服务器、工具模拟、密钥、租户、用户、工作流和任务模板都会采用上述只读呈现方式。此时密钥的条目只列出键（值本来就不会返回），用户的密码字段则被完全省略。对*所有人*都不可变的字段，例如租户的 `name` 和用户的 `username`，无论角色如何都以相同方式呈现。创建表单没有只读形式，所以它返回的是一个界面，而不是表单。

## 会话访问 {#session-access}

A2Flow 有两种聊天，它们通过两种不同的方式控制访问：

- **设计会话**是设计工作流的聊天。访问权限由**角色**决定：设计是开发人员的工作，因此租户内的开发人员共享它并可以驱动它；审阅者也可以读取它，以便在发布前审阅设计，但不能驱动它。
- **工作流会话**是一次运行所在的聊天。访问权限由**参与关系**决定：发起运行的人和被要求审批其中某项内容的人共享它，与他们的角色无关。

![访问矩阵，显示开发人员、工作流的创建者和超级管理员可以进入设计会话，审阅者对其拥有只读访问权限；运行的发起人、指定审批人和超级管理员可以进入工作流会话，管理员对工作流会话拥有只读访问权限。](./img/authorization-session-matrix.svg#gh-light-mode-only)
![访问矩阵，显示开发人员、工作流的创建者和超级管理员可以进入设计会话，审阅者对其拥有只读访问权限；运行的发起人、指定审批人和超级管理员可以进入工作流会话，管理员对工作流会话拥有只读访问权限。](./img/authorization-session-matrix-dark.svg#gh-dark-mode-only)

### 设计会话 {#design-session-access}

工作流的设计聊天（`GET /workflows/{id}/messages`、`POST /workflows/{id}/agent`）按角色而不是按每条记录的参与关系共享，这样团队就可以一起完善设计。

| 对象 | 读取历史记录 | 驱动代理 |
|---|---|---|
| 租户内的任何**开发人员** | ✅ | ✅ |
| 租户内的任何**审阅者** | ✅ | ❌ 403 |
| 工作流的**创建者**（`createdBy`），即使已失去开发人员角色 | ✅ | ✅ |
| **超级管理员** | ✅ | ✅ |
| 其他所有人 | ❌ 403 | ❌ 403 |

明确放行创建者，意味着没有人会被锁在自己发起的聊天之外。其他租户的工作流 ID 返回 **404**，绝不会返回 403。唯一的例外是超级管理员选择[所有租户](./tenants.md#all-tenants)时的 `GET .../messages`：此时工作流的解析不受租户限制，由这里的角色、创建者和超级管理员检查代替租户边界。

### 工作流执行及其工作流会话 {#workflow-execution-access}

除角色之外，对工作流执行的每项操作都要求调用方是该执行的**发起人**（运行工作流的用户），或是**其某项审批的指定审批人**，即被指名的用户，或审批所发往用户组中持有审批人角色的成员（请参阅[人工审批](../guides/approvals.md#human-approval)）。这样既保留了审批人共享的设计（审批人加入发起人的聊天），又把第三方挡在外面。读取的范围更宽，而实际动作的操作范围更窄：

| 操作 | 端点 | 发起人 | 指定审批人 | 管理员（同一租户） | 超级管理员 |
|---|---|---|---|---|---|
| 读取执行 | `GET /workflow-executions/{id}` | ✅ | ✅ | ✅ | ✅ |
| 列出或打开其任务 | `GET .../workflow-tasks` | ✅ | ✅ | ✅ | ✅ |
| 读取工作流会话的历史记录 | `GET .../messages` | ✅ | ✅ | ✅ | ✅ |
| 驱动其代理 | `POST .../agent` | ✅ | ✅ | ❌ | ✅ |
| 更改任务的**状态**（手动或通过代理） | `PATCH /workflow-tasks/{id}` | ✅ | 仅限发给他们的审批所涵盖的任务 | ❌ | 仅限没有任何审批涵盖的任务 |
| 处理审批 | `PATCH /approvals/{id}` | ❌ | 仅限该审批的审批人 | ❌ | ❌ |
| 删除执行 | `DELETE /workflow-executions/{id}` | 仅当同时是管理员 | 仅当同时是管理员 | ✅ | ✅ |

这些列之外的任何人都会收到 HTTP 403。同一个 `GET /approvals` 列表会向管理员显示租户内的所有审批，与上面的读取行一致。

运行的**任务列表在执行工作流时就已固定**：任务从工作流已发布的模板复制而来，此后只有其 `status`（以及失败原因）会改变。任何人都不能通过 API 添加、删除运行的任务，或者更改其标题、描述和依赖关系；要更改步骤，请编辑[任务模板](../guides/workflows.md#adjusting-the-task-templates)后重新运行。

**最后三行值得多读一遍。**

状态行和处理审批行，就是本页开头提到的**超级管理员绕过规则的所有权层面例外**：只有指定审批人才能处理审批，而任务的状态只能由发起人，或者由**涵盖该任务**的审批所发往的审批人更改。并非该执行的任何审批人都可以，而且（一旦有审批涵盖该任务）超级管理员或管理员也不行。审批人只能在被要求审批的范围内推进任务，即审批指定的任务及其之后直到下一个审批之前的步骤，这样决定既能让运行继续，又不会让审批人推进无关的步骤。否则，只要把任务直接改为 `已完成`，任何人都可以代替被指定的审批人（请参阅[人工审批](../guides/approvals.md#human-approval)）。无论是手动更改，还是在工作流会话的聊天中请执行代理更改，规则都相同：代理会拒绝其驱动者本来无法直接进行的状态更改。

**删除**执行则完全相反：这是一道单纯的角色门禁，完全不涉及所有权，因此管理员可以删除租户内的任何执行，而不是管理员的发起人却不能删除自己的执行。删除时，运行的任务及其工作流会话也会一并删除。

## 平台级分区 {#platform-wide-sections}

[租户](../guides/users-and-groups.md#tenants)和[系统设置](../guides/system-settings.md)是**超级管理员**专属的两个管理分区。与其他地方不同，这里的读取也受到控制：两者保存的都是平台级配置而不是租户数据，因此侧边栏入口、欢迎卡片以及背后的所有端点都对其他角色关闭。

## 审批人资格随时间的变化 {#approver-eligibility}

⚠️ 审批人资格在创建审批时验证：`list_users` / `list_user_groups` 只提供确实能够审批的目标，`request_approval` 会拒绝其他任何目标（包括没有符合资格成员的用户组）。*此后*会发生什么取决于目标类型，这一差异是有意为之：

- **目标为用户**：之后撤销审批人角色，**不会**使已发给该用户的审批失效。他们仍可处理这些审批，因此进行中的工作流绝不会卡住。
- **目标为用户组**：成员身份和角色会在作出决定时重新检查，因为“用户组”是一个不断变化的集合，而不是固定的某个人。这让新加入的成员可以接手待处理的请求，但也有另一面：撤销用户组的审批人角色授予，或用户组中不再有符合资格的成员，都会让待处理的请求变得**无人可以处理**，其运行也会无限期等待。重新授予角色或重新添加成员，就能立即解除阻塞。
