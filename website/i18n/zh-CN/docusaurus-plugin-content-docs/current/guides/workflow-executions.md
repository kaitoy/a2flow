# 工作流执行

工作流执行是[工作流](./workflows.md)的一次运行。它保存工作流名称、描述、任务和标签的副本，因此即使来源工作流后来被编辑或删除，运行历史仍忠实反映实际运行的内容。

在管理侧边栏中打开**工作流执行**即可浏览。与其他分区不同，运行是历史记录，而不是可编辑的记录，因此没有编辑表单：它的界面要么显示运行，要么让您加入运行。它的**标签**列和字段出于同样的原因是只读的，详见[工作流执行和审批的标签](./tags.md#execution-and-approval-tags)。

| 界面 | 进入方式 | 显示内容 |
|---|---|---|
| **工作流执行**列表 | 管理侧边栏 → 工作流执行 | 所有运行及其状态，以及每行的操作 |
| **工作流会话** | 行上的“打开工作流会话”操作 | 运行所在的聊天：加入、观看、回答 |
| **工作流任务** | 行上的任务链接 | 运行的任务及其状态，只读，可用“表格”或“图表”方式查看 |
| **工具调用** | 运行详情页的页眉 | 运行发起的 MCP 工具调用，以及每次调用的判定结果 |

**已模拟**标记用[工具模拟](./tool-mocks.md)替换了任意工具的运行。

[**列**菜单](./admin-ui.md#choosing-columns)还提供两个默认隐藏的列。**工作流**以当前名称显示运行的上级工作流并链接到它：每行自身的名称是运行开始时固定的快照，因此通过此列可以看到该工作流现在的名称。**草稿**为[测试运行](./workflows.md#running-a-workflow)显示对勾，即从仍为 `草稿` 的工作流启动的运行，或运行 `已修改` 工作流的[未发布的编辑](./workflows.md#trying-the-edits-out)。这两种情况运行的都是未经任何人批准的设计，因此不计入[运维指标](../operations/metrics.md)；此列可用作“是/否”筛选器来隐藏它们。

运行的详情页显示其**版本**：即运行复制任务时所依据的工作流已发布版本，例如 `v3`；测试运行显示 `—`，因为它运行的设计没有版本记录。请参阅[版本历史记录与回滚](./workflows.md#version-history)。

## 运行状态 {#run-status}

![状态机图：运行以“运行中”开始，只等待某个时间时变为“已计划”，恢复后回到“运行中”；所有任务结束且无失败时定为“已完成”，所有任务结束且至少有一个失败时定为“失败”。](./img/workflow-executions-status.svg#gh-light-mode-only)
![状态机图：运行以“运行中”开始，只等待某个时间时变为“已计划”，恢复后回到“运行中”；所有任务结束且无失败时定为“已完成”，所有任务结束且至少有一个失败时定为“失败”。](./img/workflow-executions-status-dark.svg#gh-dark-mode-only)

运行以 `运行中` 开始；当它至少有一个任务，且每个任务都进入终止状态（`已完成`、`失败` 或 `已跳过`）时，运行结束。包含失败任务的运行以 `失败` 结束。完成时间在此刻记录，之后的编辑不会改变它；完全没有任务的运行会一直保持 `运行中`。[运维指标](../operations/metrics.md)统计的就是这些数字。

当未结束的运行除了等待某个时间外无事可做时（某个任务要求等待，其会话显示**已计划，直到 …**，且其他所有会话都处于空闲或已完成状态），运行显示 `已计划` 而不是 `运行中`。一旦有会话恢复，无论是时间已到还是有人发送了消息，运行就会回到 `运行中`。[运维指标](../operations/metrics.md)把 `已计划` 的运行与 `运行中` 的运行一样计为活跃。

任务失败时，仍在等待它的任务（无论直接依赖还是沿依赖链间接依赖）都会被设为 `已跳过`，因为它们已无法运行；正因如此，运行才能结束，而不会卡在永远不会启动的任务上。不依赖失败任务的分支上的任务不受影响，因此失败后运行可能仍会处于 `运行中` 状态一段时间，直到这些任务也结束。

## 工作流会话界面 {#the-workflow-session-screen}

工作流会话是一次运行所在的聊天。打开时已有运行的启动消息，代理也已在工作：运行一创建就开始，不管是否有人打开此界面。

![流程图，展示工作流会话界面的布局：任务时间线与按任务分组的消息并排显示，消息下方通向聊天输入框。](./img/workflow-executions-layout.svg#gh-light-mode-only)
![流程图，展示工作流会话界面的布局：任务时间线与按任务分组的消息并排显示，消息下方通向聊天输入框。](./img/workflow-executions-layout-dark.svg#gh-dark-mode-only)

### 谁共享此聊天 {#who-shares-it}

运行的聊天由**参与者共享**，并非启动者私有：

| 人员 | 获得的内容 |
|---|---|
| 启动运行的**发起人** | 完整对话和聊天输入框 |
| 其某个[审批](./approvals.md)的**指定审批人** | 相同的对话和状态：批准会恢复原来的运行，而不是启动一个全新的空运行。只有审批本身由他们操作：代理为其他步骤渲染的输入表单，或 [MCP 服务器请求的确认](#mcp-server-confirmations)，对他们都是只读的，下方显示“正在等待发起人响应。”的提示 |
| 该租户的**管理员** | 只读查看 |
| 其他任何人 | 无权访问 |

当审批发送给某个**用户组**时，持有审批人角色的每位成员都是参与者，因此聊天的访问范围随用户组成员变化：将某人加入审批组，就会向其开放该用户组被请求审批的所有运行，将其移出则再次关闭。这是“任何成员都可以作出决定”的直接结果：聊天访问权限的存在正是为了让人能够作出决定。未持有审批人角色的成员不会因成员身份获得任何权限。

### 发送者头像 {#sender-avatars}

由于多人（发起人、审批人和代理）会在同一个聊天中发言，每条消息都带有**发送者头像**。将鼠标悬停在头像上可显示发送者姓名；代理的徽章则显示工作流名称。点击渲染的交互界面中的按钮也以同样的方式归属：点击生效后，该界面旁会显示操作用户的头像。

### 任务时间线 {#the-task-timeline}

左侧边缘有一条可折叠的**任务时间线**：按顺序列出运行的任务，每个任务都带有编号和按状态着色的徽章，进行中的任务会高亮显示。聊天将属于同一任务的连续消息包裹在一个**任务组**中（左侧有按状态着色的竖条，编号标题与时间线徽章一致），因此每个任务的边界一目了然。

两者双向联动：

- 滚动聊天时，视口顶部的任务会在时间线中高亮显示。
- 将鼠标悬停在时间线条目或聊天分组上，会高亮显示对应的另一方。
- 点击时间线条目，聊天会滚动到该任务的分组。

### 实时更新 {#live-updates}

每位正在查看运行的参与者都能实时看到每条回复的生成过程，无论是谁的消息触发的，也包括 A2Flow 自行运行的轮次，例如启动、审批后的恢复，以及等待某个时间的会话的恢复。回复开始时（如果是对您自己发送的消息的回复，无论您滚动到哪里；如果是对他人消息的回复，则仅在您接近底部时），聊天会一次性滚动，使最新的消息位于屏幕顶部，回复会写在其下方的空白处；写入期间视图保持不动，即使回复超出了屏幕底部也是如此。不在回复期间时，只有当您已滚动到接近底部时，视图才会跟随新消息滚动到底部；当您向上滚动阅读之前的消息时，视图不会滚动。当屏幕下方看不到的位置有新消息到达，或回复在那里写完时，聊天底部会显示 **下方有新消息** 按钮。点击它即可跳转到最新消息；如果回复仍在写入，视图会一直跟随直到写完。

您发送的消息要等代理空闲：代理仍在处理某一轮时，消息会被拒绝，回复结束后可以重新发送。等待审批的会话不接受消息，因为只有审批决定才能推动它继续。此时发送的问题会转到[咨询](#consultations)。

[设计会话](./workflows.md#adjusting-the-task-templates)也是共享聊天，头像相同。不过它由租户的开发人员共享，而不是由运行的参与者共享，并且每隔几秒自动刷新，而不会实时显示其他人的回复生成过程。

### 分支会话 {#branch-sessions}

当运行的任务图出现分支时，A2Flow 可能会把运行拆分到多个会话中，让各分支同时推进，详见[并行分支](../architecture/workflow-execution.md#parallel-branches)。这时面包屑导航下方会出现一排选项卡，每个会话一个，并标有其状态：

| 选项卡 | 说明 |
|---|---|
| **主会话** | 运行开始时所在的会话。负责汇合以及已完成分支之后的任务 |
| **分支 1**、**分支 2**、… | 分支会话，在某分支就绪而其会话正忙时分叉出来 |
| **咨询 1**、… | [咨询](#consultations)，由会话等待审批期间提出的问题开启 |

| 状态 | 含义 |
|---|---|
| 排队中 | 即将开始一轮 |
| 运行中 | 代理正在工作 |
| 等待输入 | 输入表单正在等待回答 |
| 等待审批 | 此会话请求的审批尚未决定 |
| 等待发起人 | 下一个任务运行时会[向发起人提问](#mcp-server-confirmations)，因此等待发起人从聊天中继续 |
| 已计划，直到 … | 任务必须等待某个时间；会话会在显示的时间自动恢复。向它发送消息可提前恢复 |
| 空闲 | 当前无事可做；会话等待下一个任务 |
| 已完成 | 会话已完成工作。已完成的分支会为主会话留下摘要 |
| 错误 | 上一轮失败 |

点击选项卡可打开该会话的聊天；视图跟随所选会话，URL 也会记住它，因此指向此页面的链接会打开同一选项卡。从未分支且没有咨询的运行不显示选项卡。

### 咨询 {#consultations}

等待审批的会话不接受消息，但请求仍可能引发疑问，例如实例的费用是多少，或者为什么选择这个目标。会话等待期间，聊天输入框上方的提示会说明问题将转到咨询。

1. 在等待中的会话的聊天中输入问题并发送。
2. **咨询**选项卡随即打开并显示您的问题，代理在其中回答。它从等待中的会话在发起审批请求之前所知道的一切开始，还可以读取关联到工作流的[知识库](./knowledge-bases.md)。它不能使用 MCP 服务器的工具，因此需要重新查看目标系统的问题必须等运行继续后才能解决。
3. 继续在该选项卡中提问。共享聊天的每个人都可以在此发言，因此审批人和启动运行的人也可以彼此讨论该请求。每条消息都会显示发送者。
4. 照常对审批作出决定。决定后咨询关闭：其选项卡变为**已完成**，不再接受消息。

| 咨询 | |
|---|---|
| 可以 | 根据请求的上下文、关联的知识库、运行的任务和审批以及会话中的文件作答 |
| 不能 | 使用任何 MCP 服务器工具、更改任务、请求审批、安排等待或添加文件 |
| 留下的内容 | 运行中不留下任何内容。等待中的会话永远看不到其中说过的话；对话仍可在其选项卡中阅读 |

在同一审批作出决定之前再次提问，会转到同一个咨询。

### 建议回复 {#suggested-replies}

当代理停下来等您（提出了问题、需要某个值或需要确认继续）时，聊天输入框上方会出现一排**建议回复**：几条它预期的简短回答，例如 `好的，继续` 或 `跳过此步骤`。

| | |
|---|---|
| **点击其中一条** | 将该文本放入聊天输入框。不会发送，您可以编辑后发送，或直接发送 |
| **代理工作期间** | 此行隐藏，随代理的下一个问题再次出现 |
| **您回复之后** | 此行消失，下一个问题会带来新的建议 |
| **重新加载之后** | 同一行仍在，每位可以发送消息的参与者都能看到 |

这些建议是代理对您可能输入内容的猜测，而不是仅有的可选答案：答案固定的问题会改为在消息内以选项形式提出。此行是工作流会话的功能，设计会话没有。

### 来自 MCP 服务器的确认 {#mcp-server-confirmations}

有些 MCP 服务器会在工具调用中途停下来，先询问某人后才继续，例如 Azure MCP Server 在每次操作 Key Vault 密钥前都会征求同意。这类工具在工作流设计中标记为**询问发起人**：在生成工作流时或在其设计会话中，告诉设计代理哪个任务的工具会询问。未标记的工具不允许询问，其调用会失败而不是等待。

使用已标记工具的任务会在启动前等待运行的发起人，这样问题出现时发起人就在场：

1. 运行到达该任务时，其会话显示**等待发起人**，发起人会收到“输入请求”[通知](./notifications.md)。这期间不会计时。
2. 发起人打开运行的聊天。聊天输入框上方的提示会指明该任务，并带有**继续**按钮。其他人只能看到运行正在等待发起人。
3. **继续**会以发起人的名义发送一条消息，任务随即启动。发起人自己输入任何消息也有同样效果。
4. 每个问题在聊天中显示为一张标题为“*服务器* 请求确认”的卡片，指明正在等待它的工具，下方附有一个小表单。

| | |
|---|---|
| **谁来回答** | 只有运行的发起人。审批人和管理员能看到问题，下方显示“正在等待发起人响应。” |
| **接受** | 发送表单的值。其含义由服务器决定，例如 Azure MCP Server 的表单是在 **Approve** 和 **Reject** 之间选择 |
| **谢绝** | 拒绝回答 |
| **取消** | 不作选择，关闭问题 |
| **等待期间** | 代理的这一轮仍在运行，因此聊天输入框保持禁用 |
| **如果无人回答** | 问题会过期（默认 15 分钟，除非部署[另有设置](../operations/configuration.md#mcp-tools-and-approvals)），并告知服务器问题已被关闭 |

此卡片属于提问的那一轮。该轮结束后，聊天中工具调用自身的那一行会记录结果。

### 会话中的文件 {#files-in-the-session}

工作流会话既承载消息，也承载文件。使用聊天输入框旁的**回形针**按钮附加文件，或将文件拖放到输入框的任意位置：每个文件显示为输入框上方的胶囊，点击胶囊上的 × 可将其移除。在您发送消息之前不会发送任何内容，因此移除胶囊只是丢弃该文件，它永远不会进入运行。

您发送的消息会注明随附的文件，因此重新加载后聊天记录仍会显示附件。服务器会另行告知代理这些文件，代理可以：

| 可以 | 不能 |
|---|---|
| 列出会话的文件 | 更改任何人附加的文件 |
| 读取文本文件 | 删除文件 |
| 添加自己的新文件 | 访问其他运行的文件 |

代理写入的文件在聊天中显示为带**下载**按钮的卡片。由于代理只能添加，如果它写入的文件名在会话中已存在，文件会以带编号的变体（`report (2).csv`）存储，而不会替换原有文件；卡片上显示的是实际存储的文件名。

读取仅限文本。电子表格、图片或归档文件会完整存储并可下载，但代理无法读取；如果它需要其中的内容，请提供文本导出。

| | |
|---|---|
| **谁可以附加** | 运行的发起人和指定审批人，也就是能够推动运行的人。只是查看的管理员不能附加 |
| **谁可以下载** | 能阅读聊天的所有人，包括管理员 |
| **保留时长** | 与运行相同。删除运行会删除其文件 |
| **大小限制** | 按部署设置，详见[配置](../operations/configuration.md#session-files) |

文件发送后不能逐个移除，因此会话的文件随运行一起删除。

## 工作流任务 {#workflow-tasks}

此处运行的任务是只读的：模板在[工作流](./workflows.md#adjusting-the-task-templates)上编辑，运行的状态由执行代理和审批流程推进。

每个任务都有状态（`待处理`、`进行中`、`已完成`、`失败` 或 `已跳过`）和依赖关系。**表格 / 图表**切换按钮可在列表和依赖图之间切换。依赖图按依赖顺序将任务堆叠成一个垂直列，前置任务位于依赖它们的任务之上，每个任务向右分支到其绑定工具所属的 MCP 服务器，再分支到各个工具。依赖图可以平移、缩放和适应视图，但不能编辑。

## 工具调用 {#tool-invocations}

此页面列出运行期间发起的 MCP 工具调用，以及[网关](../architecture/mcp-gateway-and-proxy.md)对每次调用的判定：`已允许` 的调用已发往上游，`已拒绝` 的调用被某条规则否决；同时显示工具、服务器、拒绝原因和所出示的[工具证书](./approvals.md#human-approval)。参数仅以摘要形式显示，原始值绝不存储。

对[已模拟](./tool-mocks.md)工具的调用无论结果如何都不会出现在此处。网关会像检查其他调用一样检查已模拟的调用，但一个注定由存储响应回答的调用不会到达任何服务器，因此它的批准或拒绝都不属于这份记录。要检查被模拟的调用，请查看运行的聊天记录。

## 删除运行 {#deleting-a-run}

行上的**删除**操作会在确认提示后移除运行：记录、其任务和工作流会话都会一并删除。
