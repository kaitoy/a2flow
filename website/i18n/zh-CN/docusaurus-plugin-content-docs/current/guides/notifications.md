# 通知

工作流的工作在后台进行：设计运行可能在您离开时结束，审批可能在等待一位还没打开应用的人。通知就是把这些事件送达相关人员的方式。

**铃铛图标**位于顶部工具栏，聊天页眉和管理侧边栏上都有，并带有未读数徽章。

## 五种事件 {#the-five-events}

| 类型 | 触发时机 | 接收者 |
|---|---|---|
| 草稿就绪 | [生成工作流](./workflows.md#generating-a-workflow)的后台设计运行已结束，草稿的任务模板可供审阅。 | 发起生成的人 |
| 生成失败 | 同一设计运行失败。它在无人值守、没有客户端查看的情况下运行，因此您要靠这条通知得知结果；原因显示在工作流的详情页及其设计聊天中。 | 发起生成的人 |
| 审批请求 | 代理在执行中途请求决定并等待。 | [指定的审批人](./approvals.md#human-approval)；目标为用户组时，每位符合条件的成员各收到一条 |
| 执行完成 | 一次运行中的每个任务都已进入终止状态。每次运行只触发一次。 | 发起运行的人 |
| 输入请求 | MCP 服务器会请求[确认](./workflow-executions.md#mcp-server-confirmations)的任务即将开始，运行正等待您从聊天中继续。 | 发起运行的人 |

点击通知会将其标为已读，并跳转到它指向的位置：与运行相关的事件跳转到该运行的聊天，与工作流相关的事件跳转到工作流详情页。

## 通知的显示位置 {#where-notifications-appear}

| | **铃铛下拉面板** | **[通知页面](./notifications.md#notification-history-page)** |
|---|---|---|
| **显示内容** | 仅未读通知，即仍需处理的内容 | 完整历史记录，包括已读通知 |
| **进入方式** | 工具栏中的铃铛 | 工具栏的个人资料按钮 → **通知** |
| **标为已读** | 每行（✓），以及仍有未读通知时面板标题中的**全部标为已读** | 每行（✓） |
| **删除** | 不提供 | 每行（✕），需确认 |

下拉面板中没有任何操作会删除通知；标为已读只是让它不再显示在这里。列表每半分钟自动刷新一次，因此无需重新加载即可收到新通知。

## 通知历史记录页面 {#notification-history-page}

通知页面以可排序、可筛选的表格列出您收到的所有通知，包含标题、类型和创建时间。在**已读**列中筛选**是**或**否**，即可只看已读或未读通知。这是唯一可以永久删除通知的地方。

A2Flow 自身的通知以[您的语言](./users-and-groups.md#language)显示，而审批的标题和描述保持代理撰写时的样子。按标题排序和筛选基于英文文本，因此在英语以外的语言中，**标题**列不提供这两项功能；请改用**类型**筛选。

通知始终按用户区分：您只能看到自己的通知，而通知会随其所属的账户、运行或工作流一起消失。

## 邮件投递 {#email-delivery}

当超级管理员在[系统设置](./system-settings.md)中配置好 SMTP 服务器后，同样的五种事件还会**通过电子邮件**发送给接收者，这样审批请求就不必等到有人打开应用。

邮件以通知的标题作为主题，以通知正文作为内容，并附上指向相关对象（执行或工作流）的链接。该链接根据运维人员在部署时设置的部署基础 URL 生成（请参阅[服务器设置](../operations/configuration.md#server-settings)）；未设置时，邮件发出时不带链接。

无法送达的接收者会在联系中继之前被跳过：内部系统用户、已停用或已删除的账户、地址未验证的账户，以及没有地址的账户。没有按用户退订的选项：邮件投递对整个平台要么开启，要么关闭。

### 投递队列 {#the-delivery-queue}

工作流操作仍在进行时不会发送任何内容。通知及其完整渲染的邮件会一起写入，因此即使发生崩溃，也不会出现通知已存在而邮件从未入队的情况。随后由工作进程清空该队列：

- **限速。** 速率限制将中继控制在每秒固定的邮件数量，整批邮件通过同一条复用的连接发出。
- **重试。** 临时性故障（中继宕机，或拒绝凭据）会安排再次尝试，退避时间逐渐增长：15 秒、30 秒、1 分钟、2 分钟，不断翻倍直至一小时。默认的重试额度大约可以撑过一小时的停机。
- **无望时放弃。** 中继报告为永久性的失败（例如收件人不存在）完全不会重试。尝试次数用尽或已永久失败的邮件，会以 `失败` 状态连同最后的错误留在队列中：这是可供查看的死信，而不是悄无声息的丢失。已投递的邮件在 30 天后清除；死信则保留。

同一时间只有一个进程发送，正因如此，速率限制才是精确而非近似的。运行多个工作进程带来的是故障转移，而不是吞吐量。发送进程在批次中途崩溃不会消耗尝试次数：下一轮会接回它的工作。

默认情况下，由 API 进程自身运行工作进程。在 Docker Compose 下则运行专用的工作进程服务，使邮件处理不占用处理请求的进程。所有可调参数都列在[配置参考](../operations/configuration.md#outgoing-email-queue)中。

积压和中继卡住的症状可在[指标端点](../operations/metrics.md)上看到。
