# 审批门禁

[审批](../guides/approvals.md)同时做两件事：它让运行停在某个步骤上，直到有人作出决定；它还把这个决定变成一份已签名的授权，明确说明它所涵盖的步骤此后可以做什么。

![审批的时序图：执行代理请求审批，A2Flow 通知审批人，同时被涵盖的步骤保持阻塞；审批人作出决定后，A2Flow 在每个被涵盖的步骤启动时向其授予证书，并让运行继续。](./img/approvals-sequence.svg#gh-light-mode-only)
![审批的时序图：执行代理请求审批，A2Flow 通知审批人，同时被涵盖的步骤保持阻塞；审批人作出决定后，A2Flow 在每个被涵盖的步骤启动时向其授予证书，并让运行继续。](./img/approvals-sequence-dark.svg#gh-dark-mode-only)

## “阻塞”意味着什么 {#what-blocked-means}

这种暂停并不是代理在礼貌地等待。

| 审批尚未决定期间 | |
|---|---|
| 被涵盖的步骤可以调用什么 | 其绑定的 MCP 工具一个也不能调用；调用在到达服务器之前就会被拒绝 |
| 由谁强制执行 | [网关](./mcp-gateway-and-proxy.md)，这是它检查的一条规则，而不是代理指令中的一句话 |
| 什么触发门禁 | 涵盖该步骤的审批的*存在*本身。待处理和已驳回的审批同样会阻塞，因此门禁在失败时保持关闭 |
| 什么不受影响 | 没有审批涵盖的步骤，它们继续按普通的工具绑定规则运行 |

因此，提示词注入或程序错误都无法靠说服通过这道门禁，因为根本没有可以说服的对象。唯一能打开它的，是针对该审批记录下来的决定。

## 证书 {#the-certificate}

审批涵盖的每个步骤都会在启动时获得一份短期证书，由部署在首次使用时自行生成的证书颁发机构签名。

证书并不是审批额外带来的东西：调用工具的**每个**步骤都有证书。审批改变的是证书来自谁：没有人被要求审批的步骤，获得的证书依据的是发起运行者的权限，而审批会把它替换为审批人自己的权限。因此记录要回答的从来不是“这次调用是否获得授权”，而是“由谁授权”。

| 证书包含 | 为什么重要 |
|---|---|
| 它代表哪个租户、哪次运行和哪个步骤，以及它所代表的是谁的权限：审批人的，还是运行发起人的 | 为一次运行签发的证书在另一次运行中毫无用处，一种权限也不能冒充另一种 |
| **步骤在启动那一刻绑定的工具** | 运行的步骤及其工具在执行时就根据工作流已发布的设计固定下来，证书在签发时再次冻结它们，而被涵盖步骤的工具根本无法再编辑，所以无论是代理还是之后的更改都无法扩大授权。批准一个步骤读取文件，绝不会变成批准它删除文件 |

### 决定涵盖的调用 {#the-calls-a-decision-covers}

证书回答的是*哪个工具*，从不回答*用什么参数调用*，而实际后果往往恰恰取决于输入。因此，请求还带有证书所没有的第二样东西：它所授权的调用，每项都指明一个工具，并限定其输入可以取的值。它在发出请求时记录，在审批人作决定之前显示给他们，此后任何人（包括代理）都不能再编辑。

随后，每次经由代理服务器的调用除了要符合证书之外，还要符合它：

| 检查项 | 在以下情况拒绝 |
|---|---|
| 工具 | 决定中没有列出该工具，即使证书授予了它 |
| 提供的每项输入 | 决定中没有提到它，也就是审批人从未见过的输入 |
| 决定中提到的每项输入 | 它缺失了，除非决定将其标记为可选 |
| 每个值 | 它超出了审批人同意的范围 |

两个已批准分支汇合处的步骤必须**同时**满足两个决定，这与它首先需要两项批准的原因相同：较宽松的审批人不能代表另一位审批人。如果两者对某个工具是否需要输入审批存在分歧，则以较严格的一方为准。

工作流设计中标记为只读的工具也会列出，显示为**任意输入**，而不是被省略。这样决定仍然是对其授权内容的完整说明，审批人可以看到哪些工具未受限定，门禁也只需查阅一份列表，而不用靠第二条规则重新读取步骤的工具。只有请求路径才能写入这样的条目；代理试图自行声明时会被拒绝。

依据运行发起人自身权限运行的步骤不按这种方式检查：没有审批人，也就无所谓偏离。约束它的内容不变：它自己的工具，以及证书中已签名的授权。

### 审批涵盖的步骤 {#the-steps-an-approval-covers}

审批涵盖**它指定的步骤及其之后的每个步骤，直到下一个审批**。因此，工作流可以把请求单独放在一个步骤中，让决定涵盖后续的工作：

![五步任务链的流程图：审批 A 涵盖前三个步骤，审批 B 从第四个步骤起接管，说明审批涵盖其指定的步骤及之后直到下一个审批的所有步骤。](./img/approvals-step-coverage.svg#gh-light-mode-only)
![五步任务链的流程图：审批 A 涵盖前三个步骤，审批 B 从第四个步骤起接管，说明审批涵盖其指定的步骤及之后直到下一个审批的所有步骤。](./img/approvals-step-coverage-dark.svg#gh-dark-mode-only)

审批 A 涵盖*请求批准*、*启动实例*和*为实例加标签*。审批 B 从*再次请求*起接管。位于请求之前的步骤绝不会被它涵盖：审批只向后生效。

| 情况 | 结果 |
|---|---|
| 指定的步骤本身不使用任何工具 | 没有问题，这也是常见做法。决定由其后的步骤承接 |
| 某个步骤位于不同分支上的两个审批之后 | **两者**都必须获得批准，它才能行动。一位审批人放行自己的分支，并不能代表另一位审批人的分支 |
| 在已被先前审批涵盖的步骤上又请求了第二个审批 | 较近的请求立即接管，先前的决定不再为该步骤授权 |
| 步骤被退回修改后重新提交 | 新请求取代旧决定成为该步骤的门禁，因此驳回不会让步骤永远卡住 |

被涵盖步骤此后的每次工具调用都必须出示其证书，网关在放行调用之前会检查以下所有各项：

- 证书代表的是这次运行和这个步骤；
- 证书由本部署签发，且未被吊销；
- 其背后的审批仍然涵盖该步骤，且涵盖该步骤的每个审批仍处于已批准状态；
- 调用方能证明证书属于自己，而不是复制来的；
- 被调用的工具在已签名的集合之内。

步骤一进入终止状态，其证书就会被吊销。安全性并不依赖于此（已结束的步骤不再运行，其调用已经会被拒绝），但这样记录中就能说明授权*为什么*不再有效，也让证书的寿命与其授权的工作保持一致。由于每个被涵盖的步骤都在启动时获得自己的证书，一长串步骤不必在一份证书的有效期内全部完成；最长有效期可以在[配置参考](../operations/configuration.md#mcp-tools-and-approvals)中调整。

## 记录能回答什么 {#what-the-record-answers}

每次已裁决的调用（无论允许还是拒绝）都会连同其出示的证书一起记录，因此即使运行结束很久之后，也能回答“是谁授权的，依据是什么”。参数只保留摘要，原始值绝不存储。可以在运行的工具调用页面上查看这些记录。

因偏离决定而被拒绝的调用会记录原因，指出有问题的输入以及审批人同意的范围，但绝不记录实际传入的值。原因按原文存储，与只保留参数摘要的是同一条记录，所以如果在这里引用被拒绝的值，就会把摘要有意排除的内容又放回去。

**保证的范围。** 网关在后端进程内运行，因此证书只能向共享该进程的验证方证明持有关系，并不能防御已经控制了后端的攻击者。它真正提供的是单一的、失败时保持关闭的强制执行点，事后无法扩大的授权，以及可供事后核查的记录。
