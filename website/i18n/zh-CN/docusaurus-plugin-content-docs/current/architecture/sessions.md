# 会话

会话是多方共享的聊天：代理、打开它的人，以及工作中被牵涉进来的其他人。代理也在这里绘制交互式界面，因此一次交流可以是一张待填写的表单，而不必是一段需要用文字回答的话。

## 谁共享会话 {#who-shares-one}

| 会话 | 共享者 | 其他人 |
|---|---|---|
| **工作流会话** | 运行的发起人，以及其任一[审批](./approvals.md)的指定审批人 | 租户的管理员以只读方式查看；其他人无权访问 |
| **设计会话** | 租户内的每位开发人员，外加超级管理员和工作流的创建者 | 无权访问 |

发给用户组的审批会把持有审批人角色的每位成员都带进来，因此聊天的参与者会随用户组成员变化；这项访问权限的存在，正是为了让他们能够作出决定。由于多人在同一段对话中发言，每条消息都带有**发送者头像**，每位参与者都能实时看到每条回复的写入过程，无需重新加载。

后端在 AG-UI 协议和代理之间架起桥梁：它双向转换事件，保持对话同步，并在事件到达时立即以流的形式发回浏览器，所以文本是逐步出现的，而不是在最后一次性显示。对话状态保存在聊天的 ID 之下，因此重新打开时会从上次中断的地方继续。

工作流会话不需要任何人打开聊天：它的每个轮次都由 A2Flow 自己运行。这包括运行创建后立即进行的**启动**；[审批](../guides/approvals.md)有了决定后让运行**继续**的轮次；任务[需要等待](../guides/workflows.md#how-the-agent-works-through-the-tasks)的时刻到来后让运行继续的轮次；以及回答参与者所发内容的轮次。聊天只是把消息交给 A2Flow，并向所有观看者显示运行中的轮次，无论它在哪台服务器上运行。（设计会话是例外：它的轮次仍然从发送消息的开发人员的聊天中运行。）

## 交互式界面 {#interactive-surfaces}

`render_a2ui` 工具由前端附加（在 A2Flow 自己运行的轮次中，则由后端使用完全相同的定义附加），并携带代理可以用来绘制的 [A2UI](https://a2ui.org) 组件目录的架构。模型调用它时，后端不执行任何操作，只转发调用，由浏览器绘制结果。

| 组件 | 用途 |
|---|---|
| `Text`、`Card`、`Row`、`Column` | 结构和文案 |
| `TextField` | 自由输入 |
| 选择器 | 在允许的值中进行选择。选项达到五个或更多的单选选择器会折叠为下拉列表，因此代理可以列出所有 EC2 实例类型或区域，而不会把对话淹没 |
| `Button` | 提交界面 |

点击按钮时，会把界面的**整个数据模型**发回，也就是所有输入或选择的值，而不只是被按下的那个按钮。这样代理才能根据用户实际输入的内容作出响应，重新加载后的聊天也能用用户自己的值（而不是代理的默认值）重新显示已回答的界面。

### 服务器在调用途中提问 {#a-servers-question-mid-call}

有一种界面完全不是由代理绘制的。MCP 服务器可以在工具调用中途停下来向人询问某件事（即 *elicitation*），等待期间调用保持打开。只有工作流设计中标记为会提问的工具才能这样做，而使用此类工具的任务要等运行的发起人进入聊天后才会启动：会话暂停在**等待发起人**状态，发起人收到通知，任务在其点击**继续**所开启的轮次中启动。随后 A2Flow 记录这个问题，并把它作为独立的活动追加到运行中轮次的流里，让每位观看者立即看到。答案通过专用路径发送，而不是通过聊天输入框，因为会话此时仍处于轮次中途：接收答案的是正在等待的工具调用，而不是新的轮次。用户看到的内容请参阅[来自 MCP 服务器的确认](../guides/workflow-executions.md#mcp-server-confirmations)。

## 聊天中的代理活动 {#agent-activity-in-the-chat}

为了让您看到代理在两次回复之间做些什么，它的中间工作会直接显示在聊天流中：

- **工作指示器**：运行正在进行但屏幕上还没有任何内容时，消息列表底部会出现一个柔和的脉动效果。
- **工具调用行**：每次后端工具调用（例如 `list_workflow_tasks`、`update_workflow_task`）都会变成一行紧凑的状态，从加载图标（`运行中…`）变为对勾（`已完成`）。经由 [MCP 网关](./mcp-gateway-and-proxy.md)路由的调用以**真实的 MCP 工具名称**显示，并带有 `MCP` 标记。`render_a2ui` 和 `render_approval` 客户端工具、写入会话文件的工具，以及提出[建议回复](../guides/workflow-executions.md#suggested-replies)的工具都有各自专用的 UI，不会显示为工具行。
- **调用详细信息**：带有参数或结果的工具行可以**点击展开**，以格式化的 JSON 显示两者，因此无需离开聊天就能查看代理实际发送和收到的内容。由[工具模拟](./mcp-gateway-and-proxy.md#tool-mocks-and-dry-runs)应答的行带有 `已模拟` 徽章，而且聊天是查看这类调用的*唯一*位置，因为被桩替换的调用不会到达代理服务器，也就不会留下审计记录。
- **推理**：支持思考的模型以流的形式输出推理时，这些思考内容会显示在一个柔和的“思考中”面板里。在内部推理但不输出思考摘要的模型不会产生这个面板。

恢复会话时，**MCP 工具调用**、**文件卡片**以及最后一个轮次的**建议回复**会根据历史记录重建；其他 A2Flow 内部工具调用和推理只在实时过程中显示。重建文件卡片，是因为文件比产生它的运行存续得更久，而聊天是显示其下载链接的唯一位置；重建建议回复，是因为它们所回答的问题仍未结束。

## 会话中的文件 {#files-in-a-session}

工作流会话除了消息之外还带有文件：既有参与者从聊天输入框附加的，也有代理在工作时写入的。设计会话没有文件。

文件遵循三条规则：

- **范围。** 一个文件恰好属于一次运行。不指明所在的运行就无法定位文件，因此从一个会话无法访问另一个会话的文件。
- **生命周期。** 文件与运行同存续，并随运行一起删除。没有单独的清理，也没有过期时间。
- **访问。** 文件没有自己的权限：附加需要有驱动运行的资格，下载需要有读取其聊天的资格。这正是聊天本身使用的两条规则。

代理可以读取和添加文件，但绝不能替换或删除；写入已被占用的名称时，会以带编号的变体名称保存。因此，无论运行之后做了什么，参与者附加的文件都会保持附加时的原样。

代理对文件的了解并不来自浏览器。服务器读取会话的文件列表，并把它与工作流提示词一起注入运行的上下文，方式和理由都相同：由客户端提供的列表，就等于由客户端提供的指令。

文件存储在数据库中，因此继承了数据库的持久性和备份，也不需要在副本之间共享卷。下载始终以附件形式、使用通用内容类型提供，因此参与者或代理存储的任何内容都不会被浏览器渲染。
