# MCP 网关与代理服务器

代理从不直接与已注册的 [MCP 服务器](../guides/mcp-servers.md)通信。每次调用都要经过 A2Flow 拥有的两个组件，它们回答两个不同的问题：

| | MCP 网关 | MCP 代理服务器 |
|---|---|---|
| **运行位置** | 在代理的进程内，紧邻数据库 | 在单独的容器中，不持有代理的任何密钥 |
| **决定什么** | 调用*是否*可以发生 | 调用在*哪里*发生：它启动或连接服务器 |
| **持有什么** | 身份、策略链、工具模拟、密钥展开、审计记录 | 一次只持有一个调用的内容：服务器的地址或命令、展开后的值、工具及其参数 |

网关是决策者，本页其余部分主要讨论它。代理服务器是接收这些决策的沙箱，它有自己的章节，见[下文](#the-sandbox)。

## 网关决定什么 {#what-the-gateway-decides}

![流程图，显示策略链如何裁决工具调用：被拒绝的调用会被驳回，并告知允许的内容；被允许的调用由模拟应答，或经过凭据注入和 MCP 代理服务器到达 MCP 服务器；拒绝和真实调用都会产生审计记录。](./img/mcp-gateway-and-proxy-policy-chain.svg#gh-light-mode-only)
![流程图，显示策略链如何裁决工具调用：被拒绝的调用会被驳回，并告知允许的内容；被允许的调用由模拟应答，或经过凭据注入和 MCP 代理服务器到达 MCP 服务器；拒绝和真实调用都会产生审计记录。](./img/mcp-gateway-and-proxy-policy-chain-dark.svg#gh-dark-mode-only)

| 网关负责 | 做什么 |
|---|---|
| **身份** | 根据调用到达时所在的对话，确定调用属于哪个租户和哪次运行 |
| **授权** | 查询一条有序的策略链，其中任何一项都可以否决 |
| **打桩** | 当运行有针对此工具的[工具模拟](#tool-mocks-and-dry-runs)时，由模拟应答 |
| **凭据** | 仅在连接时，把已注册服务器的[密钥](./secrets.md)引用展开到连接中 |
| **隔离** | 把获准的调用交给实际运行服务器的 [MCP 代理服务器](#the-sandbox) |

## MCP 代理服务器：已注册服务器的运行之处 {#the-sandbox}

您注册的 MCP 服务器并不是 A2Flow 的代码。本地服务器是 A2Flow 代您启动的程序；远程服务器是 A2Flow 向外连接的服务。无论哪种，它一旦运行起来，所做的事情就不在 A2Flow 的控制之内。

因此，它不会运行在存放 A2Flow 自身密钥的地方。代理服务器就是一个沙箱：在 Docker Compose 部署中，它是**单独的 `mcp-proxy` 容器**，其中不含以下任何内容：

| 不在代理服务器中的内容 | 所在位置 |
|---|---|
| 数据库及其中记录的所有内容 | 与代理在一起 |
| 用于加密[密钥](./secrets.md)的加密密钥 | 与代理在一起 |
| 外部密钥存储的凭据 | 与代理在一起 |
| LLM 提供商的 API 密钥 | 与代理在一起 |
| [代理技能](../guides/agent-skills.md)仓库 | 与代理在一起 |

代理服务器一次只拿到一个调用的内容：要访问的那一台服务器的地址或命令、该服务器需要的值（已从您的密钥引用展开），以及工具和参数。除此之外，那里什么也找不到。

![架构图，显示 MCP 网关决定调用是否被允许、是否被模拟以及需要哪些凭据，然后把恰好一个已授权的调用跨越信任边界交给 MCP 代理服务器，由后者启动或连接真实的 MCP 服务器。](./img/mcp-gateway-and-proxy-trust-boundary.svg#gh-light-mode-only)
![架构图，显示 MCP 网关决定调用是否被允许、是否被模拟以及需要哪些凭据，然后把恰好一个已授权的调用跨越信任边界交给 MCP 代理服务器，由后者启动或连接真实的 MCP 服务器。](./img/mcp-gateway-and-proxy-trust-boundary-dark.svg#gh-dark-mode-only)

**两端互相证明身份。** 它们之间的通道是加密的，任何一端都不接受身份不明的对端：代理服务器会拒绝未持有本部署签发证书的任何连接。此外，每个调用还带有发起它的任务的[证书](#who-authorized-a-call)，代理服务器在接触任何内容之前会再次检查该证书：它由这里签发、尚未过期、属于调用方，并且涵盖这个确切的工具。

**调用途中可以提问。** MCP 服务器可以在调用中途停下来，向运行背后的人请求[确认](../guides/workflow-executions.md#mcp-server-confirmations)。只有网关知道那个人是谁，因此代理服务器通过调用自身的连接把问题交回，答案再沿同一连接传回正在等待的服务器。调用的任何内容都不会比它的连接存续得更久，所以代理服务器可以运行任意数量的容器。

第二项检查与第一项回答的不是同一个问题。身为 A2Flow 并不意味着有权调用某个工具，持有任务的证书也不意味着这个请求就是 A2Flow 发出的。两者必须同时成立，这样请求就无法在保留有效授权的同时，悄悄让代理服务器指向另一个程序。

有一种调用不带任务证书：从 MCP 服务器表单发起的脚本[测试运行](../guides/mcp-servers.md#testing-a-script)，它背后没有任务。代理服务器只对脚本接受这种调用，绝不接受任意命令或远程服务器；而加载脚本的工具列表时，本来就要在同样的“仅限 A2Flow”检查下运行整个脚本，所以这并没有放行任何新内容。

代理服务器是第二道防线，而不是决策者。任务是否仍在运行、审批是否依然有效、证书是否已被撤回，这些问题在那里都无法回答，全都由网关负责。

## 每次启动都有独立的沙箱 {#per-launch-sandbox}

代理服务器不仅让已注册的服务器远离 A2Flow，还让它们**彼此**隔离。所有租户的服务器都在同一个代理服务器中启动，其中一些还是租户自己编写的脚本，因此代理服务器启动的每个服务器都被封闭在专属的沙箱中，沙箱为这一次调用而创建，并在调用结束时销毁。

| 沙箱内的情况 | 由此排除的风险 |
|---|---|
| 服务器只能看到自己的进程 | 读取同时运行的其他服务器获得的密钥值 |
| 系统和 A2Flow 自身的程序都是只读的 | 篡改之后的服务器（例如另一个租户的服务器）下次启动时运行的内容 |
| 其主目录（保存已下载软件包的地方）只属于它所在的租户 | 服务器取用另一个租户植入的软件包 |
| 沙箱内的一切都随调用结束而结束 | 进程在调用结束后继续逗留，监视之后的调用 |
| 代理服务器自身的凭据根本不在其中 | 向任何对象冒充代理服务器 |

远程服务器只由代理服务器向外连接，不在代理服务器中运行任何内容，因此不需要沙箱。

这种隔离基于 [bubblewrap](https://github.com/containers/bubblewrap) 构建，它是 Flatpak 背后的 Linux 沙箱工具。代理服务器在启动时会检查自己能否创建沙箱，如果不能，就拒绝启动；它绝不会退回到不使用沙箱运行服务器的方式。这对主机有何要求，请参阅[部署](../operations/deployment.md#process-layout)。

## 策略链 {#the-policy-chain}

| 顺序 | 策略 | 要求 |
|---|---|---|
| 1 | **进行中任务的工具绑定** | `(服务器, 工具)` 对必须绑定到一个状态为 `进行中` 且分配给发起调用的会话的任务；该运行的其他会话正在处理的任务不算。列出服务器提供的工具不属于调用，因此此规则不适用：设计代理通过列出工具来决定绑定什么，范围缩小到设计者在[访问控制标签](../guides/tags.md)下可以看到的服务器，而运行自身的列出操作不受标签限制 |
| 2 | **工具证书** | 调用必须出示任务的证书（请参阅[谁授权了调用](#who-authorized-a-call)），且该证书已签名的授权必须涵盖此工具。没有例外：没有审批涵盖的任务出示的是其运行发起人持有的授权 |
| 3 | **已批准的调用** | 当任务的授权来自审批人的决定时，调用必须与该决定所列的调用相符，请参阅[决定涵盖的调用](./approvals.md#the-calls-a-decision-covers)。决定中列为接受任意输入的工具，无论带什么输入都能通过此规则，因为在决定获得批准之前，它已经被规则 2 拦下。依据发起人自身授权运行的任务没有这样的列表，不在此处检查 |

策略链在遇到第一个否决时停止，并按开销从低到高排列，因此已经不符合绑定规则的调用无需为签名检查付出代价。最后一条规则排在最后还有第二个原因：只有它需要知道*哪个*任务在发起调用，而这正是由前一条规则确定的。这样也能防止完全没有权限的调用方得知审批人同意了什么。添加规则意味着向链中添加一项策略，而不是修改网关，这样“什么可以运行”才能作为一张有序列表清晰可读。

拒绝信息是写给调用方而不是写给日志看的：被拒绝的调用返回时会指出*允许*哪些工具，让模型可以自行纠正，而不用去猜。

## 谁授权了调用 {#who-authorized-a-call}

运行发起的每次工具调用都带有一份**证书**，写明其所依据的权限属于哪个人。任务被标记为**进行中**时就会获得证书；证书代表谁的权限，取决于是否有[审批](./approvals.md)涵盖该任务。

| 任务 | 获得证书的时机 | 依据谁的权限 |
|---|---|---|
| 被审批涵盖（它自己的审批，或在它之前的任务上请求的审批） | 启动时，且仅在该审批获得批准之后 | 批准它的审批人 |
| 没有被任何审批涵盖 | 被标记为**进行中**时 | 发起运行的人 |

第二行是通常的情况：没有人被要求评估这个任务，所以运行工作流的人为任务绑定的工具授权，审计跟踪也会如实记录这一点，而不是让调用没有归属。

由此得出三条规则，操作工作流的人都能看到它们的效果：

- **工具在任务启动时固定。** 证书恰好涵盖此刻绑定到任务的工具。工作流如果在任务启动之后才绑定工具，该工具就会被拒绝。设计代理被要求先绑定，但手动编辑的任务仍可能出错。审批涵盖的任务，其工具根本无法编辑。
- **请求审批会重新关上大门。** 如果请求的审批涵盖一个已在依据某人权限运行的任务，该权限会立即失效；任务和其他任务一样等待决定。
- **每个被涵盖的任务都有自己的证书。** 一个审批涵盖一连串任务，并不会让它们共用一个时限；每个任务都在启动时获得自己的证书。

## 记录什么 {#what-is-recorded}

| 每次已裁决的调用记录 | 有意不记录 |
|---|---|
| 工具、服务器，以及调用是被允许还是被拒绝 | 参数本身，只保留其摘要 |
| 被拒绝时的拒绝原因；对于超出批准范围的调用，记录有问题的输入以及审批人同意的范围 | 被拒绝输入的实际值 |
| 出示的证书，因而也记录了谁授权了调用 | |

这份记录就是运行的工具调用页面，正是它让“谁授权了这次调用”能够在事后得到回答。证书本身列在**审计日志 → 证书**下，每项授权一行。

## 工具模拟与试运行 {#tool-mocks-and-dry-runs}

[工具模拟](../guides/tool-mocks.md)让**草稿**工作流能够得到端到端的演练，而不产生其工具的副作用。这里的关键在于桩所在的*位置*。

![流程图，显示工具模拟只在经过与生产调用相同的策略链之后才被查询：被拒绝的调用与生产环境一样被拒绝，被允许的调用由模拟的下一个响应或真实的 MCP 服务器应答。](./img/mcp-gateway-and-proxy-tool-mocks.svg#gh-light-mode-only)
![流程图，显示工具模拟只在经过与生产调用相同的策略链之后才被查询：被拒绝的调用与生产环境一样被拒绝，被允许的调用由模拟的下一个响应或真实的 MCP 服务器应答。](./img/mcp-gateway-and-proxy-tool-mocks-dark.svg#gh-dark-mode-only)

桩在策略链**之后**才被查询，绝不会在它之前。因此，试运行演练的是与真实运行相同的授权：工具仍必须绑定到进行中的任务，调用仍必须出示该任务的证书。模拟唯一跳过的，是会在 A2Flow 外部产生影响的部分：调用绝不会到达代理服务器。

有两点值得了解：

- **响应按调用次数返回。** 第一个响应对应运行对该工具的第一次调用，第二个对应第二次，列表用完后重复最后一个响应。计数器属于运行，因此在一次代理运行所跨越的众多请求（以及可能涉及的多个副本）之间都能保持。
- **被桩替换的调用不会留下审计记录。** 这种记录是为到达了真实服务器、或在前往途中被拦下的调用准备的；如果为一个注定由快照应答的调用写一行记录，无论怎么解读都会产生误导。要查看被桩替换的调用，请看聊天记录，其上带有 `已模拟` 徽章。
