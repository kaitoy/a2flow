# 워크플로

워크플로는 재사용할 수 있는 작업 단위로, [에이전트 스킬](./agent-skills.md)과 **미리 디자인된 작업 목록**인 *작업 템플릿*을 묶은 것입니다. 템플릿은 실행하기 *전에* 확정되므로, 워크플로를 실행하면 매번 같은 단계를 다시 디자인하지 않고 바로 작업이 시작됩니다.

관리 사이드바에서 **워크플로**를 열어 관리합니다.

![에이전트 스킬에서 워크플로를 생성하고, 조정된 초안으로 다듬어 게시한 다음, 워크플로 실행으로 실행하는 과정을 보여 주는 순서도.](./img/workflows-lifecycle.svg#gh-light-mode-only)
![에이전트 스킬에서 워크플로를 생성하고, 조정된 초안으로 다듬어 게시한 다음, 워크플로 실행으로 실행하는 과정을 보여 주는 순서도.](./img/workflows-lifecycle-dark.svg#gh-dark-mode-only)

빈 워크플로를 만드는 방법은 없습니다. 워크플로는 스킬에서 생성해야만 만들어집니다.

## 상태 {#statuses}

![워크플로의 상세 상태를 보여 주는 상태 전이도. 생성 중에서 초안 또는 실패로 넘어가고, 실패는 다시 작성하면 초안으로 돌아가며, 초안을 게시하면 게시됨이 된다. 게시됨과 수정됨은 추가 편집과 게시로 서로 오가고, 둘 다 비활성화하면 초안으로 돌아간다.](./img/workflows-status.svg#gh-light-mode-only)
![워크플로의 상세 상태를 보여 주는 상태 전이도. 생성 중에서 초안 또는 실패로 넘어가고, 실패는 다시 작성하면 초안으로 돌아가며, 초안을 게시하면 게시됨이 된다. 게시됨과 수정됨은 추가 편집과 게시로 서로 오가고, 둘 다 비활성화하면 초안으로 돌아간다.](./img/workflows-status-dark.svg#gh-dark-mode-only)

| 상태 | 의미 | 실행할 수 있는 사람 |
|---|---|---|
| `생성 중` | 백그라운드 디자인 실행이 아직 작업 템플릿을 작성하고 있습니다. | 없음 |
| `초안` | 디자인은 있지만 게시된 적이 없거나 비활성화되었습니다. | 개발자와 슈퍼 관리자(게시 전 테스트용) |
| `실패` | 디자인 실행이 템플릿을 만들지 못하고 끝났습니다. 사유는 상세 페이지와 디자인 채팅에 표시됩니다. | 없음 |
| `게시됨` | 디자인이 고정되어 실행할 수 있습니다. | 요청자 이상의 역할을 가진 모든 사람 |
| `수정됨` | 한 번 게시된 후 편집되었습니다. 실행에는 계속 게시된 버전이 사용됩니다. | `게시됨`과 같음 |

`수정됨`은 **개발자**, **검토자**, **슈퍼 관리자**에게만 표시되는 상태입니다. 다른 모든 사람에게 이 워크플로는 `게시됨`으로 보이며, 마지막으로 게시할 때 기록된 이름, 설명, 작업 템플릿이 표시됩니다. 게시되지 않은 편집은 이들이 볼 내용이 아니며, 이들이 *볼 수 있는* 디자인이 바로 이들의 실행에서 실행될 디자인입니다.

## 화면 {#the-screens}

| 화면 | 이동 방법 | 할 수 있는 일 |
|---|---|---|
| **워크플로** 목록 | 관리 사이드바 → 워크플로 | 둘러보기, [태그](./tags.md)로 필터링, 워크플로 **실행** |
| 워크플로 상세 | 워크플로 이름 클릭 | 필드 편집, **변경 사항 취소**, **디자인 세션 열기**(개발자), **게시**, **비활성화**(검토자) |
| **작업 템플릿** | 워크플로 상세 페이지의 작업 템플릿 링크 | 표 또는 그래프로 단계를 직접 추가, 편집, 재정렬 |
| 디자인 세션 | 상세 페이지의 **디자인 세션 열기** | 디자인 에이전트와 대화하며 단계 다듬기 |

각 워크플로 레코드에는 **이름**, 분류에 쓰는 [태그](./tags.md), 따르는 **에이전트 스킬**, 상태, **설명**, 그리고 프롬프트 필드 두 개가 있습니다.

## 워크플로 생성 {#generating-a-workflow}

**워크플로 생성**은 두 곳에서 열 수 있으며, 어느 쪽이든 페이지를 떠나지 않고 같은 대화 상자가 열립니다. [에이전트 스킬](./agent-skills.md) 목록의 행 동작과 스킬 상세 페이지 헤더의 워크플로 생성 아이콘 버튼입니다. 둘 다 스킬에 게시된 리비전이 생길 때까지 비활성화되어 있습니다.

1. **워크플로 이름**(스킬 이름이 미리 채워져 있습니다)과 작업 내용을 설명하는 **프롬프트**를 입력합니다. 원한다면 **지식 베이스**에서 [지식 베이스](./knowledge-bases.md)를 선택할 수 있습니다. 선택한 지식 베이스는 새 워크플로에 바로 연결되므로 디자인 에이전트가 처음부터 찾아볼 수 있습니다. 생성하면 페이지를 이동하므로, 상세 페이지에서는 저장하지 않은 편집을 먼저 저장할지 묻습니다. 거절하면 페이지는 그대로이고 생성도 되지 않습니다.
2. 워크플로는 바로 `생성 중`으로 등록되고 워크플로 상세 페이지로 이동합니다. 이 페이지는 처리가 진행되는 동안 자동으로 새로 고쳐집니다.
3. 백그라운드에서 프롬프트가 워크플로의 **디자인 세션**에 첫 메시지로 전송됩니다. 디자인 에이전트는 스킬을 따라 요청을 단계로 나누고 워크플로의 작업 템플릿으로 등록합니다. 템플릿은 종속성 그래프를 이루며, 각 단계에는 먼저 끝나야 하는 단계와 필요한 [MCP 도구](./workflows.md#mcp-tools-for-tasks)가 선언됩니다.
4. 실행이 끝나면 디자인 대화가 **생성된 프롬프트**로 요약되고, 워크플로를 실행할 사람을 위한 짧은 **설명**이 함께 작성되며, 상태가 `초안`이 되고, [알림](./notifications.md)에 있는 링크로 워크플로에 바로 돌아갈 수 있습니다.

실행이 실패하거나 템플릿을 하나도 등록하지 못하고 끝나면 워크플로는 사유와 함께 `실패`가 되며, 알림으로 이를 알려 줍니다. 디자인 채팅은 계속 사용할 수 있습니다. 그곳이나 작업 템플릿 관리 페이지에서 작업 템플릿을 작성하면 워크플로가 `초안`으로 복구되고 실패 기록이 지워집니다.

워크플로 생성 대화 상자에 입력한 요청은 워크플로에 저장되지 않습니다. 이 요청은 디자인 대화의 첫 메시지로 남고, 생성된 요약이 그 의도를 이어 갑니다.

## 설명과 프롬프트 {#description-and-prompt}

워크플로에는 두 종류의 텍스트가 있으며, 그중 하나만 실행에 영향을 줍니다.

| 필드 | 내용 | 작성자 | 편집할 수 있는 사람 | 볼 수 있는 사람 |
|---|---|---|---|---|
| **설명** | 워크플로의 용도를 설명하는 일반 텍스트입니다. 실행에서는 전혀 읽지 않습니다. | 워크플로 생성 시 AI, 이후 사람 | 모든 개발자 | 워크플로를 열 수 있는 모든 사람 |
| **프롬프트** | 생성된 프롬프트를 재정의합니다 | 사람. 대개 AI의 요약을 직접 고쳐 씁니다 | 모든 개발자 | 관리자, 개발자, 검토자 |
| **생성된 프롬프트** | AI가 디자인 대화를 요약한 내용입니다 | AI | 슈퍼 관리자만 | 관리자, 개발자, 검토자 |

유효 프롬프트는 실행할 때마다 실행 에이전트에 컨텍스트로 전달됩니다. **프롬프트**가 비어 있지 않으면 이것이 우선하고, 비어 있으면 **생성된 프롬프트**가 사용됩니다. 재정의는 대개 요약의 사본에서 시작하므로, 프롬프트 필드에는 **생성된 프롬프트와의 차이 표시** 동작이 있어 둘 사이의 단어 단위 차이를 보여 줍니다. 양식의 현재 값을 읽으므로 저장하지 않은 편집도 차이에 반영됩니다.

설명은 워크플로 목록에 표시되고 **워크플로 실행** 대화 상자의 확인 문구 아래에도 표시되므로, 실행을 시작하는 사람이 올바른 워크플로를 골랐는지 확인할 수 있습니다. 프롬프트 필드는 상세 페이지, 목록의 선택 열인 **프롬프트**, 실행 상세 페이지 어디서든 다른 역할에는 표시되지 않습니다.

### 프롬프트 다시 생성 {#regenerating-the-prompt}

작업 템플릿을 조정하다 보면 AI 요약은 오래된 내용이 되므로, **생성된 프롬프트**에는 **디자인 대화에서 생성** 동작이 있습니다. 필요할 때 디자인 대화를 다시 요약하고 결과를 바로 저장합니다. 게시할 때는 아무것도 요약되지 않습니다. 새로 고칠지, 언제 새로 고칠지는 사용자가 결정합니다.

같은 동작은 디자인 세션의 채팅 입력란에 있는 "+" 메뉴에서도 제공됩니다. 여기서는 저장하기 전에 같은 차이 대화 상자로 변경 내용을 미리 볼 수 있어, 대화를 떠나지 않고 다시 생성할 때 편리합니다. 작업 템플릿을 아직 생성하는 동안에는 이 메뉴가 숨겨집니다.

둘 다 개발자 동작입니다. `게시됨` 워크플로의 요약을 다시 쓰면 `수정됨`으로 바뀝니다. 프롬프트가 비어 있는 실행은 요약을 대신 사용하므로, 그대로 두면 게시된 버전과 어긋나기 때문입니다.

## 작업 템플릿 조정 {#adjusting-the-task-templates}

초안의 작업 템플릿은 두 가지 방법으로 다듬을 수 있으며, 어떻게 섞어 써도 됩니다.

**채팅으로.** 워크플로 상세 페이지의 **디자인 세션 열기**를 누르면 디자인 채팅이 열립니다. 실행과 같은 채팅 화면으로, 왼쪽 가장자리에 템플릿 목록이 표시되고, 템플릿을 직접 편집하는 디자인 에이전트가 진행합니다. 디자인 에이전트는 아무것도 실행하지 않습니다. 이 세션은 테넌트의 모든 **개발자**와 슈퍼 관리자, 워크플로를 만든 사람이 공유하므로 팀이 함께 디자인을 다듬을 수 있습니다. 메시지별 보낸 사람 아바타를 포함해 공유 채팅의 동작은 [워크플로 세션](./workflow-executions.md#the-workflow-session-screen)과 같습니다. **검토자**도 게시 여부를 결정하기 전에 같은 채팅을 열어 기록을 읽을 수 있지만 메시지 입력란은 숨겨집니다. 디자인을 검토하는 일에 디자인을 조종하는 일은 포함되지 않기 때문입니다.

**직접 편집으로.** **작업 템플릿** 페이지에는 **표** 보기와 **그래프** 보기, 만들기 양식, 그리고 **종속 대상**과 **MCP 도구** 선택기가 있는 템플릿별 상세 페이지가 있습니다. 그래프는 템플릿을 종속 순서에 따라 세로 한 열로 쌓으며, 각 템플릿은 오른쪽으로 도구를 연결한 MCP 서버, 이어서 개별 도구로 갈라집니다.

템플릿은 제목, 설명, 종속 관계, 도구 연결 등 구조 면에서 실행의 작업과 같지만 **상태는 없습니다**. 수명 주기는 디자인이 아니라 실행의 것이기 때문입니다. 종속 대상은 같은 워크플로의 템플릿이어야 하며, 순환을 만드는 종속 관계는 거부됩니다.

## 게시 {#publishing}

워크플로 상세 페이지의 **게시**는 워크플로를 실행할 수 있게 만듭니다. 이는 **검토자**의 동작입니다. 개발자는 워크플로를 만들고 편집하지만 게시는 하지 않으므로, 디자인을 승격하는 사람과 작성한 사람이 다릅니다. 게시하려면 템플릿이 하나 이상 있어야 하고 진행 중인 생성이 없어야 합니다.

게시하면 **디자인이 고정됩니다**. 워크플로의 이름, 설명, 유효 프롬프트, 종속 관계와 도구 연결을 포함한 전체 템플릿 목록이 새로운 게시 버전(**v1**, **v2** 등)으로 저장됩니다. 이전 버전은 [버전 기록](#version-history)에 보관됩니다. 여기서 AI는 실행되지 않으며, 요약을 새로 고치는 것은 [별도의 동작](./workflows.md#regenerating-the-prompt)입니다. 원하는 만큼 다시 조정하고 다시 게시할 수 있습니다. 각 실행은 작업의 사본을 자체적으로 가지므로 이미 시작된 실행은 영향을 받지 않습니다.

## 게시된 워크플로 편집 {#editing-a-published-workflow}

게시한 후에 워크플로를 편집해도 실행되는 내용이 모르는 사이에 바뀌지는 않습니다. 상세 양식을 저장하거나, AI 프롬프트를 다시 생성하거나, 작업 템플릿을 추가, 편집, 삭제하면(디자인 에이전트가 채팅에서 변경한 경우 포함) 워크플로는 `수정됨`으로 바뀝니다.

| `수정됨` 상태일 때 | |
|---|---|
| 실행에 사용되는 것 | **마지막으로 게시된 버전**의 이름, 유효 프롬프트, 템플릿. 개발자가 편집 내용을 선택하지 않는 한 편집 내용은 사용되지 않습니다([편집 내용 시험](#trying-the-edits-out) 참조) |
| 실행할 수 있는 사람 | `게시됨`일 때와 같은 사람입니다. 실행 버튼의 조건은 달라지지 않습니다 |
| 편집 내용을 볼 수 있는 사람 | 개발자, 검토자, 슈퍼 관리자만 볼 수 있습니다 |
| **게시**(검토자) | 편집 내용을 이후 실행과 다른 모든 사람이 보는 내용에 반영합니다 |
| **변경 사항 취소**(개발자) | 편집 내용을 버립니다. 템플릿은 게시된 버전으로 다시 작성되고, 이름과 설명은 복원되며, 게시된 버전의 프롬프트가 다시 기록되고, 워크플로는 `게시됨`으로 돌아갑니다 |

**변경 사항 취소**는 상세 페이지의 상태 표시줄에서 게시 옆에 있는 실행 취소 아이콘입니다. 게시되지 않은 변경 사항이 없는 워크플로에서 취소하면 그렇다고 알려 줄 뿐 아무 일도 일어나지 않습니다.

개발자나 검토자 역할이 없는 사람에게는 어디서든 게시된 버전이 제공됩니다. 목록과 상세 페이지의 워크플로 이름과 설명, **작업 템플릿** 화면, 심지어 목록의 이름 검색에 걸리는 대상까지 그렇습니다. 상태는 `게시됨`으로 표시되고, 마지막 게시 이후에 추가된 작업 템플릿은 이들에게는 아예 존재하지 않습니다. 따라서 작업 중인 재디자인이 워크플로를 실행하기만 하면 되는 사람을 혼란스럽게 하는 일이 없으며, 이들이 보는 내용은 항상 이들의 실행에서 일어날 일과 일치합니다.

## 버전 기록과 롤백 {#version-history}

게시한 내용은 모두 보관됩니다. 워크플로 상세 페이지 헤더의 시계 아이콘인 **버전 기록**에는 최신순으로 버전 번호, 이름, 설명, 게시 시각과 게시한 사람이 표시됩니다. **관리자**, **개발자**, **검토자**, **슈퍼 관리자**만 볼 수 있으며, 요청자나 승인자에게는 시계 아이콘 자체가 표시되지 않습니다.

이전 디자인으로 롤백하려면(개발자) 다음과 같이 합니다.

1. **버전 기록**을 열고 원하는 버전의 **복원**을 클릭합니다.
2. 확인합니다. 해당 버전의 템플릿, 이름, 설명, 프롬프트가 워크플로의 현재 디자인을 대체하고 워크플로로 돌아갑니다.
3. 결과를 확인합니다. 복원해도 게시되지는 **않습니다**. 검토자가 **게시**를 클릭할 때까지 실행에는 현재 게시된 버전이 계속 사용되며, 게시하면 복원된 디자인이 새 버전으로 기록됩니다.

| 복원 전 상태 | 복원 후 상태 |
|---|---|
| `게시됨` 또는 `수정됨` | `수정됨`. 최신 버전을 복원한 경우에는 게시되지 않은 내용이 남지 않으므로 `게시됨` |
| `초안` | `초안` |

게시하기 전에 마음이 바뀌었다면 **변경 사항 취소**로 현재 게시된 버전을 되돌릴 수 있습니다. 이후 삭제된 MCP 서버의 도구를 연결한 버전은 복원할 수 없으며, 복원이 오류와 함께 거부됩니다.

### 내부 메모 {#internal-notes}

워크플로 상세 페이지의 **내부 메모**에는 롤백한 이유나 워크플로를 운영하는 팀이 알아야 할 내용을 기록할 수 있습니다.

| | |
|---|---|
| 볼 수 있는 사람 | 관리자, 개발자, 검토자입니다. 다른 모든 사람에게는 숨겨집니다. |
| 편집할 수 있는 사람 | 같은 세 역할입니다. 필드에 입력하고 저장 아이콘을 클릭합니다. |
| 워크플로에 미치는 영향 | 없습니다. 저장해도 상태가 바뀌지 않으며 실행에서 메모를 읽지도 않습니다. |
| 버전 | 버전이 관리되지 않습니다. 게시, 버전 복원, **변경 사항 취소**를 해도 메모는 그대로 남습니다. |

## 워크플로 비활성화 {#deactivating-a-workflow}

**비활성화**는 워크플로가 `게시됨` 또는 `수정됨`일 때 게시 옆에 나타나는 전원 끄기 아이콘으로, 게시와 마찬가지로 **검토자** 역할이 사용할 수 있으며 워크플로를 `초안`으로 되돌립니다. 그러면 요청자 역할의 실행 권한이 회수되어 한 번도 게시되지 않은 워크플로와 같은 조건이 되지만, 개발자나 슈퍼 관리자는 테스트를 위해 계속 실행할 수 있습니다. 작업 템플릿, 두 설명 필드, 게시된 스냅샷은 그대로 남으므로 다시 게시하면 바로 원래대로 돌아갑니다.

## 워크플로 실행 {#running-a-workflow}

워크플로 목록에서 **실행**을 클릭하면 **워크플로 실행**이 만들어집니다. 워크플로 실행은 그 시점의 워크플로 스냅샷을 담은 독립적인 레코드입니다.

![게시된 워크플로와 선택한 도구 모의가 새 워크플로 실행 스냅샷에 값으로 복사되고, 스냅샷이 워크플로 세션을 여는 것을 보여 주는 순서도.](./img/workflows-snapshot.svg#gh-light-mode-only)
![게시된 워크플로와 선택한 도구 모의가 새 워크플로 실행 스냅샷에 값으로 복사되고, 스냅샷이 워크플로 세션을 여는 것을 보여 주는 순서도.](./img/workflows-snapshot-dark.svg#gh-dark-mode-only)

**테스트 실행**의 경우 실행 대화 상자의 **모의 도구**에 워크플로의 작업 중 하나가 사용하는 도구의 [도구 모의](./tool-mocks.md)와 내장 도구의 모든 모의가 추가로 표시됩니다. 하나를 선택하면 이번 실행에서 해당 도구가 스텁 처리되므로, 도구의 부작용 없이 게시 전 테스트를 반복할 수 있습니다. 테스트 실행이란 `초안` 워크플로 또는 `수정됨` 워크플로의 게시되지 않은 편집(아래 참조)을 실행하는 것을 말합니다. 그 외에는 대화 상자에 모의가 표시되지 않으며 그래도 요청하면 거부됩니다. 실제처럼 보이지만 조용히 아무것도 하지 않는 실행은 실행하지 않느니만 못하기 때문입니다.

### 편집 내용 시험 {#trying-the-edits-out}

워크플로가 `수정됨`인 동안에는 디자인이 두 개이므로, 실행 대화 상자는 **개발자**에게 어느 쪽을 실행할지 묻습니다.

| 선택 | 실행되는 내용 | 기록 방식 |
|---|---|---|
| **게시된 버전** | 마지막 게시 때 저장된 디자인. 다른 모든 사람이 사용하는 디자인입니다 | 실제 요청 |
| **게시되지 않은 편집** | 지금 편집기에 있는 그대로의 디자인 | **테스트 실행**: 도구를 스텁 처리할 수 있으며 [운영 메트릭](../operations/metrics.md)에서 제외됩니다 |

게시된 버전이 미리 선택되어 있습니다. 여기서 실제 요청이란 그것을 뜻하기 때문입니다. 편집 내용을 선택하면 확정하기 전에 재디자인을 처음부터 끝까지 시연해 볼 수 있습니다. 다른 사람은 그 편집 내용을 애초에 볼 수 없으므로 이는 개발자의 동작입니다. `초안`이나 `게시됨` 워크플로에는 실행할 디자인이 하나뿐이므로 이 선택지가 나타나지 않습니다.

실행에 필요한 모든 것은 시작할 때 실행으로 복사되므로, 이후의 편집이 실행에 영향을 주지 않습니다.

| 실행에 복사되는 것 | 가져오는 곳 |
|---|---|
| 이름과 유효 프롬프트 | 마지막으로 게시된 버전 — 또는 `초안` 워크플로이거나 개발자가 게시되지 않은 편집을 선택한 경우 편집기의 현재 상태 |
| 종속 관계와 도구 연결을 포함한 `대기 중` 작업으로서의 작업 템플릿 | 같은 디자인 |
| 실행에 고정되는 에이전트 스킬 리비전 | 스킬의 게시된 리비전 |
| 선택한 도구 모의(값으로) | 그 시점의 모의 내용 |

그런 다음 실행이 진행되는 채팅인 **워크플로 세션**으로 이동합니다. 세션은 정해진 시작 메시지로 열리며 에이전트는 바로 작업을 시작합니다. 게시할 때 작업이 승인되었으므로 먼저 확인할 것이 없기 때문입니다. 그 후 실행은 렌더링된 대화형 화면과 그 안의 버튼을 포함해 일반 채팅처럼 동작합니다. 이 화면은 [워크플로 실행](./workflow-executions.md) 가이드에서 다룹니다.

### 에이전트의 작업 처리 방식 {#how-the-agent-works-through-the-tasks}

실행 에이전트는 실행의 작업을 나열하고, 다음에 실행할 수 있는 작업, 즉 종속 대상이 모두 완료된 `대기 중` 작업을 골라 `진행 중`으로 표시한 뒤, 스킬의 지시에 따라 작업을 수행하고 `완료됨`, `실패`, `건너뜀` 중 하나로 표시합니다. 모든 작업이 최종 상태에 이르면 [알림](./notifications.md)으로 실행 완료를 알려 줍니다.

상태가 바뀌는 모습은 실행의 읽기 전용 **워크플로 작업** 보기에서 표 또는 그래프로 실시간으로 볼 수 있습니다. 실행의 작업 목록은 워크플로를 게시할 때 고정된 것이므로, 에이전트는 각 작업의 상태만 바꿀 뿐 작업을 추가하거나 제거하지 않습니다.

**시간을 기다려야 하는 작업.** 요구 사항을 작업 설명에 "내일 9:00 이후에 실행", "매월 1일 전에는 실행하지 않음"처럼 평범한 말로 적으세요. 에이전트는 시간이 되기 전에 해당 작업에 이르면 작업을 `대기 중`으로 두고, 실행이 언제 계속되는지 채팅으로 알린 뒤 멈춥니다. 그때까지 세션에는 **예약됨**이 표시되고, 그 시간이 되면 A2Flow가 자동으로 재개합니다. 채팅을 열어 둘 필요는 없습니다. 시간대 없이 적은 시간은 배포 환경의 현지 시간대로 해석됩니다. 다른 세션에서 처리하는 분기는 한 세션이 기다리는 동안에도 계속 진행되며, 기다리는 세션에 메시지를 보내면 바로 재개됩니다.

## 작업용 MCP 도구 {#mcp-tools-for-tasks}

작업은 [MCP 서버](./mcp-servers.md)에 등록된 서버의 도구를 사용할 수 있습니다. 도구는 디자인 시점에 연결되고 실행 시점에 적용됩니다.

![디자인 시점의 도구 연결이 실행할 때 작업으로 복사되고 호출 시점에 검사되는 과정을 보여 주는 순서도. 도구가 진행 중인 작업에 연결되어 있으면 호출이 통과하고, 그렇지 않으면 허용된 도구 목록과 함께 거부된다.](./img/workflows-tool-binding.svg#gh-light-mode-only)
![디자인 시점의 도구 연결이 실행할 때 작업으로 복사되고 호출 시점에 검사되는 과정을 보여 주는 순서도. 도구가 진행 중인 작업에 연결되어 있으면 호출이 통과하고, 그렇지 않으면 허용된 도구 목록과 함께 거부된다.](./img/workflows-tool-binding-dark.svg#gh-dark-mode-only)

디자인하는 동안 에이전트는 사용자가 볼 수 있는 서버가 제공하는 도구를 나열하고(사용자에게 [액세스 제어 태그](./tags.md)로 숨겨진 서버는 제외됩니다) 단계에 필요한 도구를 부여할 수 있습니다. 이 연결은 템플릿에 저장되며 실행이 시작될 때 실행의 작업으로 복사됩니다.

실행 시점에는 모든 호출이 서버에 도달하기 전에 검사됩니다. (서버, 도구) 쌍이 현재 진행 중인 작업에 연결되어 있어야 합니다. 연결되지 않은 도구에 대한 호출은 허용된 도구를 나열한 메시지와 함께 거부되므로, 여러 워크플로가 공유하는 에이전트라도 작업에 부여되지 않은 도구에는 손댈 수 없습니다. [승인](./approvals.md)이 함께 붙어 있는 작업은 승인으로도 제어됩니다.

**도구 직접 연결.** 템플릿 양식의 **MCP 도구** 선택기는 두 단계로 동작합니다. 페이지가 나뉜 대화 상자에서 서버를 선택한 다음, 드롭다운에서 해당 서버의 도구를 추가합니다. 추가한 도구는 각각 제거할 수 있는 칩이 됩니다. 선택한 서버만 조회하므로 양식을 열어도 등록된 모든 서버에 접속하지 않습니다. 연결할 수 없는 서버는 도구 목록 대신 그 사실을 표시하며, 이미 연결된 도구의 칩은 어느 경우든 유지됩니다. 연결된 도구는 작업 템플릿과 워크플로 작업 목록의 **도구** 열에 칩으로 표시됩니다.

**입력 승인이 필요 없는 도구.** **선택한 도구**에 있는 각 도구의 칩에는 제거 버튼 옆에 작은 방패 버튼이 있습니다. 이 버튼을 클릭하면 해당 도구를 호출할 때 쓰는 값은 그 단계에 적용되는 [승인](./approvals.md)에서 사람이 동의할 대상에서 빠집니다. 승인 자체는 여전히 적용되며 단계는 여전히 승인을 기다립니다. 버튼의 아이콘과 색조는 도구의 현재 상태를 나타내도록 바뀌며, 마우스를 올리면 현재 상태와 클릭했을 때의 동작이 표시됩니다.

이 버튼은 목록 조회, 검색, 상태 확인처럼 **읽기만 하는** 도구에만 클릭하세요. 이 기능이 있는 이유는 두 가지이며, 둘 다 읽기 전용 작업과 관련이 있습니다.

| | |
|---|---|
| 판단할 것이 없습니다 | 아무것도 바꾸지 않는 조회의 인수에 누군가 동의할 필요가 없습니다 |
| 값을 아직 알 수 없습니다 | 단계가 다음에 할 일을 정하려고 무언가를 찾아볼 수 있으므로, 무엇을 요청할지 미리 말할 수 없습니다 |

쓰기, 삭제, 비용 발생, 전송을 하는 도구는 기본 상태로 두세요. 기본값은 "승인 필요"이므로, 추가하고 그대로 둔 도구는 입력이 계속 제한됩니다. "승인 불필요"로 전환한 도구는 실행이 나중에 요청하는 승인에 **모든 입력**으로 표시되므로, 승인자는 어떤 도구의 입력이 제한되지 않았는지 추측하지 않고 바로 알 수 있습니다.

**시작자에게 질문하는 도구.** 일부 도구는 호출 도중에 멈추고 워크플로를 실행한 사람에게 질문합니다. 예를 들어 Azure MCP Server는 시크릿에 대한 모든 작업 전에 동의를 구합니다. 워크플로를 생성할 때의 프롬프트나 디자인 세션에서 어떤 작업의 도구가 그런지 디자인 에이전트에게 알려 주면, 에이전트가 해당 도구를 질문하는 도구로 표시합니다. 이런 도구가 있는 단계는 시작하기 전에 시작자가 재개하기를 기다리므로, 시작자가 채팅에서 답할 수 있습니다([MCP 서버의 확인 요청](./workflow-executions.md#mcp-server-confirmations)). 이렇게 표시되지 않은 도구는 질문할 수 없습니다. 관리 양식에는 이 표시를 다루는 항목이 없으며, 디자인 에이전트가 설정한 값을 그대로 유지합니다. 실행의 작업 타임라인에 있는 **연결된 도구** 대화 상자에서는 이런 도구에 **호출 중에 시작자에게 질문합니다**라고 표시됩니다.

**작업 제목.** 위의 두 목록은 페이지를 나누지 않고 모든 레코드를 표시하므로 **종속 대상** 열이 상호 참조 역할을 합니다. 각 종속 대상은 제목으로 표시되며, 해당 칩에 마우스를 올리면 가리키는 행이 강조됩니다. 디자인 에이전트는 칩으로 깔끔하게 읽히도록 2~4단어, 50자의 간결한 명령형 제목만 쓸 수 있으며, 더 긴 제목은 자세한 내용을 설명으로 옮기라는 안내와 함께 거부됩니다. 이 제한은 에이전트에게만 적용됩니다. 관리 양식에서 편집하는 제목은 200자까지 쓸 수 있으며, 칩을 넘치는 제목은 잘려서 표시되고 마우스를 올리면 전체가 나타납니다.

## 지식 베이스 {#knowledge-bases}

워크플로 상세 페이지의 **지식 베이스**에서 지식 베이스를 선택하고 **저장**을 클릭하면, 디자인 에이전트와 실행 에이전트가 작업하는 동안 그 지식 베이스를 찾아봅니다. [지식 베이스](./knowledge-bases.md#linking-a-knowledge-base-to-a-workflow)를 참조하세요. 이 선택은 게시된 디자인에 포함되지 않으므로, 변경해도 워크플로가 수정됨으로 표시되지 않습니다.

## 워크플로 삭제 {#deleting-a-workflow}

워크플로를 삭제하면 작업 템플릿, 게시된 버전, 디자인 세션도 함께 삭제됩니다. 기존 [워크플로 실행](./workflow-executions.md)은 남습니다. 각 실행은 자체 스냅샷을 가지므로, 원본 워크플로가 사라진 후에도 실행 기록을 읽을 수 있습니다.
