# 알림

워크플로 작업은 백그라운드에서 진행됩니다. 자리를 비운 사이에 디자인 실행이 끝나기도 하고, 앱을 열지 않은 사람의 승인을 기다리기도 합니다. 알림은 이런 이벤트를 필요한 사람에게 전달하는 수단입니다.

상단 도구 모음의 채팅 헤더와 관리 사이드바 양쪽에 **벨 아이콘**이 있으며, 읽지 않은 알림 수를 나타내는 배지가 붙습니다.

## 다섯 가지 이벤트 {#the-five-events}

| 유형 | 발생 시점 | 받는 사람 |
|---|---|---|
| 초안 준비됨 | [워크플로 생성](./workflows.md#generating-a-workflow)의 백그라운드 디자인 실행이 끝나 초안의 작업 템플릿을 검토할 수 있게 되었을 때입니다. | 생성을 시작한 사람 |
| 생성 실패 | 같은 디자인 실행이 실패했을 때입니다. 지켜보는 클라이언트 없이 무인으로 실행되므로 이 알림으로 실패를 알게 됩니다. 이유는 워크플로의 상세 페이지와 디자인 채팅에 표시됩니다. | 생성을 시작한 사람 |
| 승인 요청 | 에이전트가 실행 도중 결정을 요청하고 기다릴 때입니다. | [지정된 승인자](./approvals.md#human-approval). 그룹이 대상이면 자격이 있는 구성원마다 하나씩 |
| 실행 완료 | 실행의 모든 작업이 최종 상태에 도달했을 때입니다. 실행당 한 번 발생합니다. | 실행을 시작한 사람 |
| 입력 요청 | MCP 서버가 [확인](./workflow-executions.md#mcp-server-confirmations)을 요청할 작업이 곧 시작되어, 실행이 사용자가 채팅에서 재개하기를 기다릴 때입니다. | 실행을 시작한 사람 |

알림을 클릭하면 읽음으로 표시되고 알림이 가리키는 곳으로 이동합니다. 실행 관련 이벤트는 해당 실행의 채팅으로, 워크플로 관련 이벤트는 워크플로의 상세 페이지로 이동합니다.

## 알림이 표시되는 곳 {#where-notifications-appear}

| | **벨 드롭다운** | **[알림 페이지](./notifications.md#notification-history-page)** |
|---|---|---|
| **표시 내용** | 읽지 않은 알림만 표시합니다. 아직 확인이 필요한 항목입니다 | 읽은 항목을 포함한 전체 기록 |
| **여는 방법** | 도구 모음의 벨 | 도구 모음의 프로필 버튼 → **알림** |
| **읽음으로 표시** | 행별(✓), 그리고 읽지 않은 항목이 남아 있는 동안 패널 머리글의 **모두 읽음으로 표시** | 행별(✓) |
| **삭제** | 제공되지 않음 | 행별(✕), 확인 후 삭제 |

드롭다운에는 알림을 삭제하는 기능이 없습니다. 읽음으로 표시하면 목록에서 치워질 뿐입니다. 목록은 30초마다 자동으로 새로 고쳐지므로 새 알림은 페이지를 다시 불러오지 않아도 나타납니다.

## 알림 페이지 {#notification-history-page}

알림 페이지에는 받은 모든 알림이 제목, 유형, 생성 시간을 기준으로 정렬하고 필터링할 수 있는 표로 표시됩니다. **읽음** 열을 **예** 또는 **아니요**로 필터링하면 읽은 알림이나 읽지 않은 알림만 볼 수 있습니다. 알림을 영구적으로 삭제할 수 있는 곳은 여기뿐입니다.

A2Flow 자체 알림은 [사용자의 언어](./users-and-groups.md#language)로 표시되지만, 승인의 제목과 설명은 에이전트가 작성한 그대로 유지됩니다. 제목 정렬과 필터링은 영어 텍스트를 기준으로 동작하므로 영어 이외의 언어에서는 **제목** 열에서 둘 다 제공되지 않습니다. 대신 **유형**으로 필터링하세요.

알림은 철저히 사용자별입니다. 자신의 알림만 볼 수 있으며, 알림은 연결된 계정, 실행 또는 워크플로와 함께 사라집니다.

## 이메일 전송 {#email-delivery}

슈퍼 관리자가 [시스템 설정](./system-settings.md)에서 SMTP 서버를 구성하면 같은 다섯 가지 이벤트가 받는 사람에게 **이메일로도** 전송되므로, 승인 요청이 누군가 앱을 열 때까지 기다릴 필요가 없습니다.

메시지의 제목은 알림 제목이고 본문은 알림 본문이며, 해당 대상(실행 또는 워크플로)으로 돌아가는 링크가 포함됩니다. 링크는 구성된 **애플리케이션 기본 URL**로 만들어지며, 설정되어 있지 않으면 링크 없이 전송됩니다.

메일을 전달할 수 없는 받는 사람은 릴레이에 연결하기 전에 제외됩니다. 내부 시스템 사용자, 비활성화되었거나 삭제된 계정, 주소가 확인되지 않은 계정, 주소가 없는 계정이 여기에 해당합니다. 사용자별 수신 거부 기능은 없으며, 이메일 전송은 플랫폼 전체에서 켜거나 끌 수만 있습니다.

### 전송 대기열 {#the-delivery-queue}

워크플로 작업이 진행 중일 때는 아무것도 전송되지 않습니다. 알림과 완전히 렌더링된 메시지가 함께 기록되므로, 장애가 발생해도 이메일이 대기열에 들어가지 않은 알림이 남는 일은 없습니다. 그런 다음 워커가 이 대기열을 처리합니다.

- **속도 조절.** 속도 제한이 릴레이로 보내는 메시지를 초당 일정 개수로 유지하며, 일괄 작업 전체가 재사용되는 연결 하나로 전송됩니다.
- **재시도.** 일시적인 실패(릴레이가 다운되었거나 자격 증명을 거부한 경우)는 간격을 늘려 가며 다시 시도합니다. 15초, 30초, 1분, 2분으로 두 배씩 늘어나 최대 1시간에 이릅니다. 기본 시도 횟수로 약 1시간의 중단을 버틸 수 있습니다.
- **가망이 없으면 포기.** 알 수 없는 받는 사람처럼 릴레이가 영구적이라고 보고한 실패는 재시도하지 않습니다. 시도 횟수를 모두 소진했거나 영구적으로 실패한 메시지는 마지막 오류와 함께 `실패` 상태로 대기열에 남습니다. 조용히 사라지는 것이 아니라 확인할 수 있는 데드 레터로 남습니다. 전송된 메시지는 30일 후 삭제되지만 데드 레터는 유지됩니다.

한 번에 정확히 하나의 프로세스만 전송합니다. 덕분에 속도 제한이 대략이 아니라 정확하게 적용됩니다. 워커를 늘려서 얻는 것은 장애 조치이지 처리량이 아닙니다. 전송 프로세스가 일괄 작업 도중 중단되어도 시도 횟수는 소모되지 않으며, 다음 처리 주기에서 그 작업을 회수합니다.

기본적으로 API 프로세스가 직접 워커를 실행합니다. Docker Compose에서는 전용 워커 서비스가 대신 실행되어 요청을 처리하는 프로세스에서 메일 처리를 분리합니다. 조정 가능한 모든 값은 [구성 참조](../operations/configuration.md#outgoing-email-queue)에 나와 있습니다.

적체와 릴레이 장애 증상은 [메트릭 엔드포인트](../operations/metrics.md)에서 확인할 수 있습니다.
