# 태그

태그는 레코드를 분류하는 레이블입니다. 태그를 붙일 수 있는 7개 레지스트리가 모두 하나의 어휘를 공유하므로, `aws` 태그 하나로 시크릿과 MCP 서버를 똑같이 좁혀 볼 수 있습니다.

![테넌트마다 하나인 공유 태그 어휘가 태그를 붙일 수 있는 7개 레지스트리(시크릿, MCP 서버, 에이전트 스킬, 지식 베이스, 워크플로, 도구 모의, 사용자 그룹)에 적용되는 것을 보여 주는 순서도.](./img/tags-vocabulary.svg#gh-light-mode-only)
![테넌트마다 하나인 공유 태그 어휘가 태그를 붙일 수 있는 7개 레지스트리(시크릿, MCP 서버, 에이전트 스킬, 지식 베이스, 워크플로, 도구 모의, 사용자 그룹)에 적용되는 것을 보여 주는 순서도.](./img/tags-vocabulary-dark.svg#gh-dark-mode-only)

관리 사이드바에서 **태그**를 열어 어휘를 관리합니다. 각 태그에는 테넌트 안에서 고유한 **이름**, 선택 사항인 **설명**, 고정된 8색 팔레트에서 고르는 **색상**(임의의 색상 값은 거부됩니다), 그리고 기본적으로 꺼져 있으며 태그를 단순한 레이블에서 액세스를 통제하는 수단으로 바꾸는 **액세스 제어** 확인란이 있습니다([액세스 제어 태그](#access-control-tags) 참고).

일반 태그를 만들거나 편집하려면 관리자 **또는** 개발자 역할이 필요합니다. 태그를 붙일 수 있는 7개 리소스 중 하나에 쓸 수 있는 역할의 합집합과 일치하므로, 태그가 필요해진 사람은 언제든 직접 만들 수 있습니다. **액세스 제어**가 선택된 태그는 다릅니다. 관리자(또는 슈퍼 관리자)만 만들거나, 필드를 편집하거나, 삭제할 수 있습니다. 개발자에게 기존 액세스 제어 태그는 완전히 읽기 전용으로 표시됩니다. 확인란은 고정 값으로, 다른 필드는 일반 텍스트로 표시되고 **저장** 또는 **삭제** 버튼은 없습니다. 일반 태그는 이전과 같이 만들거나 편집할 수 있습니다. 읽기는 다른 모든 섹션과 마찬가지로 제한이 없습니다.

## 레코드에 태그 붙이기 {#attaching-tags-to-a-record}

태그를 붙일 수 있는 모든 레코드의 만들기 양식과 상세 페이지에는 **태그** 선택기가 있습니다. 현재 선택 항목은 **태그 선택…** 버튼 위에 제거 가능한 색상 칩으로 표시되므로, 필드의 높이는 어휘의 크기가 아니라 선택한 양만큼만 늘어납니다.

1. **태그 선택…** 버튼을 클릭합니다. 대화 상자에 전체 어휘가 줄 바꿈되는 색상 칩 격자로 표시되며, 각 칩은 토글입니다. 눌린 칩은 채우기가 더 진해지고 *동시에* 앞쪽에 체크 표시가 붙으므로, 상태가 색상에만 의존하지 않습니다.
2. 필요하면 격자를 좁힙니다. 두 필터를 함께 사용할 수 있습니다. 이름 입력란과 8개 팔레트 견본 행이며, 견본은 여러 개를 동시에 누를 수 있습니다. 모두 해제한 상태가 필터가 지워진 상태입니다.
3. **선택**으로 확정하거나 **취소**로 초안을 버립니다. 선택한 뒤 필터로 보이지 않게 된 태그도 선택된 상태로 유지됩니다.

태그를 붙이는 작업은 태그를 만든 권한과 관계없이 해당 레코드 자체의 쓰기 역할이 있어야 합니다.

## 태그로 필터링 {#filtering-by-tag}

태그를 붙일 수 있는 모든 목록에는 각 레코드의 칩을 보여 주는 **태그** 열이 있고, 열 머리글 메뉴에서 여러 개를 선택할 수 있습니다. 이 열은 모든 행의 높이를 한 줄로 유지합니다. 현재 너비에 들어가는 만큼 칩을 표시하고 나머지는 끝의 `+N` 칩에 개수로 표시합니다. 이 칩을 클릭하면 레코드의 모든 태그를 나열하는 대화 상자가 열리며, 각 태그에 마우스를 올리면 설명이 표시됩니다. 가장자리를 끌거나 다른 열을 숨겨 열을 넓히면 개수로만 표시되던 태그가 다시 칩으로 나타납니다. 선택은 **논리곱**이며 메뉴에도 "필터(모두 일치)"로 표시됩니다. 따라서 레코드에 선택한 태그가 *모두* 있어야 하며, 태그를 추가할수록 결과가 좁아집니다. 필터는 화면에 보이는 페이지뿐 아니라 전체 데이터 세트에 적용됩니다.

태그는 다른 열 필터와 별개의 축이지만 표시 여부에 관한 규칙은 같습니다. [열 선택기](./admin-ui.md)에서 **태그** 열을 숨기면 태그 필터가 지워지며, 이는 다른 열을 숨기면 해당 열의 필터가 지워지는 것과 똑같습니다.

## 액세스 제어 태그 {#access-control-tags}

**액세스 제어**가 선택된 태그는 태그가 붙은 레코드를 볼 수 있는 사람을 제한합니다. 이 태그의 칩에는 **태그** 목록의 **미리 보기** 열, 레코드의 **태그** 열, 선택기 등 어디에 나타나든 자물쇠 표시가 붙고, **태그** 목록에는 필터링할 수 있는 **액세스 제어** 열이 추가됩니다.

액세스는 자신의 [사용자 그룹](./users-and-groups.md#user-groups)으로 결정됩니다. 그룹에도 자체 태그가 있으며, 자신이 속한 모든 그룹의 태그를 합쳐서 판단합니다.

| 레코드에 있는 태그 | 볼 수 있는 조건 |
|---|---|
| 액세스 제어 태그 없음(일반 태그만 있거나 태그 없음) | 항상 볼 수 있습니다. 일반 태그는 아무것도 제한하지 않습니다 |
| 액세스 제어 태그 하나 이상 | 자신의 그룹들이 합쳐서 그 태그를 **모두** 가지고 있을 때 |

볼 수 없는 레코드는 그냥 없는 것처럼 동작합니다. 목록에 나타나지 않고, 직접 링크를 열어도 찾을 수 없다고 표시됩니다. 관리자와 슈퍼 관리자는 모든 것을 봅니다. 관리자는 어떤 액세스 제어 태그의 제한도 받지 않고, 슈퍼 관리자는 여기에 더해 플랫폼 전체에 걸쳐 있으며 어떤 그룹에도 속하지 않으므로 다른 규칙도 적용될 수 없습니다.

태그를 붙일 때 적용되는 안전장치가 하나 있습니다. **자신의 그룹에 없는 액세스 제어 태그는 붙일 수 없습니다.** 다음에 페이지를 열 때 레코드가 자신에게 보이지 않게 되므로 저장이 오류와 함께 거부됩니다. 먼저 관리자에게 그 태그가 있는 그룹에 추가해 달라고 요청하세요. *사용자 그룹*에 태그를 붙이는 경우는 예외입니다. 관리자가 애초에 액세스를 부여하는 방법이 바로 그것이기 때문입니다.

이 제한은 레코드를 열고, 편집하고, 실행하고, 삭제할 수 있는 사람에 관한 것입니다. 레코드가 내부적으로 사용하는 것에는 영향을 주지 않습니다. 워크플로는 생성 기반이 된 에이전트 스킬과 MCP 서버가 참조하는 시크릿으로 계속 실행되며, 요청자가 그 스킬이나 시크릿을 직접 열 수 없어도 마찬가지입니다.

워크플로 디자인은 예외입니다. 단계에 도구를 제공하는 것은 자신이 직접 MCP 서버를 사용하는 것으로 간주됩니다. 작업 템플릿의 **MCP 도구** 선택기에서 고르든, 사용자를 대신해 일하는 디자인 에이전트에게 요청하든, **자신이** 열 수 있는 서버의 도구만 연결할 수 있습니다. 자신의 그룹에 없는 액세스 제어 태그가 붙은 서버는 에이전트의 도구 목록에 나타나지 않으며, 연결하려고 하면 서버가 없는 것처럼 거부됩니다. 볼 수 있는 사람이 이미 단계에 연결한 도구는 단계를 편집해도 그대로 유지되고, **변경 사항 취소**는 게시된 연결을 그대로 복원합니다.

## 워크플로 실행과 승인의 태그 {#execution-and-approval-tags}

[워크플로 실행](./workflow-executions.md)에도 **태그** 열과 필드가 표시되며 해당 실행에 속한 [승인](./approvals.md)도 마찬가지입니다. 다만 읽기 전용이고 위의 7개 레지스트리에는 포함되지 않습니다. 실행이 시작되면 그 시점에 워크플로에 있는 태그를 복사합니다. 이후 워크플로의 태그를 변경하거나 워크플로를 삭제해도 이미 시작된 실행의 표시는 바뀌지 않습니다. 이 두 화면에는 **태그** 선택기가 없고 목록에도 태그 필터가 없습니다. 태그를 붙이고 떼는 작업은 워크플로에서만 합니다.

이렇게 복사된 액세스 제어 태그도 워크플로와 똑같이 실행과 그 승인을 제한합니다. 실행이 복사한 태그가 자신의 그룹에 더 이상 없으면 그 실행과 그 아래의 모든 승인이 목록과 직접 링크에서 사라지며, 자신이 실행을 시작했거나 지정된 승인자여도 마찬가지입니다. 실행 안에서 할 수 있던 모든 작업도 마찬가지입니다. 채팅에 메시지 보내기, 작업 열기, 그 아래의 승인을 승인하거나 반려하기는 모두 실행이 존재하지 않는 것처럼 실패합니다. 다른 액세스 제어 태그와 마찬가지로 관리자와 슈퍼 관리자만 예외입니다. 태그는 실행 *전에* 워크플로에 붙여 두어야 합니다. 복사는 실행이 시작되는 순간 한 번만 일어나므로, 이후 워크플로의 태그를 변경해도 이미 시작된 실행에는 적용되지 않습니다.

실행에 복사된 액세스 제어 태그는 [승인을 요청](./approvals.md#human-approval)할 수 있는 대상도 결정합니다. 개인을 대상으로 지정하려면 그 사람의 그룹 중 하나에 실행이 가진 해당 태그가 모두 있어야 하고, [사용자 그룹](./users-and-groups.md#user-groups)을 대상으로 지정하려면 그 그룹 자체에 해당 태그가 있어야 합니다. 그렇지 않으면 그 사람이나 그룹이 요청을 보고 결정할 수 없으므로 요청이 거부됩니다. 관리자는 다른 곳에서도 이 태그를 우회하므로 개인 대상일 때는 예외입니다. 사용자 그룹에는 이런 예외가 없으며, 구성원 중에 관리자가 있어도 마찬가지입니다.

## 이름 변경과 삭제 {#renaming-and-deleting}

**이름 변경은 언제든 안전합니다.** 레코드는 태그를 이름이 아니라 식별자로 참조하므로, 태그가 붙은 모든 레코드가 다시 동기화할 필요 없이 새 이름을 따릅니다. 바로 이것이 각 레코드에서 자유롭게 입력하지 않고 태그를 미리 등록하는 이유입니다.

**삭제**는 반대로 동작합니다. 태그가 붙은 레코드 때문에 삭제가 막히지 않고, 모든 레코드에서 태그가 제거됩니다. 확인 대화 상자에도 그렇게 표시됩니다. **액세스 제어**가 선택된 태그를 삭제하려면 편집과 마찬가지로 관리자 또는 슈퍼 관리자 권한이 필요하며, 일반 태그 삭제는 개발자도 계속 할 수 있습니다.
