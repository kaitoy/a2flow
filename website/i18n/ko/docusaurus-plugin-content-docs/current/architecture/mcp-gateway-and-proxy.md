# MCP 게이트웨이와 프록시

에이전트는 등록된 [MCP 서버](../guides/mcp-servers.md)와 직접 통신하지 않습니다. 모든 호출은 A2Flow가 소유한 두 구성 요소를 거치며, 이 둘은 서로 다른 질문에 답합니다.

| | MCP 게이트웨이 | MCP 프록시 |
|---|---|---|
| **실행 위치** | 에이전트 프로세스 안, 데이터베이스 옆 | 에이전트의 시크릿을 전혀 갖지 않는 별도 컨테이너 |
| **결정하는 것** | 호출을 *허용할지* 여부 | 호출이 *어디서* 일어날지. 서버를 시작하거나 서버에 연결합니다 |
| **보유하는 것** | 신원, 정책 체인, 도구 모의, 시크릿 확장, 감사 기록 | 한 번에 호출 하나: 서버의 주소 또는 명령, 확장된 값, 도구와 그 인수 |

게이트웨이는 의사 결정자이며, 이 페이지의 나머지는 대부분 게이트웨이에 관한 내용입니다. 프록시는 그 결정을 넘겨받는 샌드박스로, 별도의 섹션은 [아래](#the-sandbox)에 있습니다.

| 게이트웨이가 맡는 것 | 하는 일 |
|---|---|
| **신원** | 호출이 도착한 대화를 근거로 어떤 테넌트와 어떤 실행에 속하는지 확정합니다 |
| **권한 부여** | 어느 하나라도 거부할 수 있는, 순서가 정해진 정책 체인을 확인합니다 |
| **스텁 처리** | 실행에 이 도구의 [도구 모의](#tool-mocks-and-dry-runs)가 있으면 그것으로 응답합니다 |
| **자격 증명** | 등록된 서버의 [시크릿](./secrets.md) 참조를 연결 시점에만 확장해 연결에 사용합니다 |
| **격리** | 허용된 호출을 서버를 실제로 실행하는 [MCP 프록시](#the-sandbox)에 넘깁니다 |

## MCP 프록시: 등록된 서버가 실행되는 곳 {#the-sandbox}

등록한 MCP 서버는 A2Flow의 코드가 아닙니다. 로컬 서버는 A2Flow가 사용자를 대신해 시작하는 프로그램이고, 원격 서버는 A2Flow가 바깥으로 연결하는 서비스입니다. 어느 쪽이든 일단 실행되면 그 동작은 A2Flow가 통제할 수 없습니다.

그래서 서버는 A2Flow의 시크릿이 있는 곳에서 실행되지 않습니다. 프록시는 샌드박스이며, Docker Compose 배포에서는 **별도의 `mcp-proxy` 컨테이너**입니다. 이 컨테이너에는 다음 항목이 전혀 없습니다.

| 프록시에 없는 것 | 있는 곳 |
|---|---|
| 데이터베이스와 그 안에 기록된 모든 내용 | 에이전트 쪽 |
| [시크릿](./secrets.md)을 암호화하는 키 | 에이전트 쪽 |
| 외부 시크릿 저장소의 자격 증명 | 에이전트 쪽 |
| LLM 제공자의 API 키 | 에이전트 쪽 |
| [에이전트 스킬](../guides/agent-skills.md) 저장소 | 에이전트 쪽 |

프록시가 받는 것은 한 번에 호출 하나뿐입니다. 연결할 서버 하나의 주소 또는 명령, 시크릿 참조에서 이미 확장된 해당 서버에 필요한 값, 그리고 도구와 인수입니다. 그 밖에는 찾아낼 것이 없습니다.

![호출의 허용 여부, 모의 여부, 필요한 자격 증명을 결정하는 MCP 게이트웨이가 권한이 부여된 호출 정확히 하나를 신뢰 경계 너머의 MCP 프록시로 넘기고, MCP 프록시가 실제 MCP 서버를 시작하거나 연결하는 것을 보여 주는 아키텍처 다이어그램.](./img/mcp-gateway-and-proxy-trust-boundary.svg#gh-light-mode-only)
![호출의 허용 여부, 모의 여부, 필요한 자격 증명을 결정하는 MCP 게이트웨이가 권한이 부여된 호출 정확히 하나를 신뢰 경계 너머의 MCP 프록시로 넘기고, MCP 프록시가 실제 MCP 서버를 시작하거나 연결하는 것을 보여 주는 아키텍처 다이어그램.](./img/mcp-gateway-and-proxy-trust-boundary-dark.svg#gh-dark-mode-only)

**양쪽 끝은 서로의 신원을 증명합니다.** 둘 사이의 채널은 암호화되어 있고, 어느 쪽도 신원이 확인되지 않은 상대를 받아들이지 않습니다. 프록시는 이 배포에서 발급한 인증서를 갖지 않은 모든 연결을 거부합니다. 또한 개별 호출마다 호출하는 작업의 [인증서](#who-authorized-a-call)가 함께 전달되며, 프록시는 무언가에 접근하기 전에 이 인증서를 다시 확인합니다. 여기서 발급되었는지, 만료되지 않았는지, 호출자의 것인지, 바로 이 도구를 포함하는지를 확인합니다.

**호출은 도중에 질문을 할 수 있습니다.** MCP 서버는 호출 도중에 멈춰 실행의 당사자에게 [확인](../guides/workflow-executions.md#mcp-server-confirmations)을 요청할 수 있습니다. 그 사람이 누구인지 아는 것은 게이트웨이이므로, 프록시는 호출 자체의 연결을 통해 질문을 돌려보내고, 답변은 같은 연결을 거슬러 기다리는 서버로 전달됩니다. 호출에 관한 어떤 것도 연결보다 오래 남지 않으므로 프록시는 컨테이너를 몇 개든 띄워 실행할 수 있습니다.

두 번째 확인은 첫 번째 확인과 같은 질문이 아닙니다. A2Flow라고 해서 특정 도구를 호출할 권한이 있는 것은 아니며, 작업의 인증서를 가졌다고 해서 그 요청이 A2Flow가 보낸 요청인 것도 아닙니다. 둘 다 성립해야 하므로, 요청이 유효한 권한을 유지한 채 슬그머니 프록시가 다른 프로그램을 가리키게 할 수 없습니다.

작업 인증서를 지니지 않는 호출이 하나 있습니다. MCP 서버 양식에서 수행하는 스크립트의 [테스트 실행](../guides/mcp-servers.md#testing-a-script)으로, 그 뒤에 작업이 없습니다. 프록시는 이를 스크립트에 대해서만 허용하고 임의의 명령이나 원격 서버에는 허용하지 않습니다. 스크립트의 도구 목록을 불러오는 것만으로도 같은 A2Flow 전용 확인 아래 스크립트 전체가 이미 실행되므로, 이로 인해 새로 통과되는 것은 없습니다.

프록시는 의사 결정자가 아니라 두 번째 방어선입니다. 작업이 아직 실행 중인지, 승인이 아직 유효한지, 인증서가 폐기되었는지는 프록시에서 답할 수 없으며, 모두 게이트웨이가 판단합니다.

## 실행마다 전용 샌드박스 {#per-launch-sandbox}

프록시는 등록된 서버를 A2Flow로부터 떼어 놓을 뿐 아니라 **서로로부터도** 떼어 놓습니다. 모든 테넌트의 서버가 같은 프록시에서 시작되고 그중 일부는 테넌트가 직접 작성한 스크립트이므로, 프록시가 시작하는 각 서버는 해당 호출 하나를 위해 만들어지고 호출이 끝나면 해체되는 전용 샌드박스 안에 격리됩니다.

| 샌드박스 내부 | 이를 통해 막는 것 |
|---|---|
| 서버에는 자신의 프로세스만 보입니다 | 동시에 실행 중인 다른 서버에 전달된 시크릿 값 읽기 |
| 시스템과 A2Flow 자체 프로그램은 읽기 전용입니다 | 이후에 시작될 서버(예: 다른 테넌트의 서버)가 다음 시작 시 실행할 내용 변경 |
| 다운로드한 패키지를 보관하는 홈 디렉터리는 해당 테넌트 전용입니다 | 다른 테넌트가 심어 둔 패키지를 서버가 가져다 쓰는 일 |
| 내부의 모든 것은 호출이 끝나면 종료됩니다 | 호출 후에도 프로세스가 남아 이후의 호출을 감시하는 일 |
| 프록시 자체의 자격 증명은 전혀 없습니다 | 누군가에게 프록시를 사칭하는 일 |

프록시가 바깥으로 연결만 하는 원격 서버는 프록시 안에서 아무것도 실행하지 않으므로 샌드박스가 필요 없습니다.

이 격리는 Flatpak의 기반인 Linux 샌드박싱 도구 [bubblewrap](https://github.com/containers/bubblewrap)을 기반으로 합니다. 프록시는 시작할 때 샌드박스를 만들 수 있는지 확인하고, 만들 수 없으면 시작을 거부합니다. 샌드박스 없이 서버를 실행하는 방식으로 대체하는 일은 절대 없습니다. 호스트에 필요한 조건은 [배포](../operations/deployment.md#process-layout)를 참조하세요.

## 정책 체인 {#the-policy-chain}

| 순서 | 정책 | 요구 사항 |
|---|---|---|
| 1 | **진행 중 도구 연결** | `(서버, 도구)` 쌍이 `진행 중`이고 호출 세션에 할당된 작업에 연결되어 있어야 합니다. 실행의 다른 세션이 처리 중인 작업은 해당되지 않습니다. 서버가 제공하는 도구를 나열하는 것은 호출이 아니므로 이 규칙이 적용되지 않습니다. 디자인 에이전트는 무엇을 연결할지 결정하기 위해 나열하며, 이때 디자이너가 [액세스 제어 태그](../guides/tags.md)에 따라 볼 수 있는 서버로 범위가 좁혀집니다. 실행 자체의 나열은 태그로 좁혀지지 않습니다 |
| 2 | **도구 인증서** | 호출은 작업의 인증서를 제시해야 하며([누가 호출을 승인했는가](#who-authorized-a-call) 참조), 인증서의 서명된 권한이 해당 도구를 포함해야 합니다. 예외는 없습니다. 어떤 승인의 대상도 아닌 작업은 실행 시작자가 보유한 권한을 제시합니다 |
| 3 | **승인된 호출** | 승인자의 결정이 작업을 허가하는 근거인 경우, 호출은 그 결정에 나열된 호출과 일치해야 합니다. [결정이 다루는 호출](./approvals.md#the-calls-a-decision-covers)을 참조하세요. 결정에서 모든 입력을 받는 것으로 나열된 도구는 결정이 부여될 때까지 이미 규칙 2에서 멈춰 있었으므로, 무엇을 전달하든 이 규칙을 통과합니다. 시작자 자신의 권한으로 실행되는 작업에는 이런 목록이 없으며 여기서 확인되지 않습니다 |

체인은 첫 번째 거부에서 멈추고 비용이 적은 순서로 배치되므로, 이미 연결 규칙에 실패한 호출은 서명 확인 비용을 치르지 않습니다. 마지막 규칙이 마지막에 실행되는 데에는 다른 이유도 있습니다. *어떤* 작업이 호출하는지 알아야 하는 규칙은 이것뿐이며, 그 앞의 규칙이 이를 확정합니다. 또한 아무 권한도 없는 호출자가 승인자가 동의한 내용을 알아내지 못하게 합니다. 규칙을 추가하려면 게이트웨이를 편집하는 대신 체인에 정책을 추가합니다. 덕분에 "무엇을 실행할 수 있는가"를 하나의 순서 있는 목록으로 읽을 수 있습니다.

거부 메시지는 로그가 아니라 호출자를 위해 작성됩니다. 거부된 호출에는 허용된 도구의 이름이 함께 반환되므로, 모델은 추측하지 않고 스스로 바로잡을 수 있습니다.

## 누가 호출을 승인했는가 {#who-authorized-a-call}

실행의 모든 도구 호출에는 그 권한의 주인을 밝히는 **인증서**가 함께합니다. 작업은 **진행 중**으로 표시될 때 인증서를 부여받으며, 누구의 권한을 지니는지는 [승인](./approvals.md)의 대상인지에 따라 달라집니다.

| 작업 | 인증서를 받는 시점 | 권한의 주인 |
|---|---|---|
| 자신의 승인 또는 앞선 작업에 요청된 승인의 대상 | 시작할 때, 해당 승인이 부여된 후에만 | 승인을 부여한 승인자 |
| 어떤 승인의 대상도 아님 | **진행 중**으로 표시될 때 | 실행을 시작한 사람 |

두 번째 행이 일반적인 경우입니다. 아무도 그 작업을 판단하도록 요청받지 않았으므로 워크플로를 실행한 사람이 작업에 연결된 도구를 승인하고, 감사 추적은 호출을 주체 없이 남기지 않고 그 사실을 명시적으로 기록합니다.

여기서 세 가지 규칙이 나오며, 모두 워크플로를 운영하는 사람에게 보입니다.

- **도구는 작업이 시작될 때 고정됩니다.** 인증서는 그 순간 작업에 연결된 도구만 정확히 포함합니다. 작업이 시작된 후에야 도구를 연결하는 워크플로에서는 그 도구가 거부됩니다. 디자인 에이전트에게는 먼저 연결하도록 안내되어 있지만, 직접 편집한 작업은 여전히 이를 잘못할 수 있습니다. 승인의 대상인 작업은 도구를 전혀 편집할 수 없습니다.
- **승인을 요청하면 문이 다시 닫힙니다.** 누군가의 권한으로 이미 실행 중인 작업을 다루는 승인이 요청되면 그 권한은 즉시 물러나고, 작업은 다른 작업과 마찬가지로 결정을 기다립니다.
- **대상 작업은 각자 인증서를 받습니다.** 작업 체인을 다루는 하나의 승인이 모든 작업을 하나의 시간 제한에 묶지는 않습니다. 각 작업은 시작할 때 자신의 인증서를 부여받습니다.

## 기록되는 내용 {#what-is-recorded}

| 결정된 호출별로 기록되는 내용 | 의도적으로 기록하지 않는 내용 |
|---|---|
| 도구, 서버, 허용 또는 거부 여부 | 인수 자체. 다이제스트만 보관합니다 |
| 거부된 경우 거부 이유. 승인 범위를 벗어난 호출이면 문제가 된 입력과 승인자가 동의한 범위 | 거부된 입력의 실제 값 |
| 제시된 인증서, 그리고 이를 통해 호출을 승인한 사람 | |

이 기록이 실행의 **도구 호출** 페이지이며, 이 덕분에 "누가 이 호출을 승인했는가"에 사후에 답할 수 있습니다. 인증서 자체는 **감사 로그 → 인증서**에 부여 건당 한 행으로 나열됩니다.

## 도구 모의와 드라이 런 {#tool-mocks-and-dry-runs}

[도구 모의](../guides/tool-mocks.md)를 사용하면 도구의 부작용 없이 **초안** 워크플로를 처음부터 끝까지 시험해 볼 수 있습니다. 여기서 중요한 것은 스텁이 *어디에* 위치하느냐입니다.

![도구 모의는 프로덕션 호출과 동일한 정책 체인을 거친 후에만 참조된다는 것을 보여 주는 순서도. 거부된 호출은 프로덕션과 똑같이 거부되고, 허용된 호출은 모의의 다음 응답이나 실제 MCP 서버가 응답합니다.](./img/mcp-gateway-and-proxy-tool-mocks.svg#gh-light-mode-only)
![도구 모의는 프로덕션 호출과 동일한 정책 체인을 거친 후에만 참조된다는 것을 보여 주는 순서도. 거부된 호출은 프로덕션과 똑같이 거부되고, 허용된 호출은 모의의 다음 응답이나 실제 MCP 서버가 응답합니다.](./img/mcp-gateway-and-proxy-tool-mocks-dark.svg#gh-dark-mode-only)

스텁은 정책 체인 **이후에** 참조되며, 절대 그 전에 참조되지 않습니다. 따라서 드라이 런은 실제 실행이 거치는 것과 동일한 권한 확인을 연습합니다. 도구는 여전히 진행 중인 작업에 연결되어 있어야 하고, 호출은 여전히 그 작업의 인증서를 제시해야 합니다. 모의가 건너뛰는 것은 A2Flow 외부에 영향을 주는 부분뿐이며, 프록시에는 절대 도달하지 않습니다.

알아 둘 만한 결과가 두 가지 있습니다.

- **응답은 호출 횟수를 따릅니다.** 첫 번째 응답은 실행에서 해당 도구를 처음 호출할 때, 두 번째 응답은 두 번째 호출할 때 사용되며, 목록이 끝나면 마지막 응답이 반복됩니다. 카운터는 실행에 속하므로 하나의 에이전트 실행에 걸친 여러 요청과 레플리카가 달라져도 유지됩니다.
- **스텁 처리된 호출은 감사 기록을 남기지 않습니다.** 이 기록은 실제 서버에 도달했거나 도달하는 도중에 멈춘 호출을 위한 것입니다. 처음부터 스냅샷으로 응답할 호출에 행을 남기면 어느 쪽으로든 오해를 낳습니다. 스텁 처리된 호출은 채팅 기록에서 `모의됨` 배지로 살펴봅니다.
