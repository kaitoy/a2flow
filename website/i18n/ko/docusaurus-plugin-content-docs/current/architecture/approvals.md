# 승인 게이트

[승인](../guides/approvals.md)은 두 가지 일을 동시에 합니다. 사람이 결정할 때까지 실행을 한 단계에서 멈추고, 그 결정을 해당 단계들이 이후 무엇을 할 수 있는지 정확히 밝히는 서명된 권한으로 바꿉니다.

![승인의 시퀀스 다이어그램. 실행 에이전트가 승인을 요청하면, 대상 단계가 차단된 상태에서 A2Flow가 승인자에게 알립니다. 승인자가 결정하면 A2Flow는 대상 단계가 시작될 때마다 인증서를 부여하고 실행을 계속하게 합니다.](./img/approvals-sequence.svg#gh-light-mode-only)
![승인의 시퀀스 다이어그램. 실행 에이전트가 승인을 요청하면, 대상 단계가 차단된 상태에서 A2Flow가 승인자에게 알립니다. 승인자가 결정하면 A2Flow는 대상 단계가 시작될 때마다 인증서를 부여하고 실행을 계속하게 합니다.](./img/approvals-sequence-dark.svg#gh-dark-mode-only)

## "차단"의 의미 {#what-blocked-means}

이 일시 중지는 에이전트가 예의 바르게 기다리는 것이 아닙니다.

| 승인이 결정되지 않은 동안 | |
|---|---|
| 대상 단계가 호출할 수 있는 것 | 연결된 MCP 도구 중 어느 것도 호출할 수 없습니다. 호출은 서버에 도달하기 전에 거부됩니다 |
| 이를 강제하는 주체 | [게이트웨이](./mcp-gateway-and-proxy.md)가 확인하는 규칙이며, 에이전트 지침에 적힌 문장이 아닙니다 |
| 게이트를 작동시키는 조건 | 해당 단계를 대상으로 하는 승인의 *존재*입니다. 대기 중인 승인과 반려된 승인은 똑같이 차단하므로, 게이트는 실패 시 차단 상태를 유지합니다 |
| 영향을 받지 않는 것 | 어떤 승인의 대상도 아닌 단계입니다. 일반적인 도구 연결 규칙에 따라 계속 실행됩니다 |

따라서 프롬프트 인젝션이나 버그가 말로 게이트를 통과할 수는 없습니다. 설득할 상대가 없기 때문입니다. 게이트를 여는 것은 승인에 기록된 결정뿐입니다.

## 인증서 {#the-certificate}

승인 대상인 각 단계에는 시작할 때 수명이 짧은 인증서가 부여되며, 이 인증서는 배포가 처음 사용할 때 스스로 생성하는 인증 기관이 서명합니다.

인증서는 승인이 추가하는 것이 아닙니다. 도구를 호출하는 단계는 **모두** 인증서를 가집니다. 승인이 바꾸는 것은 인증서의 출처입니다. 아무도 승인 요청을 받지 않은 단계는 실행을 시작한 사람의 권한으로 인증서를 부여받으며, 승인은 이를 승인자 본인의 권한으로 대체합니다. 그래서 기록이 답하는 질문은 "이 호출이 승인되었는가"가 아니라 항상 "누가 승인했는가"입니다.

| 인증서에 담기는 내용 | 중요한 이유 |
|---|---|
| 어떤 테넌트, 실행, 단계를 대표하는지, 그리고 승인자와 실행 시작자 중 누구의 권한을 지니는지 | 한 실행을 위해 발급된 인증서는 다른 실행에서 쓸모가 없고, 한 종류의 권한이 다른 종류를 대신할 수 없습니다 |
| **단계가 시작되는 순간 연결되어 있던 도구** | 실행의 단계와 도구는 실행 시점에 워크플로의 게시된 디자인에서 고정되고, 인증서는 발급 시 이를 다시 고정하며, 승인 대상 단계의 도구는 더 이상 전혀 편집할 수 없습니다. 따라서 에이전트도, 나중의 변경도 권한을 넓힐 수 없습니다. 파일 읽기 승인이 파일 삭제 승인으로 바뀌는 일은 없습니다 |

### 결정이 다루는 호출 {#the-calls-a-decision-covers}

인증서는 *어떤 도구인지*만 답할 뿐 *어떤 값으로 호출하는지*는 답하지 않는데, 결과를 좌우하는 것은
대개 입력입니다. 그래서 요청에는 인증서에 없는 두 번째 항목, 즉 요청이 허가하는 호출 목록이 담깁니다.
각 호출은 도구 이름과 입력이 가질 수 있는 값의 범위를 명시합니다. 이 목록은 요청 시점에 기록되고,
승인자가 결정하기 전에 표시되며, 이후에는 에이전트를 포함해 누구도 편집할 수 없습니다.

이후 프록시를 거치는 모든 호출은 인증서와 함께 이 목록의 적용을 받습니다.

| 확인 대상 | 거부되는 경우 |
|---|---|
| 도구 | 인증서가 부여한 도구라도 결정에 나열되어 있지 않은 경우 |
| 제공된 각 입력 | 결정에 이름이 없는 경우. 즉 승인자가 본 적 없는 입력인 경우 |
| 결정에 이름이 있는 각 입력 | 결정에서 선택 사항으로 표시하지 않았는데 누락된 경우 |
| 각 값 | 승인자가 동의한 범위를 벗어나는 경우 |

승인된 두 분기가 만나는 단계는 처음에 두 결정이 모두 필요한 것과 같은 이유로 **두** 결정을 모두
충족해야 합니다. 더 관대한 승인자가 다른 승인자를 대변하지는 않기 때문입니다. 도구의 입력에 승인이
필요한지에 대해 두 결정이 다르면 더 엄격한 쪽을 따릅니다.

워크플로의 디자인에서 읽기 전용으로 표시된 도구도 빠지지 않고 **모든 입력**으로 나열됩니다. 결정은 자신이
허가하는 내용의 완전한 기록으로 남으므로, 승인자는 어떤 도구가 제한 없이 남았는지 볼 수 있고, 게이트는
단계의 도구를 새로 읽는 두 번째 규칙 대신 하나의 목록만 확인하면 됩니다. 이런 항목을 쓰는 것은 요청 경로뿐이며,
에이전트가 직접 선언하려고 하면 거부됩니다.

실행 시작자 본인의 권한으로 수행되는 단계는 이런 방식으로 확인하지 않습니다. 승인자가 없었으므로 벗어날
기준도 없기 때문입니다. 이 단계를 제한하는 것은 변함없이 자신의 도구와 인증서의 서명된 권한입니다.

### 승인이 다루는 단계 {#the-steps-an-approval-covers}

승인은 **자신이 지정한 단계와 다음 승인 전까지 그 뒤의 모든 단계**를 다룹니다. 따라서 워크플로는 요청을 별도의 단계로 두고 결정이 그다음 작업까지 미치게 할 수 있습니다.

![승인 A가 처음 세 단계를 다루고 승인 B가 네 번째 단계부터 이어받는 5단계 작업 체인의 순서도. 승인은 자신이 지정한 단계와 다음 승인 전까지 그 뒤의 모든 단계를 다룹니다.](./img/approvals-step-coverage.svg#gh-light-mode-only)
![승인 A가 처음 세 단계를 다루고 승인 B가 네 번째 단계부터 이어받는 5단계 작업 체인의 순서도. 승인은 자신이 지정한 단계와 다음 승인 전까지 그 뒤의 모든 단계를 다룹니다.](./img/approvals-step-coverage-dark.svg#gh-dark-mode-only)

승인 A는 *진행 승인 요청*, *인스턴스 시작*, *인스턴스 태그 지정*을 다룹니다. *다시 요청*부터는 승인 B가 이어받습니다. 요청보다 앞에 있는 단계는 절대 다루지 않습니다. 승인은 앞으로만 미칩니다.

| 상황 | 일어나는 일 |
|---|---|
| 지정된 단계 자체는 도구를 사용하지 않음 | 문제없으며 흔한 경우입니다. 결정은 그 뒤의 단계로 이어집니다 |
| 어떤 단계가 서로 다른 분기의 승인 두 개 뒤에 있음 | 동작하려면 **둘 다** 부여되어야 합니다. 한 승인자가 자신의 분기를 승인했다고 해서 다른 승인자를 대변하지는 않습니다 |
| 이전 승인이 이미 다루는 단계에 두 번째 승인을 요청함 | 더 가까운 요청이 즉시 이어받고, 이전 결정은 해당 단계를 더 이상 허가하지 않습니다 |
| 단계가 재작업을 위해 반환되어 다시 제출됨 | 새 요청이 이전 결정을 대신해 그 단계의 게이트가 되므로, 반려 때문에 단계가 영구히 멈추는 일은 없습니다 |

이후 대상 단계의 모든 도구 호출은 인증서를 제시해야 하며, 게이트웨이는 호출을 어디로든 보내기 전에 다음을 모두 확인합니다.

- 인증서가 이 실행과 이 단계를 대표하는지
- 이 배포에서 발급했고 폐기되지 않았는지
- 인증서의 근거인 승인이 아직 해당 단계를 다루고, 해당 단계를 다루는 모든 승인이 여전히 부여된 상태인지
- 호출자가 인증서를 복사한 것이 아니라 자신의 것임을 증명할 수 있는지
- 호출하는 도구가 서명된 집합 안에 있는지

인증서는 해당 단계가 종료 상태에 도달하면 폐기됩니다. 안전성이 여기에 달려 있는 것은 아닙니다. 끝난 단계는 더 이상 실행 중이 아니므로 호출은 이미 거부되기 때문입니다. 하지만 폐기를 통해 권한이 효력을 잃은 *이유*가 기록에 남고, 인증서의 수명이 그것이 허가한 작업과 일치하게 됩니다. 각 대상 단계는 시작할 때 자신의 인증서를 부여받으므로, 긴 단계 체인이 인증서 하나의 수명 안에 끝날 필요는 없습니다. 최대 수명은 [구성 참조](../operations/configuration.md#mcp-tools-and-approvals)에서 조정할 수 있습니다.

## 기록이 답하는 질문 {#what-the-record-answers}

결정된 모든 호출은 허용되었든 거부되었든 제시된 인증서와 함께 기록되므로, "누가 어떤 근거로 이를 승인했는가"에 실행이 끝난 지 한참 뒤에도 답할 수 있습니다. 인수는 다이제스트로만 보관하며 원시 값은 절대 저장하지 않습니다. 이 기록은 실행의 **도구 호출** 페이지에서 읽을 수 있습니다.

결정을 벗어나 거부된 호출에는 문제가 된 입력과 승인자가 동의한 범위를 밝힌 이유가 기록되지만, 실제로 전달된 값은 기록되지 않습니다. 이유는 작성된 그대로, 인수를 다이제스트로만 보관하는 바로 그 기록에 저장되므로, 거부된 값을 여기에 인용하면 다이제스트가 제외하려는 내용을 다시 넣는 셈이 됩니다.

**보장의 범위.** 게이트웨이는 백엔드 프로세스 안에서 실행되므로, 인증서는 같은 프로세스를 공유하는 검증자에게 소유를 증명할 뿐이며 이미 백엔드를 장악한 공격자에 대한 방어 수단은 아닙니다. 인증서가 실제로 제공하는 것은 실패 시 차단되는 단일 적용 지점, 사후에 넓힐 수 없는 권한, 나중에 확인할 수 있는 기록입니다.
