# デプロイ

デプロイの構成要素は、バックエンドとフロントエンドと 1 つのリレーショナルデータベースです。3 つをまとめて立ち上げる一番短い道は [Docker Compose で動かす](../getting-started/docker-compose.md)です。ここから先は、その構成がプロキシの背後に入り、残しておく価値のあるデータを抱えるようになったときに変わることです。

## リバースプロキシとロードバランサー

**スティッキーセッション(セッションアフィニティ)は不要です。** [水平スケーリング](./scaling.md)を参照してください。1 つの ADK セッションを同時に 1 つのドライバーに留めているのはルーティングのアフィニティではなく PostgreSQL のアドバイザリロックで、しかもそれが効くのは 1 本の SSE ストリームのあいだだけです。

SSE の 2 つのルート(`POST /api/v1/agent` と `POST /api/v1/workflow-executions/{id}/agent`)には、リバースプロキシやロードバランサーの層で次の設定が必要です。

- **これらのパスでレスポンスのバッファリングを無効にする。** アプリはどちらにも `X-Accel-Buffering: no` を付けており、nginx は全体でバッファリングが有効でもこれをレスポンス単位で尊重します。ほかのプロキシやロードバランサーでは、設定レベルでバッファリングを切る必要があります(nginx 自身の `proxy_buffering off;` など。`X-Accel-Buffering` が効くのは nginx だけです)。
- **`text/event-stream` の gzip や圧縮を無効にする。** アプリ自身がレスポンスを圧縮することはありません(`GZipMiddleware` は登録していません)。したがってクライアントから見える圧縮は、ロードバランサーやプロキシの層から来ているとしか考えられません。`text/event-stream` を対象外にしてください。
- **読み取り/アイドルのタイムアウトを十分長くとる。** 現在、エージェントの実行にサーバー側の時間制限はありません(`session_timeout_seconds` はなく、実行をタイムアウトで包んでもいません)。そのためストリームを終わらせられるのはプロキシ層の読み取りタイムアウトだけで、短すぎると正当な長時間の応答を黙って切ってしまいます。「一般的な」リクエストのタイムアウトではなく、想定する最長の実行より十分に長く設定してください。
- **uvicorn のグレースフルシャットダウンの猶予は 30 秒です**(`--timeout-graceful-shutdown`。`Dockerfile` の `CMD` で設定しています)。ローリングデプロイでは、コンテナが SIGTERM を受け取ってから 30 秒後にまだ開いている SSE ストリームは強制的に終了します。これは安全です。アドバイザリロックは接続とともに解放され、クライアントは新しいリクエストで再開します。中断や切断されたストリームがすでにそう振る舞っているのと同じです。

## 永続化が必要な状態

コンテナより長生きし、デプロイが元どおり立ち上がるために永続ストレージに置く(またはバックアップから復元できるようにする)必要があるものが 3 つあります。

- **データベース** — REST のレコードも ADK のセッションストアも、`DB_URL` が指すデータベースに入ります。[データベース](../architecture/database.md)を参照してください。
- **エージェントスキルのストア** — `SKILLS_DIR` はキャッシュではなく永続的な状態です。ワークフロー実行は開始時のスキルのリビジョンに固定されます。[エージェントスキルストア](./configuration.md#agent-skill-store)を参照してください。
- **シークレットの暗号化キー** — 失うと、保存済みのローカルシークレットはすべて復号できなくなります。[シークレットの管理](./configuration.md#secret-management)を参照してください。
