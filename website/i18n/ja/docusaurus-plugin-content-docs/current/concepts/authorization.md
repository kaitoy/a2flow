# ロールと認可

ユーザーはそれぞれ**ロール**を持ち、実行できる操作がそれで決まります。ロール同士に**上下関係はありません**。例外が一つだけあります。**スーパー管理者はロールによるチェックをすべて素通り**します。そのため、ほかのどのロールとも**排他**です。あるユーザーはスーパー管理者であるか、残る 4 つのロールの組み合わせを持つかのどちらかで、両方ということはありません。この素通りには意図的な例外が 2 か所あり、いずれも所有者レベルのチェックです([人による承認](../guides/approvals.md#human-approval)を参照)。**ロールを一つも持たない**ユーザーも有効です。自分の[アカウント](../guides/users-and-groups.md#users)(アバター)は管理できますが、それ以外は何もできません。通常のチャット(`/sessions/*`)はスーパー管理者専用です(後述)。

ロールがユーザーに届く経路は 2 つあり、認可のチェックはすべてその**和集合**、つまりユーザーの**実効ロール**を見ます。

- **直接付与** — [ユーザー](../guides/users-and-groups.md#users)ページからユーザーレコードに付与します。
- **継承** — 所属する[ユーザーグループ](../guides/users-and-groups.md#user-groups)から受け取ります。グループにロールを割り当てると、メンバー全員がそれを得ます。

グループ経由でしか持っていないロールも、直接付与されたものとまったく同じ価値があります。同じゲートを通過し、承認者として指名できるようになり、なりすましからも同じように守られます。キャッシュは一切なく、和集合はリクエストのたびに解決するので、グループへの追加や削除は再同期の手順なしにその場で効きます。グループ自体を宛先にすることもできます。[承認](../guides/approvals.md#human-approval)は個人ではなくグループに送れて、`approver` を持つメンバーなら誰でも決裁できます。**グループが `super_admin` を付与することはできません**。UI に選択肢が出ず、API も拒否し(HTTP 422)、データベースの CHECK 制約が両方を裏打ちしています。スーパー管理者はプラットフォーム全体を対象とし、グループはちょうど 1 つのテナントに属するので、スーパー管理者がグループのメンバーになることもありません。

| ロール | 権限 |
|---|---|
| `super_admin` | すべて(ロールによるゲートをすべて素通りします。ただし[人による承認](../guides/approvals.md#human-approval)で説明する、指名された承認者のチェックは素通り**しません**) |
| `admin` | ユーザーの CRUD、シークレットの CRUD、自テナント内のすべてのワークフロー実行とそのタスク、チャット履歴、すべての承認への読み取り(後述の**ワークフロー実行へのアクセス**を参照。管理者は実行のエージェントを動かしたり、タスクを作成・編集・削除したり、実行を削除したり、承認を決裁したりはできません) |
| `developer` | シークレットの CRUD、MCP サーバーの CRUD、[ツールモック](../guides/tool-mocks.md)の CRUD、エージェントスキルの CRUD、ワークフローの生成・編集・公開・無効化(AI が生成した `generatedDescription` の再生成を含みます。ただしこのフィールドを直接編集できるのはスーパー管理者だけです)、タスクテンプレートの CRUD、設計セッションのチャット、ワークフローの実行(`POST /workflows/{id}/execute`。公開前テストのため `draft` のワークフローも実行できます) |
| `requester` | **公開済み**(および `modified`)のワークフローの実行(`POST /workflows/{id}/execute`) |
| `approver` | ワークフロー承認の指名先になれること(個人として、または承認の宛先となったグループのメンバーとして)と、自分宛の承認を決裁すること |

**読み取りは開いたままです。** ロールで制限されるのは書き込みとワークフロー実行と承認だけで、認証済みのユーザーなら誰でもコレクションを `GET` できます(名前の解決、承認者の選択、ワークフローの一覧表示に UI が必要とするためです)。シークレットの*値*は、ロールに関係なく API から返りません。ロールの割り当ては[ユーザー](../guides/users-and-groups.md#users)の管理ページから、まとめて割り当てる場合は[ユーザーグループ](../guides/users-and-groups.md#user-groups)のページから行います。`super_admin` を付与・剥奪できるのはスーパー管理者だけです。

拒否されたリクエストは HTTP 403(`FORBIDDEN`)を返し、管理画面はロールで許されない操作やナビゲーション項目を隠します。**一覧**ページでは、追加ボタンと行ごとの操作列(削除、および MCP サーバーの「レジストリを見る」。作成フォームに進むだけの導線です)が消えます。読み取りが開いているため、書き込み権限のない人が詳細ページを開くこともあります。その場合、エージェントスキル、MCP サーバー、ツールモック、シークレット、テナント、ユーザー、ワークフロー、タスクテンプレートはいずれも**読み取り専用**で描画されます。各フィールドは入力欄ではなく沈んだ表示の値になり、保存と削除は消え、キャンセルは戻るに変わります。シークレットのエントリはキーだけが並び(値はそもそも返りません)、ユーザーのパスワード欄は完全に省かれます。テナントの `name` やユーザーの `username` のように*誰にとっても*変更できないフィールドは、ロールに関係なく同じ見た目になります。**作成**フォームには読み取り専用の姿がないので、代わりにアクセス拒否の画面を返します。そこへ導く追加ボタンはすでに隠れているので、ロールなしで `/admin/<section>/new` に到達するのは直リンクの場合だけです。

初期投入される **`root`** ユーザーは `super_admin` を持ち、プラットフォーム全体を対象とします(テナントなし)。**Default** テナントに初期投入される **`admin`** ユーザーは `admin` を持ち、そのテナントに閉じます。それ以外のユーザーはロールなしから始まります。

**テナントとして振る舞う。** ほとんどのリソース(エージェントスキル、ワークフロー、シークレット、MCP サーバー、ワークフロー実行、チャットなど)はテナントに属しますが、プラットフォーム全体を対象とするスーパー管理者は自分のテナントを持ちません。そこでアプリのヘッダーに**テナント切り替え**があり(スーパー管理者にだけ表示されます)、どのテナントとして振る舞うかを選べます。選択は再読み込みをまたいで記憶され、管理画面もチャットも含めてどこにでも適用されます。テナントを選んでいない状態では、テナント単位のリクエストは HTTP 403 で拒否されます。テナントを切り替えても*ロール*は変わりません。どのテナントを選んでいても、スーパー管理者はロールのゲートを素通りします。

切り替えには**全テナント**という選択肢もあります。読み取り専用の管理一覧・詳細ページで、全テナントのデータを一度に閲覧できます(選択中は書き込みは拒否されたままです)。有効にすると、これらのページには**テナント**列やフィールドが増え、別テナントの行を区別できます。ワークフローの設計セッションのチャットと、ワークフロー実行のワークフローセッションのチャット(`GET /workflows/{id}/messages`、`GET /workflow-executions/{id}/messages`)にも届くので、スーパー管理者は他テナントのワークフローや実行を確認するときにその履歴も読めます。ただしそれらのチャットを動かすエージェントのエンドポイント(`POST .../agent`)には届きません。こちらは常に具体的なテナントを 1 つ選んでいる必要があります。

**ユーザーへのなりすまし。** スーパー管理者はプラットフォーム全体のどのユーザーとしても、管理者は自テナント内のどのユーザーとしても振る舞えます。`super_admin` を持つ相手には誰もなりすませません。`admin` を持つ相手になりすませるのはスーパー管理者だけです。通常の管理者は、そのロールが直接付与でもグループからの継承でも、同格の管理者にはなりすませません。これで、なりすましを使って自分が持っていない権限を得ることはできなくなります(スーパー管理者は管理者が通るゲートをすでに素通りしているので、管理者として振る舞っても新しく得るものはありません)。開始は[ユーザー](../guides/users-and-groups.md#users)一覧の**なりすまし**操作からです。実行中はヘッダーに「Acting as `<user>`」のチップが出て、ワンクリックで**停止**できます。

なりすまし中のリクエストは、読み取りも書き込みも、監査用の `createdBy` と `updatedBy` フィールドも、すべてなりすまし先のユーザーに帰属します。そのユーザー自身がサインインしている場合とまったく同じです。実際の操作者のセッションは下でそのまま保たれるので、停止するときに再度サインインする必要はありません。なりすましのセッションは、誰が誰にいつ、という形で監査証跡に永続的に記録されます。

**ワークフロー実行へのアクセス。** ロールとは別に、ワークフロー実行に対する各操作(読み取り、ワークフローセッションのチャット履歴の読み込み、タスクの一覧や編集、エージェントの駆動)には、呼び出し元がその実行の**開始者**(ワークフローを実行したユーザー)であるか、**その実行の承認のいずれかで指名された承認者**であることが必要です。指名された承認者とは、名指しされたユーザーか、承認の宛先となったグループのメンバーで `approver` を持つ人です([人による承認](../guides/approvals.md#human-approval)を参照)。無関係なユーザーには HTTP 403 が返ります。承認者がチャットを共有する設計(承認者が開始者のチャットに加わる)を保ちつつ、第三者を締め出すためです。

ただし**読み取り**はもう少し広くとってあります。レコードの読み取り、タスクの一覧(入れ子の一覧と個別タスクのページの両方)、チャット履歴の読み込みには、そのテナントの**管理者**も入れます。開始者でも承認者でもない管理者が、すべての実行を確認できるようにするためです。それでも管理者は、実行のエージェントを動かすことも、タスクを作成・更新・削除することも、実行自体を削除することもできません。同じ `GET /approvals` の一覧は、管理者にはテナント内のすべての承認を見せます。実行の**削除**はさらに厳しく、開始者(またはスーパー管理者)だけです。タスクの**ステータス**変更は、そのタスクに承認が紐づいている場合にさらに絞られます。その実行の承認者なら誰でもよいわけではなく、実行の開始者か、その承認で指名された承認者だけです([人による承認](../guides/approvals.md#human-approval)を参照)。ここでも管理者への例外はありません。

**プラットフォーム全体のセクション。** [テナント](../guides/users-and-groups.md#tenants)と[システム設定](../guides/system-settings.md)の 2 つは、**スーパー管理者**が自分のものとして抱えている管理セクションです。ほかと違って読み取りも制限されます。どちらもテナントのデータではなくプラットフォームレベルの設定を持つため、サイドバーの項目も、ウェルカム画面のカードも、背後のエンドポイントもすべて、ほかのロールには閉じています。

**チャットセッションへのアクセス。** 通常のチャット(`/sessions`、`/sessions/new`、`/sessions/{id}`、およびその背後の `POST /agent` と `GET|DELETE /sessions*`)は**スーパー管理者**に限定されています。それ以外には HTTP 403 が返り、ウェルカムページの「チャットを開始」カードは隠れ、スーパー管理者以外が直接そこへ移動しようとするとフロントエンドがアクセス拒否の画面を出します。以下の設計セッションとワークフローセッションのチャットとは別物で、そちらはそれぞれのアクセス規則のもとで開いています。

**設計セッションへのアクセス。** ワークフローの設計チャット(`GET /workflows/{id}/messages`、`POST /workflows/{id}/agent`)も共有されますが、レコードごとの参加関係ではなくロールで決まります。そのテナントの**開発者**なら誰でも読めて動かせるので、チームで設計を練り上げられます。スーパー管理者はいつもどおり通過し、ワークフローの `createdBy` は開発者ロールをあとから外されてもアクセスを保ちます。自分が始めたチャットから締め出される人が出ないようにするためです。それ以外には HTTP 403 が返ります。他テナントのワークフロー ID は 403 ではなく 404 になります。例外はスーパー管理者が**全テナント**を選んでいるときの `GET .../messages` で(上の「テナントとして振る舞う」を参照)、この場合ワークフローはテナントに関係なく解決され、いま説明したロールと作成者とスーパー管理者のチェックが、テナント境界の代わりを務めます。

⚠️ 承認者として適格かどうかは、承認を作成する時点で検証します。`list_users` と `list_user_groups` は実際に承認できる宛先しか返さず、`request_approval` はそれ以外を拒否します(適格なメンバーがいないグループも含みます)。*そのあと*どうなるかは宛先によって違い、この違いは意図したものです。

- **宛先がユーザーの場合** — あとから `approver` ロールを剥奪しても、すでにそのユーザー宛になっている承認は**無効になりません**。引き続き決裁できるので、進行中のワークフローが止まってしまうことはありません。
- **宛先がグループの場合** — 所属とロールを決裁時に再チェックします。「そのグループ」は固定の個人ではなく、動く集合だからです。だからこそ新しく加わったメンバーが保留中の依頼を拾えるのですが、逆にも働きます。グループから `approver` の付与を外したり、適格なメンバーが一人もいなくなったりすると、保留中の依頼は**誰にも決裁できなく**なり、その実行はいつまでも待ち続けます。ロールを付け直すか、メンバーを戻せば、すぐに解けます。
