# 用語

このドメインの大部分は 4 つの用語で説明できます。しかもそのうち 2 つはチャットです。区別しておく価値があります。

| 用語 | 何か | 保存先 |
|---|---|---|
| **ワークフロー** | 再利用できる、事前に設計された仕事の単位。エージェントスキルと、そこから生成されたタスクテンプレートの組。 | `workflows` |
| **設計セッション** | ワークフローのタスクテンプレートを作り、練り上げるチャット。ワークフロー 1 件につきちょうど 1 つあり、実行より先に存在します。 | 専用のテーブルはありません。`Workflow.sessionId` が指す ADK セッションなので、ワークフローの ID が識別子になります。 |
| **ワークフロー実行** | ワークフローの 1 回の実行。実行時点のワークフローとスキルのメタデータのスナップショットであり、その実行の `WorkflowTask`、`Approval`、メッセージメタデータの親になります。 | `workflow_executions` |
| **ワークフローセッション** | 1 件のワークフロー実行が行われるチャット。設計セッションの実行時版にあたります。 | 専用のテーブルはありません。`WorkflowExecution.session_id` が指す ADK セッションなので、実行の ID が識別子になります。 |
| **ユーザーグループ** | テナント内のユーザーをまとめた名前つきの束。所属メンバー全員がそのロールを継承します。 | `user_groups`(所属は `user_group_members`) |

つまり、設計セッションはワークフローを設計し、ワークフローセッションはワークフローを実行します。どちらのチャットもそれ自体は独立したエンティティではないため、所属するレコードで指し示します。設計セッションはワークフローで、ワークフローセッションは実行で指し、それぞれそのレコードの ID をそのまま自分のアドレスとして借ります。

ただし URL は分かれます。設計セッションは管理画面の中、`/admin/workflows/{workflowId}/design-session` にあり、そのワークフローのほかの管理画面と並びます。ワークフローセッションは管理画面の外、トップレベルの `/workflow-executions/{executionId}/session` にあり、実行の管理画面 `/admin/workflow-executions/{executionId}` とは別物です。

設計セッションの持ち主はワークフローの `createdBy`(生成したユーザー)で、ワークフローセッションの持ち主が実行の `initiatorId` であるのと同じです。どちらのチャットも**共有**されており、ADK セッションのキーをこの持ち主にしていることが共有を成り立たせています。入ってきた人は誰でも同じ 1 つの会話にたどり着き、自分専用のコピーに分岐しません。入れる人の条件は違います。設計セッションはそのテナントの開発者を、ワークフローセッションはその実行で指名された承認者を受け入れます。どちらも誰がどのメッセージを送ったかを記録するので、チャットには参加者それぞれのアバターが表示されます。
