# ワークフロー実行

ワークフロー実行は、[ワークフロー](./workflows.md)の 1 回の実行です。ワークフローの名前、説明、タスク、タグの写しを自分で持つので、元のワークフローがあとから編集されたり削除されたりしても、実行の履歴は実際に走った内容のまま残ります。

管理サイドバーの**ワークフロー実行**を開くと一覧できます。ほかのセクションと違い、実行は編集するレコードではなく履歴なので、編集フォームはありません。画面はどれも、実行の内容を見せるか、実行に参加させるためのものです。**タグ**の列とフィールドが読み取り専用なのも同じ理由からです。[ワークフロー実行と承認のタグ](./tags.md#execution-and-approval-tags)を参照してください。

| 画面 | たどり方 | 見えるもの |
|---|---|---|
| **ワークフロー実行**一覧 | 管理サイドバー → ワークフロー実行 | すべての実行とそのステータス、行ごとの操作 |
| **ワークフローセッション** | 行のワークフローセッションを開く | 実行が進むチャット。参加する、眺める、答える |
| **ワークフロータスク** | 行のタスクへのリンク | その実行のタスクとステータス。読み取り専用で表とグラフの 2 表示 |
| **ツールの呼び出し** | 実行の詳細ヘッダー | その実行が行った MCP ツール呼び出しと、それぞれの判定 |

**モック済み**は[ツールモック](./tool-mocks.md)でいずれかのツールを差し替えた実行を示します。

[**列**メニュー](./admin-ui.md#choosing-columns)には、既定で隠れている列がもう 2 つあります。**ワークフロー**はその実行のもとになったワークフローを今の名前で示し、そこへリンクします。行そのものの名前は実行開始時のスナップショットで固定なので、そのワークフローが今どう呼ばれているかはこの列で分かります。**下書き**は[テスト実行](./workflows.md#running-a-workflow) — `下書き` のままのワークフローから始めた実行か、`変更あり` のワークフローの[未公開の編集内容](./workflows.md#trying-the-edits-out)を実行したもの — にチェックマークを付けます。どちらも誰も承認していない設計を動かしたものなので、[運用メトリクス](../operations/metrics.md)には数えられません。この列は「はい」「いいえ」のフィルターとしても働くので隠せます。

実行の詳細ページには**バージョン**が表示されます。その実行がタスクを写したワークフローの公開版(`v3` など)です。テスト実行はどのバージョンにも記録されていない設計を動かしたので `—` になります。[バージョン履歴とロールバック](./workflows.md#version-history)も参照してください。

## 実行のステータス {#run-status}

![実行は「実行中」で始まり、時刻を待つだけの間は「予定」になって再開すると「実行中」に戻り、全タスクが終わって失敗がなければ「完了」、1 つ以上が失敗していれば「失敗」に落ち着くことを示す状態遷移図。](./img/workflow-executions-status.svg#gh-light-mode-only)
![実行は「実行中」で始まり、時刻を待つだけの間は「予定」になって再開すると「実行中」に戻り、全タスクが終わって失敗がなければ「完了」、1 つ以上が失敗していれば「失敗」に落ち着くことを示す状態遷移図。](./img/workflow-executions-status-dark.svg#gh-dark-mode-only)

実行は `実行中` で始まり、タスクが 1 つ以上あり、そのすべてが終端の状態 — `完了`、`失敗`、`スキップ` — に達した時点で確定します。失敗したタスクを含む実行は `失敗` で終わります。終了時刻はそのときに刻まれ、あとから編集しても動きません。タスクが 1 つもない実行は `実行中` のままです。[運用メトリクス](../operations/metrics.md)が数えるのはこの値です。

終わっていない実行が時刻を待つ以外に何もしていない間 — タスクが待機を求めてそのセッションが**予定(… まで)** と表示され、ほかのセッションがすべて**待機**か**完了**のとき — 実行は `実行中` ではなく `予定` と表示されます。時刻が来るか、誰かがメッセージを送ってセッションが再開すると、すぐに `実行中` に戻ります。[運用メトリクス](../operations/metrics.md)では、`予定` の実行も `実行中` と同じく進行中として数えます。

タスクが失敗すると、それを待っているタスク — 直接でも連鎖の先でも — はすべて `スキップ` になります。もう動けないからです。これが、決して始まらないタスクに引っかからず実行を確定させる仕組みです。失敗したタスクに依存していないブランチのタスクは影響を受けないので、失敗のあとも、それらが終わるまで実行が `実行中` のままということはあります。

## ワークフローセッション画面 {#the-workflow-session-screen}

ワークフローセッションは、1 回の実行が進むチャットです。開くと実行の開始メッセージが並び、エージェントはすでに作業を始めています。実行は作られた時点で始まるので、この画面を誰も開かなくても進みます。

![ワークフローセッションの画面レイアウトを示すフローチャート。タスクタイムラインと、タスクごとにまとまったメッセージが横に並び、メッセージの先にチャット入力がある。](./img/workflow-executions-layout.svg#gh-light-mode-only)
![ワークフローセッションの画面レイアウトを示すフローチャート。タスクタイムラインと、タスクごとにまとまったメッセージが横に並び、メッセージの先にチャット入力がある。](./img/workflow-executions-layout-dark.svg#gh-dark-mode-only)

### 誰と共有されるか {#who-shares-it}

実行のチャットは、始めた人だけのものではなく、**参加者で共有**されます。

| 誰 | 何ができるか |
|---|---|
| 実行を始めた**開始者** | 会話の全体と、チャット入力 |
| その実行の[承認](./approvals.md)の**指名された承認者** | 同じ会話と同じ状態。承認すると、空のセッションが新しく始まるのではなく、元の実行が再開します。承認者が操作できるのは自分の承認だけです。エージェントが他のステップのために描画した入力フォームや、[MCP サーバーが求める確認](#mcp-server-confirmations)は読み取り専用になり、その下に「開始者の応答を待っています。」と出ます |
| そのテナントの**管理者** | 読み取り専用での閲覧 |
| それ以外 | アクセスできません |

承認の宛先が**グループ**の場合、承認者ロールを持つメンバー全員が参加者になります。つまりチャットの参加範囲はグループのメンバーに追随します。承認者グループに人を加えると、そのグループが承認を求められているすべての実行が開き、外すとまた閉じます。「メンバーの誰が決めてもよい」ことの当然の帰結です。チャットへのアクセスは、判断できるようにするためにあります。承認者ロールを持たないメンバーは、所属していても何も得ません。

### 送信者のアバター {#sender-avatars}

1 つのチャットに複数の人 — 開始者、承認者、そしてエージェント — が書き込むので、どのメッセージにも**送信者のアバター**が付きます。マウスを乗せると送信者の名前が出ます。エージェントのバッジからはワークフロー名が出ます。描画された対話的な画面の中のボタンを押した場合も同じように扱われ、押した人のアバターがその画面の横に出ます。

### タスクタイムライン {#the-task-timeline}

左端には折りたためる**タスクタイムライン**があります。実行のタスクが順に並び、それぞれにステータス色の番号バッジが付き、進行中のものが強調されます。チャット側では、同じタスクに属する連続したメッセージが**タスクグループ**にまとめられます。ステータス色の縦線と、タイムラインのバッジと同じ番号の見出しが付くので、タスクの切れ目が一目で分かります。

2 つは双方向につながっています。

- チャットをスクロールすると、表示の先頭にあるタスクがタイムライン側で強調されます。
- タイムラインの項目かチャットのグループにマウスを乗せると、対応するもう一方が強調されます。
- タイムラインの項目をクリックすると、チャットがそのタスクのグループまでスクロールします。

### 自動更新 {#live-updates}

実行を見ている参加者は全員、返答が書かれていく様子をその場で見られます。誰のメッセージがきっかけでも同じで、キックオフ、承認後の再開、時刻を待っていたセッションの再開のように A2Flow が自分で動かすターンも含みます。返答が始まると（自分が送ったメッセージへの返答ならスクロール位置にかかわらず、ほかの人のメッセージへの返答なら下の方を見ているときに）、チャットは最新のメッセージが画面の一番上に来るまで一度だけスクロールし、返答はその下の空いたスペースに書かれていきます。書かれている間は、返答が画面の下からはみ出しても表示は動きません。返答中以外は、新しいメッセージを追って一番下までスクロールするのは、すでに下の方を見ているときだけです。上にスクロールして前のメッセージを読んでいる間は、自分でメッセージを送ったとき以外、どちらのスクロールも起きません。画面の下の見えないところに新しいメッセージが届いたときや、そこで返答が書き終わったときは、チャットの下部に **下に新しいメッセージがあります** ボタンが表示されます。クリックすると最新のメッセージまで移動し、返答がまだ書かれている途中なら、書き終わるまで表示が追いかけます。

送ったメッセージはエージェントを待ちます。エージェントがまだターンの作業中なら、そのメッセージは受け付けられないので、返答が終わってから送り直してください。承認を待っているセッションはメッセージを受け付けません。そのセッションを先へ進めるのは承認の判断だからです。その間に送った質問は、代わりに[相談セッション](#consultations)へ届きます。

[設計セッション](./workflows.md#adjusting-the-task-templates)も共有チャットで、アバターも同じです。ただし共有する相手は実行の参加者ではなくテナントの開発者で、ほかの人の返答は書かれていく様子ではなく、数秒ごとの自動更新で表示されます。

### ブランチセッション {#branch-sessions}

実行のタスクグラフが分岐すると、A2Flow はブランチが並んで進むよう、実行を複数のセッションに分けることがあります。詳しくは[並列ブランチ](../architecture/workflow-execution.md#parallel-branches)を参照してください。そのときはパンくずの下にセッションごとのタブが並び、それぞれにステータスが表示されます。

| タブ | 何か |
|---|---|
| **メイン** | 実行が始まったセッション。合流と、終わったブランチの後に続くタスクを進めます |
| **ブランチ 1**、**ブランチ 2**、… | ブランチセッション。ブランチの準備が整ったとき、担当セッションが手一杯だったためにフォークされたもの |
| **相談 1**、… | [相談セッション](#consultations)。セッションが承認を待っている間に質問したときに開いたもの |

| ステータス | 意味 |
|---|---|
| 待機中 | まもなくターンが始まる |
| 実行中 | エージェントが作業中 |
| 入力待ち | 入力フォームが回答を待っている |
| 承認待ち | このセッションが求めた承認がまだ判断されていない |
| 開始者待ち | 次のタスクが実行中に[開始者へ質問する](#mcp-server-confirmations)ので、開始者がチャットから再開するのを待っている |
| 予定(… まで) | タスクが時刻を待っている。表示の時刻になると自動で再開する。メッセージを送ると早めに再開する |
| 待機 | いまはやることがなく、次のタスクを待っている |
| 完了 | セッションの作業が終わった。終わったブランチはメインセッションへ要約を残す |
| エラー | 直前のターンが失敗した |

タブをクリックすると、そのセッションのチャットが開きます。選んだセッションは URL にも残るので、このページへのリンクを開くと同じタブが開きます。分岐せず、相談セッションもない実行にはタブは出ません。

### 相談セッション {#consultations}

承認を待っているセッションはメッセージを受け付けません。それでも、インスタンスの費用はいくらか、なぜこの対象を選んだのか、といった質問が出てくることはあります。セッションが承認を待っている間は、チャット入力欄の上に、質問は相談セッションへ届くという案内が出ます。

1. 承認を待っているセッションのチャットに質問を入力して送ります。
2. 質問の入った**相談**タブが開き、そこでエージェントが答えます。エージェントは承認依頼までに待機中のセッションが知っていたことをすべて引き継いで始まり、ワークフローにリンクされた[ナレッジベース](./knowledge-bases.md)も参照できます。MCP サーバーのツールは使えないので、対象のシステムを改めて調べる必要がある質問には、実行が先へ進むまで答えられません。
3. 続けて質問するときも、そのタブで送ります。チャットを共有している人は誰でも書き込めるので、承認者と実行を始めた人が依頼について話し合うこともできます。どのメッセージにも送った人が表示されます。
4. いつもどおり承認を判断します。判断すると相談セッションは閉じ、タブは**完了**になって、それ以上メッセージを受け付けなくなります。

| 相談セッション | |
|---|---|
| できること | 依頼までの文脈、リンクされたナレッジベース、実行のタスクと承認、セッションのファイルをもとに答える |
| できないこと | MCP サーバーのツールの使用、タスクの変更、承認の依頼、待機の予約、ファイルの追加 |
| 残るもの | 実行には何も残らない。待機中のセッションはそこで話した内容を見ない。会話自体はタブで読める |

同じ承認がまだ判断されていない間にした次の質問は、同じ相談セッションに届きます。

### 返答の候補 {#suggested-replies}

エージェントが質問したり、値や進行の許可を求めたりして返事待ちになると、チャット入力欄の上に**返答の候補**が並びます。`はい、進めてください` や `この手順は飛ばして` のような、エージェントが予想する短い返事です。

| | |
|---|---|
| **候補をクリックすると** | その文が入力欄に入ります。送信はされないので、書き換えてからでも、そのままでも送れます |
| **エージェントの作業中** | 候補は隠れます。次の質問と一緒にまた出てきます |
| **返事を送ると** | 候補は消え、次の質問には新しい候補が付きます |
| **リロードしても** | 同じ候補が出ます。送信できる参加者全員に見えます |

候補はエージェントが「こう打つだろう」と予想したもので、これしか答えられないという選択肢ではありません。答えが決まった数に限られる質問は、メッセージの中の選択肢として聞かれます。候補が出るのはワークフローセッションだけで、設計セッションにはありません。

### MCP サーバーからの確認 {#mcp-server-confirmations}

MCP サーバーの中には、ツール呼び出しの途中で止まり、先へ進む前に人に何かを尋ねるものがあります。たとえば Azure MCP Server は、Key Vault のシークレットに対する操作のたびに同意を求めます。こうしたツールには、ワークフローの設計で**開始者に質問する**という印を付けます。ワークフローを生成するとき、または設計セッションで、どのタスクのツールが質問してくるかを設計エージェントに伝えてください。印のないツールは質問できず、その呼び出しは待たずに失敗します。

印の付いたツールを使うタスクは、質問が来たときに開始者がその場にいるよう、始まる前に開始者を待ちます。

1. 実行がそのタスクに来ると、セッションは**開始者待ち**になり、開始者に 「入力の依頼」の[通知](./notifications.md)が届きます。この間、時間切れになるものはありません。
2. 開始者が実行のチャットを開くと、チャット入力の上にタスク名と**再開**ボタンが表示されます。他の人には、開始者を待っていることだけが表示されます。
3. **再開**を押すと開始者の名前でメッセージが送られ、タスクが始まります。開始者が自分でメッセージを書いて送っても同じです。
4. 質問はチャットに「*サーバー名* が確認を求めています」という見出しのカードとして現れ、待っているツール名と、小さなフォームが表示されます。

| | |
|---|---|
| **答えられる人** | 実行の開始者だけです。承認者や管理者には質問が表示され、その下に「開始者の応答を待っています。」と出ます |
| **承諾** | フォームの値を送ります。値の意味はサーバーが決めます。Azure MCP Server のフォームは **Approve** と **Reject** の選択です |
| **辞退** | 回答を断ります |
| **キャンセル** | 選ばずに質問を閉じます |
| **待っている間** | エージェントのターンはまだ実行中なので、チャット入力は使えません |
| **誰も答えない場合** | 質問は期限切れになります。既定では 15 分で、[環境で変えられます](../operations/configuration.md#mcp-tools-and-approvals)。サーバーには閉じられたものとして伝わります |

カードは質問したターンに属します。そのターンが終わったあとは、チャットに残るツール呼び出しの行が結果を記録します。

### セッションのファイル {#files-in-the-session}

ワークフローセッションはメッセージだけでなくファイルも持てます。チャット入力欄の横の**クリップ**ボタンから添付するか、入力欄のどこかにファイルをドロップしてください。添付したファイルは入力欄の上にチップとして並び、チップの × で取り消せます。送信するまで何も送られないので、チップを消せばそのファイルは実行に届きません。

送信したメッセージには添付したファイルの名前が入るので、リロードしても記録に残ります。エージェントにはサーバーの側から別途ファイルの一覧が伝わり、次のことができます。

| できること | できないこと |
|---|---|
| セッションのファイルを一覧する | 誰かが添付したファイルを書き換える |
| テキストであれば中身を読む | ファイルを削除する |
| 新しいファイルを追加する | ほかの実行のファイルに触れる |

エージェントが書いたファイルは、**ダウンロード**ボタンの付いたカードとしてチャットに現れます。エージェントは追加しかできないので、セッションにすでにある名前で書いた場合は上書きではなく番号付きの別名（`report (2).csv`）で保存され、カードには実際に保存された名前が出ます。

読めるのはテキストだけです。表計算ファイルや画像、アーカイブもそのまま保存・ダウンロードできますが、エージェントは中身を読めません。内容を渡したい場合はテキストに書き出したものを添付してください。

| | |
|---|---|
| **添付できる人** | 実行の開始者と、指名された承認者。実行を進められる人と同じです。見ているだけの管理者は添付できません |
| **ダウンロードできる人** | チャットを読める人すべて。管理者を含みます |
| **保持される期間** | 実行と同じ。実行を削除するとファイルも消えます |
| **サイズ上限** | デプロイごとの設定です。[設定](../operations/configuration.md#session-files)を参照してください |

送信したあとのファイルを 1 つずつ消すことはできません。セッションのファイルは実行と一緒に消えます。

## ワークフロータスク {#workflow-tasks}

実行のタスクはここでは読み取り専用です。テンプレートを編集するのは[ワークフロー](./workflows.md#adjusting-the-task-templates)の側で、実行のステータスを進めるのは実行エージェントと承認の流れだからです。

各タスクはステータス — `保留中`、`進行中`、`完了`、`失敗`、`スキップ` — と依存関係を持ちます。**表 / グラフ**の切り替えで一覧と依存グラフを行き来できます。グラフはタスクを依存順に縦 1 列に積み、先に終わるべきものを上に置き、それぞれが右へ、ツールを借りている MCP サーバー、さらに個々のツールへと枝分かれします。移動と拡大縮小、全体表示ができますが、編集はできません。

## ツールの呼び出し {#tool-invocations}

このページには、その実行で行われた MCP ツール呼び出しと、[ゲートウェイ](../architecture/mcp-gateway-and-proxy.md)が下した判定が並びます。上流に届いた `許可` と、規則に阻まれた `拒否` があり、ツール名、サーバー、拒否の理由、提示された[ツール証明書](./approvals.md#human-approval)が出ます。引数はダイジェストとしてのみ表示され、生の値は保存されません。

[モック](./tool-mocks.md)されたツールへの呼び出しは、結果がどうであれここには出ません。ゲートウェイはモックされた呼び出しもほかと同じように検査しますが、最初から保存済みのレスポンスで答えられる呼び出しはどのサーバーにも届かないので、その許可も拒否もこの記録には属しません。差し替えられた呼び出しを確認する場所は、実行のチャットの記録です。

## 実行を削除する {#deleting-a-run}

行の**削除**を押すと、確認のうえで実行が削除されます。レコード、そのタスク、そしてワークフローセッションが一緒に消えます。
