# 承認

承認は、実行を止めて人を待つための仕組みです。エージェントが実行の途中で承認を求め、指名された承認者がチャットで判断し、その判断がタスクのツールを解錠します。

## 人による承認 {#human-approval}

エージェントが動く前にユーザーの明示的な了解が必要なとき(たとえば破壊的な操作や取り消せない操作)、エージェントは実行の途中で**承認**を求めます。

1. エージェントはバックエンドの `request_approval` ツールを呼びます。これは現在のセッションに対して `pending` の **Approval** レコードを保存します(任意で `WorkflowTask` に紐づきます)。依頼の宛先は**ちょうど 1 つ**で、両方でも、どちらでもなくてもいけません。
   - **`approver`** — 特定のユーザー 1 人。`list_users` ツールで探します(このツールが返すのは [`approver` ロール](../concepts/authorization.md)を持つユーザーだけです)。通知が行くのもその人だけで、判断できるのもその人だけです。
   - **`approverGroupId`** — [ユーザーグループ](./users-and-groups.md#user-groups)。`list_user_groups` ツールで探します。`approver` を持つ**すべての**メンバーに、それぞれの承認依頼通知が届き、誰か 1 人の**最初の**判断で依頼が完了します。承認が 1 人の都合で止まらないようにするためです。承認できるメンバーが 1 人もいないグループは、決裁のしようがないので最初から拒否されます。誰かが判断しても、ほかのメンバーの通知が取り消されることはありません。単に操作できなくなるだけです。

   エージェントには、チームの誰が判断してもよい場面ではグループを優先し、スキルが特定の人物を求めている場合に個人を指名するよう指示してあります。
2. エージェントは依頼内容を平文で説明したうえで、**`render_approval`** を呼びます。これは AG-UI の**フロントエンドツール**です(クライアントが `RunAgentInput.tools` で宣言するもので、A2UI とは別物です)。`render_a2ui` と同じく、ブリッジはこれを長時間実行のクライアントツールとして公開します。実行が一時停止し、フロントエンドがチャットに**承認/却下**の操作と、任意の**コメント**欄を描画します。この操作が見えるのは**指名された承認者だけ**です。宛先がグループなら `approver` を持つメンバー全員に見えるので、複数人が同時に持つこともあります。それ以外の人には読み取り専用の「待機中」のメッセージが出ます。
3. ボタンを押すと、判断(とコメント)が `PATCH /api/v1/approvals/{id}` でバックエンドに**直接**書き込まれ、その判断がツールの結果として返って、エージェントの実行が再開します。決裁したユーザーは監査フィールドと、サーバーが管理する専用の **`decidedBy`** の両方に記録されます。宛先がグループのときに「誰が承認したのか」に答えるのはこの `decidedBy` です。グループ名だけでは分かりません。依頼を決裁できるのは指名された承認者だけで、**例外はありません。宛先でないスーパー管理者でも同じです**。ほかのユーザーからの `PATCH` は HTTP 403(`FORBIDDEN`)で拒否されます。判断は**確定**です。承認グループのメンバー 2 人が本当に競合しうるので、すでに記録されたステータスを*変えよう*とする 2 回目の `PATCH` は、最初の判断を上書きせず HTTP 409(`APPROVAL_ALREADY_RESOLVED`)で拒否されます。あとからコメントを編集することは引き続きでき、`decidedAt` も `decidedBy` も動きません。
4. `approved` ならエージェントは先へ進みます。`rejected` ならタスクを `failed`(または `skipped`)にします。エージェントは `get_approval` ツールで判断を確認し直せます。
5. 承認を与えると、そのタスクに対して**証明書が発行**されます。MCP ツールを実際に解錠するのはこの証明書です(後述)。

**承認のゲートを強制するのはサーバーであって、エージェントではありません。** 承認が紐づいたタスクは、その承認が下りるまで、割り当てられた [MCP ツール](./mcp-servers.md)を 1 つも呼べません。MCP プロキシが呼び出しを拒否します。承認が下りると短命な X.509 証明書が発行され、それ以降そのタスクからのツール呼び出しは、署名つきでこの証明書を提示しなければ拒否されます。承認が紐づいていないタスクは影響を受けず、通常のツール割り当ての規則のまま動きます。

モデルへの指示ではできなかったことが 2 つ手に入ります。

- **プロンプトインジェクションやバグで承認を飛ばせません。** 以前のゲートはエージェントのシステム指示と、フロントエンドが実行の再開を断ることの組み合わせでした。どちらもサーバーが確認する規則ではありません。
- **許可されたツールは判断の瞬間に凍結されます。** 証明書は、承認者が承認を押した時点でそのタスクに割り当てられていたツールを持ちます。エージェントは実行中に自分のタスクのツール割り当てを書き換えられるので、呼び出し時に割り当てを読むチェックはエージェントが広げられるチェックです。証明書に署名し直すことはできません。ファイルを読むことを承認したものが、ファイルを削除する承認に化けることはありません。

判断されたツール呼び出しは、許可も拒否も、証明書のシリアルと、そのために署名された正確なバイト列とともに記録されます。「どの承認がこれを許可し、誰が与えたのか」にあとから答えられ、暗号的に検証もできます。

署名のルート証明書は最初の使用時に生成され、暗号化して保存されます。設定は要りません。証明書の有効期間(既定 1 時間)と時計のずれの許容幅は、`MCP_APPROVAL_CERT_TTL_SECONDS` と `MCP_APPROVAL_CERT_SIGNATURE_WINDOW_SECONDS` で調整できます。`GET /api/v1/approvals/{id}/certificate` と[承認](./approvals.md#browsing-approvals)の管理詳細ページは、その承認が何を許可したのかを示します。許可されたツール、有効期間、証明書が失効しているかどうかです。設計と実装のメモは [backend/README.md](https://github.com/kaitoy/a2flow/blob/master/backend/README.md#approval-certificates) にあります。

> **この保証の範囲。** MCP プロキシは現在バックエンドのプロセス内で動くので、署名が証明するのは、同じプロセスを共有する検証者に対して証明書の鍵を持っていることです。すでにバックエンドを掌握した攻撃者への防御ではありません。得られるのは、フェイルクローズな強制点が 1 か所にまとまること、あとから広げられない許可、そして検証できる記録です。証明書は `clientAuth` を持つので、プロキシをネットワーク越しに切り出すことになっても、同じ材料がそのまま本物の TLS クライアント認証になります。

承認は `a2flow.db` に保存され、`WorkflowExecution` と一緒にカスケードで削除されます(任意の `WorkflowTask` へのリンクは、そのタスクが削除されると `NULL` になります)。一覧は[承認](./approvals.md#browsing-approvals)の管理画面で見られます。

例外なしの規則は、紐づいたタスクの**ステータス**にも及びます。`WorkflowTask` の `status` をいきなり `completed` にできてしまうと、そのセッションの承認者なら誰でも宛先の代わりを務められることになるので、`PATCH /api/v1/workflow-tasks/{id}` は `status` の変更をセッションの持ち主か、タスクに `Approval` が紐づいている場合はその適格な承認者(名指しされたユーザー、またはその承認グループのメンバーで `approver` を持つ人)に限定します。承認が紐づいていないタスクは、これまでどおりセッションの参加者なら誰でも、という広い規則のままです。

**ワークフローセッション**(実行が行われる ADK のチャット)のキーは、いま見ている人ではなく、その実行の**開始者**(実行を始めたユーザー)です。そのため、指名された承認者という別のユーザーが開いても、**同じ** ADK セッションを共有します。開始者の会話と状態がそのまま見えて、承認すると新しい空のセッションを始めるのではなく元の実行が再開します。エージェントのストリーム(`POST /workflow-executions/{id}/agent`)も履歴の読み込み(`GET /workflow-executions/{id}/messages`)も、`WorkflowExecution` レコードから開始者を解決します。(ワークフローではない通常のチャットセッションは、これまでどおりユーザーごとのキーです。)共有はこの参加者に限られ、それ以外のユーザーは HTTP 403 で拒否されます([ロールと認可](../concepts/authorization.md)を参照)。

承認の宛先がグループの場合、`approver` を持つメンバー全員がこの参加者にあたるので、共有チャットはグループの所属に追従します。承認グループに誰かを加えると、そのグループが承認を求められているすべての実行が開き、外すと次のリクエストから閉じます。「どのメンバーでも決裁できる」ことの直接の帰結です。チャットへのアクセスは決裁のために存在しているからです。`approver` を持た*ない*メンバーは、所属から何も得ません。

この 1 つのチャットが共有されるため、複数の人(**申請者**である開始者、指名された**承認者**、そして**エージェント**)が書き込みます。そこで各メッセージには誰が送ったかを示す**送信者アバター**が付きます。申請者や承認者のメッセージの横にはその人のアバターが、エージェントのメッセージの横にはエージェントのバッジが出ます(マウスを乗せるとワークフロー名が出ます)。描画された A2UI のサーフェス内でボタンを押した場合も同じように帰属し、解決され次第、そのサーフェスの横に操作した人のアバターが出ます。

ADK は人間のメッセージをすべて `user` という作成者で記録し、A2UI の操作の確認応答はツールレスポンス(function-response)イベントとして記録します。そのためバックエンドは両方を実際の送信者に帰属させます。エージェント実行のエンドポイントが、ワークフローセッションの既存の `user` イベントとツールレスポンスの `tool_call_id` をスナップショットしておき、実行が終わった時点で新しく増えたぶんの送信者として現在のユーザーを記録します。`GET /workflow-executions/{id}/messages` は各メッセージの `senderUserId` を返します。うまく終わらなかった実行も同じです。ストリームの途中でクライアントが切断すると(タブを閉じた、ページを再読み込みした)実行はキャンセルされますが、すでに追加されたメッセージは終了処理の中で帰属され、持ち主なしのまま放置されません。ツールレスポンスのメッセージは自分の ID ではなく `tool_call_id` をキーにします。AG-UI と ADK のブリッジが、読み取るたびに新しい ID を振り直すためです。送信者が記録されていないメッセージ(帰属の仕組みができる前の履歴)は開始者にフォールバックします。アバターにマウスを乗せると送信者の名前が出ます。

このようなメッセージごとの付帯情報は、1 つの **`message_meta`** テーブルにまとめてあります。実行完了時の処理が、null 可能な列をそれぞれ独立に upsert します。現在あるのは `sender_user_id`(上記)と `workflow_task_id`(後述)です。1 行はどのチャットに属するかを、`workflow_execution_id`(ワークフローセッション)か `workflow_id`(**設計セッション**。こちらもテナントの開発者で共有され、同じように帰属します。[タスクテンプレートを調整する](./workflows.md#adjusting-the-task-templates)を参照)のちょうど一方で示し、それぞれ `adk_event_id` との組で一意になります。

チャットが共有されているため、ページは **10 秒ごとに `GET /workflow-executions/{id}/messages` をポーリング**します。参加者が再読み込みなしでほかの人のメッセージ(とエージェントの進捗)を見られるようにするためです。閲覧者自身のエージェント実行が進行中のあいだはポーリングを止め(ライブのストリームを壊さないためです)、変化のない履歴の再適用は飛ばします。新しいメッセージに合わせて一番下まで追従するのは、閲覧者がすでに下端近くにいるときだけです。

チャット画面の左端には、折りたためる**タスクタイムライン**も出ます。実行の `WorkflowTask` が順に並び、それぞれに番号とステータス色のバッジが付き、進行中のタスクが強調されます。エージェントはタスクに取りかかる前に `update_workflow_task(status="in_progress")` を呼んでライフサイクルを進めるので、実行のたびにバックエンドがワークフローセッションのイベントを順にたどり、直近のこの遷移を追跡して、それ以降の各メッセージの `workflow_task_id` として進行中のタスクを記録します。`GET /workflow-executions/{id}/messages` は各メッセージの `workflowTaskId` を返し、チャットは同じタスクの連続したメッセージを**タスクグループ**でまとめます。ステータス色の左レールと、タイムラインのバッジと同じ番号の見出しが付くので、各タスクの区切りが一目で分かります。タイムラインとチャットは双方向につながっています。チャットをスクロールすると、画面上端にあるタスクがタイムラインで強調され(スクロールスパイ)、タイムラインの項目かチャットのグループにマウスを乗せると対応するもう一方が強調され、タイムラインの項目をクリックするとチャットがそのタスクのグループまでスクロールします。

## 承認を閲覧する {#browsing-approvals}

[http://localhost:3000/admin/approvals](http://localhost:3000/admin/approvals) ですべての **Approval** 依頼を閲覧できます([人による承認](./approvals.md#human-approval)を参照)。既定の一覧に出るのは、タイトル、元になった**ワークフロー実行**の管理詳細ページへのリンク(名前は実行から解決し、解決できるまでは生の ID を出します)、ステータス(`pending` / `approved` / `rejected` / `returned`)、説明、作成日時で、並べ替えと絞り込みの操作が付きます。指名された承認者(ユーザー名か、管理ページへリンクした**承認グループ**の名前)、実際に判断した人(`Decided By`)、承認者のコメント、判断の日時は既定では隠れていますが、列ピッカーから出せます。

各行の操作列には**ワークフローセッションを開く**ボタンもあります。[ワークフロー実行](./workflow-executions.md)の一覧にあるものと同じで、`/workflow-executions/{id}/session` へ直接移動します。判断は普通、チャット内の承認/却下/差し戻しの操作から行います。この画面は読み取り専用の閲覧用です。承認済みの依頼の詳細ページには、その証明書が持つ**許可された MCP ツール**が、証明書のシリアル、有効期間、失効状態とともに出ます([人による承認](./approvals.md#human-approval)を参照)。`GET` と `PATCH /api/v1/approvals` のエンドポイントは [API リファレンス](http://localhost:3000/api-doc)に記載しています。

**`returned`** は承認と却下に並ぶ 3 つ目の判断です。依頼を決着させるのではなく、修正して出し直すよう仕事を差し戻します。差し戻しの比率が高ければ、そもそも依頼すべきでなかったというより、上流の品質に問題があることを示します。どの判断が記録される場合でも、`pending` から抜ける遷移でサーバー管理の **`decidedAt`** が打たれます。あとからコメントを編集してもこれは動かないので、`createdAt` から `decidedAt` までの所要時間は承認者の実際の時間のままです。
