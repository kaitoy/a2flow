# エージェントスキル

[http://localhost:3000/admin/agent-skills](http://localhost:3000/admin/agent-skills) でエージェントスキルのレジストリを管理します。Git リポジトリに置かれた AI エージェントのスキルのカタログです。

| 操作 | パス |
|-----------|------|
| スキルの一覧 | `GET /admin/agent-skills` |
| スキルの新規登録 | `GET /admin/agent-skills/new` |
| スキルの詳細ページ(編集・削除) | `GET /admin/agent-skills/{id}` |
| スキルからワークフローを生成 | 一覧の操作列の「ワークフローを生成」、または詳細ページのヘッダーにあるワークフロー生成のアイコンボタン([ワークフローを生成する](./workflows.md#generating-a-workflow)を参照) |
| スキルのリポジトリを pull | `POST /api/v1/agent-skills/{id}/pull` |

スキルは SQLite のデータベース(既定では `a2flow.db`。`backend/.env` の `DB_URL` で変更できます)に保存されます。各レコードには、スキル名、リポジトリ URL、リポジトリ内のパス、任意の **Ref**(ブランチ名またはタグ名)、説明、そして分類に使う[タグ](./tags.md)が入ります。

## スキルストア

スキルを登録するとその場で応答が返り、リポジトリの**シャロークローンがバックグラウンドで**走ります。使うのは [Dulwich](https://www.dulwich.io/) なので、外部の `git` コマンドは不要です。クローンは `SKILLS_DIR` の下のスキルストアへ、リビジョンごとに 1 つの不変ディレクトリとして公開されます。

```
$SKILLS_DIR/<agent_skill_id>/<commit_sha>/
```

クローンは一時的な隣のディレクトリに用意してから、1 回のアトミックな rename で所定の位置に移します。そのため、ストアを読んでいるレプリカが書きかけのリビジョンを見ることはありません。公開されたリビジョンはその後**一切変更されません**。pull は隣に足すだけです。

一覧と詳細ページには、各スキルの**ステータス**(`Cloning` / `ready` / `failed`。失敗時は理由つき)と、公開している短い**リビジョン**が出ます。この状態は 2 つのフィールドが担っていて、意味が違います。

- **`commitSha`** — 公開されているリビジョンです。スキルが実行可能になるのは、これが設定されて**から**です。リビジョンのないスキルに対してワークフローを開始しようとすると HTTP 409(`SKILL_NOT_READY`)で拒否されます。
- **`syncStatus`** — *直近の*クローンまたは pull がどうだったかです。pull が失敗しても `commitSha` は**消えません**。動いていたスキルは前のリビジョンのまま動き続け、変わるのはステータスとエラーだけです。

**pull** は、設定した **Ref**(未設定なら既定ブランチ)でリポジトリをクローンし直します。スキルが上流の変更を取り込む手段であり、登録時のクローンが失敗したあと URL や認証情報を直して再試行する手段でもあります。**Ref**(ブランチ名またはタグ名)を設定すると、クローンも pull もリポジトリの既定ブランチではなくその ref に固定されます。ブランチの先端が動いたり、タグが張り直されたりしたときは、次にスキルを同期したタイミングで取り込まれます。1 つのスキルに対する同時クローンは、`backend/infrastructure/locks.py` のアドバイザリロックによってレプリカをまたいで直列化されます。ほかのレプリカがすでにクローン中だと分かったレプリカは、同じ作業を重ねず処理を飛ばします。pull が成功すると、どのワークフロー実行からも参照されなくなったリビジョンが削除されます。

`docker compose` では `SKILLS_DIR` は `/var/lib/a2flow/skills` で、`skills` という Docker ボリュームに永続化されるので、コンテナを作り直してもストアは残ります。これは**キャッシュではなく永続的な状態**です。ワークフロー実行は開始時のリビジョンに固定されるため、このディレクトリを消すと、既存の実行は管理者がもう一度 pull するまでスキルを読み込めなくなります。バックエンドを 2 レプリカ以上にする場合は、すべてのレプリカが同じボリュームをマウントする必要があります。

プライベートリポジトリには、任意の**認証パスワード**フィールドで対応します。値を打ち込むのではなく、登録済みの[シークレット](./secrets.md)と、その中の**エントリキー**を 2 つのドロップダウンから選びます。リポジトリのクローン時に、そのエントリの値が HTTP ベーシック認証のパスワード(通常はパーソナルアクセストークン)として使われます。どちらの種類のシークレットも選べます。`vault` タイプのシークレットのエントリキーは、ローカルに保存されていないので KV v2 のパスからその場で読みます。**認証ユーザー名**フィールドの既定値は `x-access-token` です(GitHub の PAT に適した値です)。実際のアカウント名を要求するホストでは明示的に設定してください。

シークレットは `name/key` の参照として保存され、クローン時に解決されます。そのためあとから削除したり名前を変えたりすると、次の pull が失敗し、理由がスキルに記録されます。詳細ページはそうした古い参照を黙って落としません。`(not found)` の印と警告を付けたまま選択された状態で残るので、消すかどうかは自分で決められます。
