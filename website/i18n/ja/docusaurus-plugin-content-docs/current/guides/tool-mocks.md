# ツールモック

[http://localhost:3000/admin/mcp-tool-mocks](http://localhost:3000/admin/mcp-tool-mocks) で**ツールモック**を管理します。**下書き**のワークフローを、ツールの副作用なしに端から端まで動かすための代役です。モックされたツールは呼ばれません。代わりにモックに設定した結果が返るので、MCP サーバーへのリクエストは飛ばず、承認も記録されず、誰にもメールは届きません。

モックにするかどうかは実行単位ではなく**ツール単位**で選びます。リハーサルは現実的であってこそ役に立つからです。あるシステムを検索してから書き込むワークフローなら、書き込みだけを差し替えられます。読み取りは本物のサーバーに当たり続けるので、エージェントは実データをもとに考えます。同じ理由で、モックが省くのは副作用だけで、規則は省きません。モックされた MCP 呼び出しも、その実行の現在のタスクが使ってよいツールかどうか、そのタスクが待っている承認があるかどうかを確認されます。本番で拒否されるワークフローは、リハーサルでも拒否されます。

モックの対象は、[登録済みの MCP サーバー](./mcp-servers.md)のツール 1 つか、A2Flow の**組み込み**ツールです(組み込みは今のところ `request_approval` だけです。副作用を消さない限り、実行を続けるのに人の対応が要るツールだからです)。

**レスポンス**は呼び出しの回数で引く順序つきのリストです。1 つ目がそのツールへの最初の呼び出しに、2 つ目が 2 回目に対応し、以下同様です。リストを使い切ると最後のレスポンスが繰り返されるので、レスポンスが 1 つだけなら定数のように振る舞います。これがあるおかげで、モック 1 つで固定値ではなくシナリオを表現できます。最初の依頼は承認して 2 番目は却下し、ワークフローが両方をどう扱うかを見る、といった具合です。各レスポンスは次のいずれかです。

| 種類 | 意味 |
|---|---|
| `structured` | 結果の `structuredContent` に置く JSON オブジェクト。呼び出し側が結果からフィールドを読むツール向けです |
| `text` | 結果のテキスト部分に置く文字列 |
| `error` | 失敗した呼び出しとして返すメッセージ。エージェントからはツールがエラーを報告したように見えます |

モックは、下書きワークフローの**実行ダイアログでチェックする**ことで適用されます([ワークフローを実行する](./workflows.md#running-a-workflow)を参照)。公開済みのワークフローではダイアログにモックは出ません。実行を開始すると、選んだ各モックのその時点の内容が実行へ**コピー**されます。そのため、あとからモックを編集したり削除したりしても、すでに動いている実行が変わることはありません。差し替えられていた呼び出しが黙って本物に戻ることも起きません。

モックされた呼び出しが何を送って何を返したかは、実行のチャットの記録で確認できます。ツールの行を展開すると引数と結果が出て、**モック済み**のバッジが付きます。実行の[ツール呼び出し](./workflow-executions.md)のページには意図的に出しません。あのページは MCP プロキシが実際に下した判断を記録するもので、差し替えられた呼び出しはそこまで届かないからです。

モックされた `request_approval` も宛先の検証は行います。モックが省くのは副作用であってチェックではありません。そのため、承認者として適格でない相手を指定したワークフローは、本番と同じようにリハーサルでも失敗します。

| 操作 | パス |
|-----------|------|
| ツールモックの一覧 | `GET /admin/mcp-tool-mocks` |
| ツールモックの作成 | `GET /admin/mcp-tool-mocks/new` |
| ツールモックの編集・削除 | `GET /admin/mcp-tool-mocks/{id}` |
