# ワークフロー

[http://localhost:3000/admin/workflows](http://localhost:3000/admin/workflows) でワークフローを管理します。ワークフローは再利用できる仕事の単位で、エージェントスキルと**事前に設計されたタスク一覧**(そのワークフローの*タスクテンプレート*)を組にしたものです。ライフサイクルは**生成 → 調整 → 公開 → 実行**です。タスクテンプレートは実行より*前*に設計して固めるので、ワークフローを実行すると毎回設計し直すことなくすぐ作業に入ります。

| 操作 | パス |
|-----------|------|
| スキルからワークフローを生成 | [エージェントスキル](./agent-skills.md)の「ワークフローを生成」(一覧の行操作、または詳細ページのヘッダーのアイコンボタン。どちらも `POST /agent-skills/{id}/workflows` を呼びます) |
| ワークフロー一覧 | `GET /admin/workflows` |
| ワークフローの詳細ページ(編集・公開・無効化・変更の破棄・設計セッションを開く) | `GET /admin/workflows/{id}` |
| タスクテンプレートの管理 | `GET /admin/workflows/{id}/task-templates` |
| ワークフローの実行 | 一覧の「実行」ボタン(`POST /workflows/{id}/execute` を呼びます) |

ワークフローのレコードには、名前、分類に使う[タグ](./tags.md)、エージェントスキルへの参照、ライフサイクルの**ステータス**(`generating` / `draft` / `failed` / `published` / `modified`)、そして 2 つの説明フィールドが入ります。`generatedDescription` は、ワークフローの生成時と、`developer` がこのフィールドの**生成アクション**を押すたびに、AI が**設計の会話から要約**したものです。直接編集できるのは**スーパー管理者**だけです。もう一方の `description` は自由入力で、どの `developer` でも上書きとして設定できます。空でないほう(`description` が優先、なければ `generatedDescription`)が実行時の文脈として実行エージェントに渡ります。

上書きは AI の要約に手を入れたものになるのが普通なので、詳細ページの説明フィールドには**差分アクション**があり、`generatedDescription` から `description` への単語単位の差分をダイアログで表示します。読むのはフォームの現在値なので、未保存の編集も差分に含まれます。ワークフローは `a2flow.db` に保存されます。素の `POST /workflows` はありません。ワークフローが生まれる道は生成だけです。

## ワークフローを生成する {#generating-a-workflow}

**ワークフローを生成**は 2 か所から開けます。どちらもページを離れずに同じモーダルダイアログを開きます。[エージェントスキル](./agent-skills.md)一覧の行操作と、スキル詳細ページのヘッダーにあるワークフロー生成のアイコンボタンです。スキルの clone がリビジョンを公開するまで、どちらも無効です。ダイアログではワークフローの**名前**(スキル名が初期値として入ります)と、仕事内容を書く**プロンプト**を尋ねます。生成すると新しいワークフローへ移動してしまうので、詳細ページは先に未保存の編集を保存するか確認します。ここで断ればページはそのままで、生成も行われません。

ダイアログを送信すると、次のことが起こります。

1. スキルに公開済みのリビジョン(`commitSha`)があるかを確認します。なければ HTTP 409(`SKILL_NOT_READY`)です。新しいワークフロー(`status: "generating"`)がその場で登録され(HTTP 201)、設計に使う**設計セッション**の ID を持ち、そのリビジョンに固定されます。フロントエンドはワークフローの詳細ページへ移動し、生成中はポーリングします。
2. **バックグラウンドの設計実行**が、プロンプトを設計セッションの最初のチャットメッセージとして送り、*初期設計*エージェントを動かします。エージェントはスキルに従って依頼を手順に分解し、1 回の `register_design_tasks` 呼び出しでワークフローの**タスクテンプレート**として登録します(DAG です。各手順は `key` と、先行する `depends_on` を宣言し、任意で MCP の `tools` の割り当ても持ちます)。
3. 実行が終わると、設計の会話が要約されて(LLM 呼び出し 1 回)ワークフローの `generatedDescription` になり、ステータスが **`draft`** に変わり、**ワークフローの下書き完了通知**がそのワークフローへのリンクとともに上がります。失敗した場合(LLM のエラー、またはテンプレートを 1 つも登録しなかった実行)は、行に理由つきの **`failed`** が付き、**ワークフロー生成失敗の通知**が上がります。理由はワークフローの詳細ページと、設計チャットのバナーに表示されます。設計チャットは使える状態のままです。そこから(または管理画面のテンプレートエディタから)タスクテンプレートを書けば、ワークフローは **`draft`** に戻り、失敗の記録も消えます。設計を作り直すことが修復にあたるからです。

プロンプト自体はワークフローには保存されません。設計の会話の最初のメッセージとして残り、生成された要約が意図を先へ運びます。

## 説明を再生成する {#regenerating-the-description}

タスクテンプレートを調整していくと AI の要約は古くなります。そこでワークフロー詳細ページの**生成された説明**フィールドには**生成アクション**があり(`POST /workflows/{id}/generate-description`、developer 限定)、求めに応じて設計の会話を要約し直して(LLM 呼び出し 1 回)、結果をそのまま保存します。公開時に自動で要約することはありません。要約をいつ更新するかはユーザーが決めます。

同じ操作は設計セッションのチャット入力欄からも使えます。「+」メニュー(developer 限定。ワークフローのタスクテンプレートを生成中は隠れます)に**説明を生成**があり、保存前に詳細ページと同じ説明差分ダイアログで変更をプレビューします。会話から離れずに再生成したいときに便利です。

`published` のワークフローは、要約が書き換わると `modified` になります。`description` が空の実行はこちらにフォールバックするので、そのままだと公開済みのバージョンから中身がずれてしまうためです。生成中や、要約する設計の会話がない場合は HTTP 409(`WORKFLOW_DESCRIPTION_NOT_GENERATABLE`)を、LLM の呼び出しが失敗した場合は HTTP 502(`SUMMARIZATION_FAILED`)を返します。

## タスクテンプレートを調整する {#adjusting-the-task-templates}

下書きのタスクテンプレートは 2 つのやり方で練り上げられます。混ぜて使ってもかまいません。

- **チャットで** — ワークフロー詳細ページの**設計セッションを開く**ボタンが `/admin/workflows/{workflowId}/design-session` を開きます(チャットは自分の ID を持たないので、ワークフローで指し示します)。実行時と同じチャット UI で、左端にテンプレートの一覧が並びます。動かすのは対話型の*設計*エージェントで、そのツール(`register_design_tasks`、`create_design_task`、`list_design_tasks`、`get_design_task`、`update_design_task`、`delete_design_task`)がワークフローのテンプレートを直接編集します。設計エージェントが何かを実行することはありません。設計セッションはそのテナントの**開発者**全員(に加えてスーパー管理者とワークフローの `createdBy`)で共有されるので、チームで一緒に設計を練れます。共有チャットの仕組み(履歴のポーリング、A2UI のサーフェス、メッセージごとの送信者アバター)をそのまま使い、2 人が同時に送信するとワークフローセッションと同じ実行ロックで衝突します。
- **手作業で** — **タスクテンプレート**の管理ページ(`/admin/workflows/{id}/task-templates`)には、おなじみのテーブル表示とグラフ表示があります(グラフは依存順にテンプレートを 1 列に縦に積み、そこから右へ、ツールを取る MCP サーバー、さらに個々のツールへと枝分かれします)。加えて作成フォームと、**依存先**と **MCP ツール**のピッカーを持つテンプレートごとの詳細ページがあります。裏では `GET /workflows/{id}/task-templates` と `POST`/`PATCH`/`DELETE /workflow-task-templates`(developer 限定)を使います。

テンプレートの構造はセッションのタスクと同じで、タイトル、説明、DAG の辺(`workflow_task_template_dependencies`)、MCP ツールの割り当て(`workflow_task_template_tool_bindings`、サーバー側は `RESTRICT`)を持ちます。ただし**ステータスは持ちません**。ライフサイクルは設計ではなく実行のものだからです。DAG の規則は同じです(参照先は同じワークフロー内であること、循環は HTTP 409 `DEPENDENCY_CYCLE` で拒否)。

## 公開する

**公開**(ワークフロー詳細ページ、`POST /workflows/{id}/publish`、developer 限定)がワークフローを実行可能にします。テンプレートが 1 つ以上あり、生成が進行中でないことが必要です。そうでなければ HTTP 409(`WORKFLOW_NOT_RUNNABLE`)です。公開は**設計を凍結**します。ワークフローの名前、実効的な説明(`description` があればそれ、なければ `generatedDescription`)、テンプレート一覧全体(辺とツールの割り当てを含みます)が公開バージョンとして取り込まれ、前のものを置き換えます。ここで LLM は動きません。AI の要約を更新するのは[ユーザーが自分で起こす別の操作](./workflows.md#regenerating-the-description)です。調整して公開し直すことはいつでもできます。すでに始まっている実行はタスクテンプレートをコピー済みなので影響を受けません(後述)。

## 公開後の編集と `modified`

公開したあとにワークフローを編集しても、実行される内容が黙って変わることはありません。詳細フォームの保存、AI 説明の再生成、**タスクテンプレート**の追加・編集・削除のいずれかを行うと、ワークフローは **`modified`** に移ります。

- 実行は編集後ではなく、**最後に公開したバージョン**(その名前、実効的な説明、テンプレート)を使い続けます。
- `published` のときに実行できた人は引き続き実行できます。一覧の実行ボタンのゲートは変わりません。
- 編集を今後の実行に反映するには、もう一度**公開**します。
- **変更を破棄**(詳細ページのステータスバーで公開の隣に現れる元に戻すアイコン、`POST /workflows/{id}/discard-changes`、developer 限定)は編集を捨てます。タスクテンプレートは公開バージョンから書き直され(元のテンプレート ID を再利用するので依存の辺は残ります)、名前は復元され、公開バージョンで凍結された実効的な説明がワークフローの `description` フィールドに書き戻されます(`generatedDescription` はそのままです)。ワークフローは `published` に戻ります。未公開の変更がないワークフローを破棄しようとすると HTTP 409(`WORKFLOW_NOT_MODIFIED`)が返ります。

**設計チャット**でタスクテンプレートを練ることも編集にあたります。設計エージェントが `published` のワークフローのタスクテンプレートを追加・変更・削除すると、手作業の編集とまったく同じように `modified` に移ります。

## ワークフローを無効化する

**無効化**(ワークフローが `published` か `modified` のときに詳細ページのステータスバーで公開の隣に現れる電源アイコン、`POST /workflows/{id}/deactivate`、developer 限定)は、ワークフローを **`draft`** に戻します。これで `requester` ロールの実行権が失われます。一度も公開されていないワークフローと同じゲートです。`developer` と `super_admin` はテスト目的で引き続き実行でき、タスクテンプレート、2 つの説明フィールド、公開スナップショットはそのまま残ります。もう一度公開すればそのまま `published` に戻ります。`published` でも `modified` でもないワークフローを無効化しようとすると HTTP 409(`WORKFLOW_NOT_DEACTIVATABLE`)が返ります。

## ワークフローを実行する {#running-a-workflow}

**published** か **modified** のワークフロー(`developer` または `super_admin` が呼び出す場合は、公開前テストのため **draft** も)で**実行**を押すと、**WorkflowExecution** が作られます。実行時点のワークフロー設定のスナップショットを持つ、独立したエンティティです。

**draft** のワークフローでは、実行ダイアログにテナントの[ツールモック](./tool-mocks.md)も並びます。チェックするとその実行に限ってそのツールを差し替えるので、公開前のテストをツールの副作用なしに何度でも繰り返せます。公開済みのワークフローではモックは出ませんし、それでも指定すると HTTP 409(`WORKFLOW_NOT_RUNNABLE`)で拒否されます。公開済みの実行が黙って何もしないほうが、実行しないより悪いからです。

1. それ以外のステータスはバックエンドがその場で拒否します。`draft` のワークフローも `developer` と `super_admin` 以外の呼び出し元には HTTP 409(`WORKFLOW_NOT_RUNNABLE`)で拒否します。スキルの公開済みリビジョンも再確認します(なければ `SKILL_NOT_READY`)。リポジトリはスキルの登録時に clone 済みなので、**ここでは何も clone しません**。
2. `WorkflowExecution` のレコードが保存されます。ワークフロー名、実効的な説明(ユーザーが設定していれば `description`、なければ AI が生成した `generatedDescription`)、スキルの情報、実行が行われる**ワークフローセッション**の ID、そして実行が**固定される**スキルのリビジョン(`agentSkillCommitSha`)が入ります。この時点でワークフローがまだ `draft` だった場合(公開前のテスト実行)、レコードには `isDraft: true` が立ち、[運用メトリクス](../operations/metrics.md)から除外されます。このフラグはあとから変わりません。ワークフローのタスクテンプレートは **`pending` の WorkflowTask として実行にコピー**されます(依存の辺とツールの割り当てを含み、ID は振り直されます)。あとからテンプレートを編集してもこの実行には影響しません。`modified` のワークフローでは、名前も説明もテンプレートも、編集後の行ではなく**最後に公開したバージョン**から来ます。その実行に選んだ[ツールモック](./tool-mocks.md)も同時に**レコードへコピー**されます。参照ではなく値としてコピーするので、あとからモックを編集・削除してもこの実行の挙動は変わりません。ADK セッション自体は最初のエージェント呼び出し時に遅延して作られます。
3. バックエンドは `WorkflowExecution` を返します(HTTP 201)。フロントエンドは `/workflow-executions/{workflowExecution.id}/session` へリダイレクトします。ここが**ワークフローセッション**、つまり実行が行われるチャットです。自分のレコードを持たないので、実行の ID で指し示します。
4. マウント時にそのページは `WorkflowExecution` を取得し、過去のメッセージがなければ `POST /workflow-executions/{id}/agent` 経由で決まったキックオフメッセージを自動送信します。ページは通常のチャットと同じ共有アプリバー(通知ベル、テーマ切り替え、アカウントメニュー)を描画し、タイトルの横にワークフロー名を出します。**A2Flow** ロゴは[ウェルカムページ](./admin-ui.md#welcome-page)へリンクします。
5. `/workflow-executions/{id}/agent` エンドポイントは、スキルに紐づいた `ADKAgent`(`agent_skill_id`、固定されたリビジョン、**そしてエージェントの役割**をキーにします)を読み込み、AG-UI の SSE イベントを返します。通常の `POST /agent` エンドポイントと同じです。エージェントは**実行専用**の指示のもとで動きます。タスクは公開によって承認済みなので、**すぐに開始**します。実行の実効的な説明は、信頼できる実行時の文脈としてサーバー側で注入されます。
6. これ以降のユーザーのメッセージも `POST /workflow-executions/{id}/agent` を通るので、A2UI の描画も、A2UI 上の操作(描画されたボタンのクリックなど)も、チャットの体験一式もそのまま働きます。

### エージェントによる実行管理

実行エージェントは、あらかじめコピーされた WorkflowTask を順に処理します。タスクを一覧し、次に実行できるもの(依存がすべて `completed` の `pending` タスク)を選び、`in_progress` にして、スキルに従って作業し、`completed`(または `failed` や `skipped`)にします。すべてのタスクが終了状態に達すると、**セッション完了通知**が上がります。これを支えるツールは 5 つです。`create_workflow_task`、`list_workflow_tasks`、`get_workflow_task`、`update_workflow_task`、`delete_workflow_task` で、ADK のセッション ID から現在のセッションを解決し、REST API が公開しているのと同じ `WorkflowTask` レコードを操作します(そのため必要なら実行の途中でもエージェントがタスク一覧を調整できます)。ステータスが変わる様子は、読み取り専用の**ワークフロータスク**の管理画面(テーブルまたはグラフ)でリアルタイムに追えます。ツールのリファレンスは [backend/README.md](https://github.com/kaitoy/a2flow/blob/master/backend/README.md#agent-task-tools) にあります。

### タスクが使う MCP ツール {#mcp-tools-for-tasks}

WorkflowTask は、[MCP サーバー](./mcp-servers.md)の管理ページに登録した MCP サーバーのツールを使えます。

1. **設計時に割り当てる** — 設計中、エージェントは `list_mcp_tools` を呼びます。登録済みのサーバーすべてに並行して問い合わせ、各サーバーが公開しているツールを返します(到達できないサーバーはサーバー単位で報告され、一覧全体が失敗することはありません)。外部ツールが必要な手順には、`register_design_tasks` の中で `tools` エントリ(`[{"server_id": …, "tool_name": …}]`)が付きます。割り当てはテンプレートに保存され、実行時に実行のタスクへコピーされ、REST の読み取りモデルには `toolBindings` として現れます。
2. **実行時に強制する** — エージェントは割り当てられたツールを `call_mcp_tool(server_id, tool_name, arguments)` のプロキシ経由で呼びます。この呼び出しはすべて A2Flow 自身の MCP プロキシ層を通ります。プロキシは呼び出し元を解決し、アクセス制御ポリシーを参照し、サーバーのシークレット参照を展開してから、ようやく呼び出しごとの接続を開きます(ストリーマブル HTTP のリクエストか、stdio サーバーなら新しく起動する子プロセスです)。最初のポリシーは割り当ての確認です。`(サーバー, ツール)` の組は、そのセッションで現在 `in_progress` のタスクに割り当てられていなければなりません(複数が進行中なら、その割り当ての和集合です)。割り当てのないツールへの呼び出しは、許可されているツールを列挙したエラーで拒否されます。そのため、スキル単位でキャッシュされる共有エージェントであっても、タスクに与えられていないツールを使うことはできません。プロキシを独立した層にしてあるのは、認証やもっと細かいアクセス制御をあとから一か所に足せるようにするためです。[backend/README.md](https://github.com/kaitoy/a2flow/blob/master/backend/README.md#mcp-proxy) を参照してください。

割り当てられたツールは、タスクテンプレートとワークフロータスクの一覧の**ツール**列にチップとして出ます。テンプレートのフォームには **MCP ツール**のピッカーがあり、エージェントスキルの認証パスワードのピッカーと同じく 2 段階で動きます。ページングされたダイアログでサーバーを選び、続いてドロップダウンからそのツールを 1 つずつ追加します。追加したツールは削除できるチップになります。ライブで問い合わせるのは選んだサーバーだけなので、フォームを開くコストは登録済みの全サーバーへの接続ではなく、レジストリの単純な読み取り 1 回です。到達できないサーバーはツール一覧の代わりにその旨を表示しますが、すでに割り当て済みのツールのチップはどちらの場合でも残ります。

この 2 つの一覧はページングせず**すべて**のレコードを表示します。そのおかげで**依存先**列が相互参照として働きます。依存はタイトルで示され、チップにマウスを乗せると依存先のタスクの行が強調されます。設計エージェントには、タスクのタイトルを簡潔な命令形にする制約が課されています(2〜4 語、30 文字)。チップとして読みやすくするためで、長すぎるとタスクのツールが「詳細は説明に移すように」というメッセージとともに拒否します。(この制限が縛るのはエージェントだけです。管理フォームから編集するタイトルは 200 文字まで使えます。)それでもチップからあふれるタイトルは切り詰められ、マウスを乗せると全文が出ます。

ワークフロー実行は通常のチャットセッションから独立しています。ワークフローを削除しても既存の `WorkflowExecution` レコードには影響しません(削除時に `workflow_id` の外部キーが `NULL` になりますが、スナップショットのデータは残ります)。ただしワークフローを削除すると、そのタスクテンプレートと公開バージョンは**削除されます**(カスケード)。行と一緒に、そのワークフローが指していた設計セッションも消えます。

実行の個々のタスクは `WorkflowTask` レコードとして保存されます。各タスクはステータス(`pending` / `in_progress` / `completed` / `failed` / `skipped`)を持ち、`createdAt` 順に並びます。API のリファレンスは [backend/README.md](https://github.com/kaitoy/a2flow/blob/master/backend/README.md#workflow-tasks) にあります。`WorkflowExecution` を削除するとそのタスクもカスケードで消えます。

タスクは平坦なリストではなく**有向非巡回グラフ(DAG)**を作ります。各タスクは `dependsOnIds` フィールドで、同じセッション内の 0 個以上のタスクに依存できます(`(task, dependsOn)` の辺は `workflow_task_dependencies` の中間テーブルに保存されます)。依存先は存在し、かつ同じセッションに属している必要があります(そうでなければ HTTP 422 `FOREIGN_KEY_VIOLATION`)。循環を作る辺は、自己依存も含めて HTTP 409 `DEPENDENCY_CYCLE` で拒否されます。タスクを削除すると、そのタスクをどちら向きに参照している辺もカスケードで消えます。
