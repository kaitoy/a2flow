# ユーザー、グループ、テナント

誰がサインインできて、どこに属するのかは 3 つの管理セクションで扱います。個々のアカウント、ロールをまとめて付与する名前つきの束、そしてそれらが収まるテナントです。

## ユーザー {#users}

[http://localhost:3000/admin/users](http://localhost:3000/admin/users) でアプリケーションのユーザーを管理します。

| 操作 | パス |
|-----------|------|
| ユーザー一覧 | `GET /admin/users` |
| ユーザーの新規作成 | `GET /admin/users/new` |
| ユーザーの詳細ページ(編集・削除) | `GET /admin/users/{id}` |

ユーザーのレコードには、ユーザー名(テナント内で一意。テナントを持たないプラットフォーム全体のユーザーどうしでも別途一意)、姓、名、メールアドレス、`enabled` フラグ、`emailVerified` フラグ、そのユーザーの[ロール](../concepts/authorization.md)が入ります。パスワードは保存前に [bcrypt](https://pypi.org/project/bcrypt/) でハッシュ化され、API から返ることはありません。編集時にパスワード欄を空のままにすると、既存のパスワードが保たれます。ユーザーは `a2flow.db` に保存されます。

**ロール。** 作成フォームと詳細ページにはロールのピッカー(ロールごとにチェックボックス)があり、一覧には**ロール**列が出ます。ロールは JSON のリストとして保存されるため、一覧 API の `s` や `q` によるサーバー側の並べ替え・絞り込みはできません。**スーパー管理者**のチェックボックスは、サインインしているユーザーがスーパー管理者でなければ無効です。付与も剥奪もバックエンドが拒否します。スーパー管理者はほかのすべてのロールと排他なので、これをチェックするとほかのロールのチェックボックスがすべて無効になります(逆も同じです)。理由は区切り線とヒントで示されますが、いずれにせよ両方の組み合わせはバックエンドが拒否します。

**グループから来るロール。** ピッカーが編集するのは**直接**の付与だけです。[ユーザーグループ](./users-and-groups.md#user-groups)から継承したロールは、その下の**グループから来るロール**に読み取り専用のチップとして並びます。ユーザーを編集しても変えられず、変えられるのはグループの編集だけです。一覧の**ロール**列には両方が出ますが、継承したものは薄いチップになるので、このページで変えられる付与がどれかは見て分かります。2 つがどう合わさるかは[ロールと認可](../concepts/authorization.md)を参照してください。

**グループ。** 現在の所属は削除できるチップとして並び、**グループを選択…** ボタンからテナントのユーザーグループのモーダル表を開いて追加できます(ページングと絞り込みはサーバー側です)。プラットフォーム全体のアカウント(スーパー管理者と初期投入されるシステムユーザー)ではこのボタンは隠れます。テナントのグループに属することが決してないからです。所属は `GET /api/v1/users/{id}/groups` で読み、`PUT /api/v1/users/{id}/groups` という別のリクエストで書きます。書くのは選択が実際に変わったときだけです。同じ所属は反対側、つまり各[グループ](./users-and-groups.md#user-groups)の詳細ページからも編集できます。

**なりすまし。** [なりすましの規則](../concepts/authorization.md)で対象になる行には**なりすまし**の操作が出ます。サインインしている本人の行、`super_admin` を持つ行、そして閲覧者がスーパー管理者でない限り `admin` を持つ行では隠れます。確認すると、そのユーザーとしてウェルカムページへ移動します。誰が誰になりすませるのか、どう停止するのかは[ロールと認可](../concepts/authorization.md)を参照してください。

**プロフィール。** サインインしているユーザーは、**プロフィール**ページ(ツールバーのプロフィールボタン →**プロフィール**、`/profile`)で自分のアカウントを確認できます。ページの先頭はアイデンティティカードです。オーロラのバナー、その下端にまたがるアバター、ページ見出しになる表示名が並び、その横に `@username` のハンドル、ロール、`enabled` と `emailVerified` のフラグがステータスピルとして出ます。その下には残りの属性が 2 枚の**読み取り専用**カードに分かれます。**アカウント**(ユーザー名、メールアドレス、姓名)と**アクセス**(ロール、**グループから来るロール**、**グループ**)です。バックエンドが本人からの更新を受け付けるのはアバターだけなので(それ以外は `admin` ロールと管理画面のユーザー詳細ページが必要です)、これらの属性は無効化した入力欄ではなく素のテキストとして描画されます。**グループから来るロール**はグループの所属から継承したロールで、管理画面のユーザー詳細ページと同じ薄いチップで出ます(上の[グループから来るロール](./users-and-groups.md#users)を参照)。**グループ**は所属そのもので、`GET /api/v1/users/{id}/groups` から読みます。このページで唯一編集できるのはアバターで、編集はアバターをクリックして行います。

**アバター。** どのユーザーにもアバターがあり、ツールバーのプロフィールボタン、管理画面のユーザー一覧と詳細ページに出ます。既定では [boring-avatars](https://github.com/boringdesigners/boring-avatars) の `beam` バリアントでクライアント側が決定的に生成する SVG です。画像は保存されず、ネットワークアクセスも発生しません。シードはユーザーのテナントとユーザー名(`{tenantId}/{username}`)です。ユーザー名はテナント内でしか一意でないため、2 つのテナントに同じユーザー名がいても別の顔になります。プラットフォーム全体のユーザー(`super_admin` と初期投入されるシステムユーザー)はテナントを持たないので、ユーザー名だけをシードにします。

サインインしているユーザーは、[プロフィールページ](./users-and-groups.md#users)のアイデンティティカードのアバターをクリックして開くダイアログから、自分のアバターを管理できます。好きな画像を**アップロード**する(PNG、JPEG、WebP、GIF、2 MB まで)か削除するか、生成されるアバターの**配色**を編集するかです。アップロードは即座に確定してダイアログを閉じます。ダイアログで未保存の状態を持つのはパレットだけなので、**既定に戻す**は色見本を戻すだけで、確定するのは**保存**です(こちらもダイアログを閉じます)。アプリケーションの既定と一致するパレットは「パレットなし」として保存されます。つまり戻して保存すると、既定のコピーを書き込むのではなくレコードが消えます。保存せずにダイアログを閉じたぶんは破棄されます。

パレットは `UserRead.avatarConfig.colors`(最大 8 つの `#rrggbb` を順に並べたリスト)として保存され、アバターが描画されるすべての場所に適用されます。どの色がどこに来るかはシードが決めるので、パレットを共有していてもユーザーごとの見た目は保たれます。パレットが保存されていない場合は `frontend/src/lib/avatar-palette.ts` にあるアプリケーションの既定を使います。アバターの編集は本人だけができます。管理画面のユーザー詳細ページではアバターは読み取り専用で、アップロードも配色の操作もありません。アップロードした画像は専用の `user_avatars` テーブルに保存され、`GET /api/v1/users/{id}/avatar` から配信されます。`UserRead.avatarUpdatedAt` が存在の目印とキャッシュ破棄のキーを兼ねます。アップロードや削除を行うとサインイン中のユーザー情報がどこでも更新されるので、ツールバーのプロフィールボタンもすぐ切り替わります。優先順位は**アップロードした画像 → 独自パレットのアバター → 既定パレットのアバター**で、画像を消すかパレットを戻すと次の候補に落ちます。

**監査上の所有者。** 永続化されるすべてのレコードは `createdBy` と `updatedBy` を `users.id` への外部キーとして保持し、値は**認証済みセッション**から入ります([認証](../concepts/authentication.md)を参照)。操作したユーザーが存在しない書き込みは HTTP 422(`FOREIGN_KEY_VIOLATION`)で拒否されます。「最初のユーザーは誰が作るのか」というブートストラップ問題を解くため、`users` テーブルが空のときは起動時にログイン不可の隠し**システムユーザー**が投入され、初期投入される `root` と `admin` の所有者になります。管理画面に生の ID が出ることはありません。各詳細ページは `createdBy` と `updatedBy` をユーザーの「姓 名」に解決し、一覧も同じようにユーザー ID を解決します。

**名前の一括解決。** ユーザー参照を多く含む画面(監査のフッター、ワークフローの開始者や承認者の表)は、`POST /api/v1/users/resolve-names` の 1 回の呼び出しでまとめて解決します。最大 1000 件の ID を受け取り、それぞれについて `{id, displayName}` を返します。テナント境界の扱いは `GET /api/v1/users/{id}` と同じです。呼び出し元のテナント外のユーザーには名前が付かず、その ID はレスポンスに現れないので、UI は生の ID を表示します。2 種類のアカウントだけは落とさずラベルを付けます。どちらもテナントをまたいでレコードを所有しており、裸の UUID が出るとバグに見えるからです。初期投入されるシステムユーザーは **System User** に、呼び出し元から見えない `super_admin` は **Super Admin** に解決されます。後者はすべて同じラベルなので、どの個人だったかは伏せられます。スーパー管理者が呼び出した場合はこの境界の対象外で、すべての実名が見えます。

**ユーザーの削除。** ほかのレコードから参照されていなければ、データベースから物理削除されます。まだ参照されている場合(`createdBy` や `updatedBy` のいずれかから)は代わりに**論理削除**になり、`deletedAt` が設定されてアカウントは無効化されます。既存の参照が有効なまま保たれ、名前も引き続き解決できます。論理削除されたユーザー(とシステムユーザー)はユーザー一覧には出ませんが、ID を指定すれば取得できます。

## ユーザーグループ {#user-groups}

[http://localhost:3000/admin/user-groups](http://localhost:3000/admin/user-groups) でユーザーグループを管理します。ユーザーをまとめた名前つきの束で、持っているロールをメンバー全員に付与します。

| 操作 | パス |
|-----------|------|
| ユーザーグループ一覧 | `GET /admin/user-groups` |
| ユーザーグループの新規作成 | `GET /admin/user-groups/new` |
| グループの詳細ページ(編集・削除) | `GET /admin/user-groups/{id}` |

グループはちょうど 1 つのテナントに属し(名前はそのテナント内で一意です)、説明と、**付与するロール**と、**メンバー**を保持します。メンバーは自分のユーザーレコードに付与されたロールに加えて、これらのロールを持ちます。2 つがどう合わさるかは[ロールと認可](../concepts/authorization.md)を参照してください。ユーザー側に非正規化して持たせるものは何もないので、グループのロールや所属を変えると、影響を受ける全員について次のリクエストから効きます。

**付与するロール。** ロールのピッカーは[ユーザー](./users-and-groups.md#users)のページと同じもので、**スーパー管理者**だけがありません。グループがこれを付与することはできず、選択肢はスーパー管理者を含むすべての閲覧者から隠れています。それでも送信すると HTTP 422 で拒否され、データベースの CHECK 制約がそれを裏打ちします。

**メンバー。** 現在のメンバーは削除できるチップとして並び、**メンバーを選択…** ボタンからテナントのユーザーのモーダル表を開いて追加できます(ページングと絞り込みはサーバー側です)。プラットフォーム全体のアカウント(スーパー管理者と初期投入されるシステムユーザー)は出てきません。どのテナントにも属さないためメンバーになれないからで、これが `super_admin` がグループ経由で届かない理由でもあります。メンバーを指定するとグループの所属をまるごと置き換えます。編集時にこのフィールドに触れなければ、そのまま保たれます。同じ所属は反対側、つまり各[ユーザー](./users-and-groups.md#users)の詳細ページからも編集できます。

書き込みには `admin` ロールが必要です。読み取りはほかのセクションと同じく開いているので、ロールのない閲覧者にも一覧と読み取り専用の詳細ページが見えます。グループを**削除**すると所属の行も一緒に消えます。アカウント自体はそのままですが、そのグループが付与していたロールは失われます。

## テナント {#tenants}

[http://localhost:3000/admin/tenants](http://localhost:3000/admin/tenants) でテナントを管理します。マルチテナンシーにおける最上位の組織境界です。ほかのすべての管理セクションと違って、ここは**スーパー管理者**に限定されます。それ以外のロールにはサイドバーからもウェルカムページからも隠れ、バックエンドは他者からの書き込みを HTTP 403(`FORBIDDEN`)で拒否します。

| 操作 | パス |
|-----------|------|
| テナント一覧 | `GET /admin/tenants` |
| テナントの新規作成 | `GET /admin/tenants/new` |
| テナントの詳細ページ(編集・削除) | `GET /admin/tenants/{id}` |

テナントのレコードには、一意な `displayName`(人が読むラベル)、一意で URL に使える `name`(小文字のケバブケース。将来パスやサブドメインで使う想定)、削除せずに停止するための `enabled` フラグが入ります。テナントを無効にすると、そのユーザーのサインインが止まり、すでにログイン中の人も次のリクエストでサインアウトされます。[ユーザー](./users-and-groups.md#users)が属するテナントは多くても 1 つです(`User.tenantId`)。ユーザーが 1 人でも割り当たっているテナントは削除できず、API は HTTP 409(`CONFLICT_REFERENCED`)で拒否します。**Default** テナント(`name: default`)は初回起動時に自動で投入され、初期投入される `admin` ユーザーを抱えます。
