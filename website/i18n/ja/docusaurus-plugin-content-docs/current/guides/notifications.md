# 通知

上部ツールバーの**ベルのアイコン**(チャットのヘッダーと管理画面のサイドバーの両方にあります)を押すと、未読件数のバッジが付いた通知センターが開きます。通知は**ユーザーごと**で、`a2flow.db` に保存され、**ポーリング**で届きます(フロントエンドが 30 秒ごとに更新します)。

ベルのドロップダウンに出るのは**未読の通知だけ**です。まだ対応が要るものを浮かび上がらせる場所だからです。既読を含む全履歴は専用の[通知ページ](./notifications.md#notification-history-page)にあり、アカウントメニュー(ツールバーのプロフィールボタン →**通知**)から開けます。通知を削除できるのもここだけです。

通知を生むワークフローのイベントは 4 つです。宛先はイベントによって変わります。`request_approval` の通知はその承認で**指名された承認者**に宛てられ、宛先がグループなら適格なメンバーごとに 1 通ずつ届きます。それ以外は**セッションや生成を開始したユーザー**に宛てられます。

| 種類 | 上がるとき |
|---|---|
| `workflow_draft_ready` | [「ワークフローを生成」](./workflows.md#generating-a-workflow)のバックグラウンド設計実行が終わり、下書きの初期タスクテンプレートが確認できる状態になったとき。 |
| `workflow_generation_failed` | その設計実行が失敗したとき。クライアントが見ていない状態で走るので、ユーザーが失敗を知る経路がこれです。理由はワークフローの詳細ページと設計チャットに出ます。 |
| `approval_request` | エージェントが実行の途中で判断を求め(`request_approval`)、指名された承認者を待つとき。 |
| `execution_completed` | その実行のすべての `WorkflowTask` が終了状態(`completed` / `failed` / `skipped`)に達したとき。実行ごとに 1 回だけ出ます。最後のタスクを書いたのが実行エージェントでも REST のタスクエンドポイントでも同じです。同じ判定が実行自身の[終了ステータス](./workflow-executions.md)も決めます。 |

通知をクリックすると既読になり、関係する場所へ移動します。実行に紐づくイベントは `/workflow-executions/{id}/session` のチャットへ、ワークフローに紐づくイベント(`workflow_draft_ready` と `workflow_generation_failed`)はワークフローの詳細ページへ飛びます。各行には**既読にする(✓)**ボタンもあり、移動せずにドロップダウンから消せます。パネルのヘッダーには**すべて既読にする**もあり(未読が残っているあいだだけ出ます)、未読の通知を一度に片付けられます。ドロップダウンから通知を削除する手段はありません。既読にするのは、脇へどけるだけです。

## 通知履歴のページ {#notification-history-page}

[`/notifications`](http://localhost:3000/notifications) のページは、ツールバーのプロフィールボタンのアカウントメニュー(**通知**)から開けます。サインイン中のユーザーが受け取ったすべての通知が、既読も含めて、並べ替えと絞り込みのできる表(タイトル、種類、作成日時)として並びます。表の上の**すべて/未読**の切り替えで既読状態のフィルタを変えられ、未読の各行には同じ**既読にする**の操作があり、すべての行には**削除(✕)**ボタンがあって、確認ダイアログのあとその通知を完全に削除します。

`GET /api/v1/notifications` は、ほかのコレクションのエンドポイントと同じ `limit` / `offset` / `s` / `q` の[一覧クエリパラメータ](./admin-ui.md#list-query-parameters)を受け取ります。未読だけの一覧は `?q=read:eq:false`、並び順はたとえば `?s=-createdAt`(既定)です。`PATCH /api/v1/notifications/{id}` はリクエストボディを受け取り、変更できるフィールドは `read` だけです。`{"read": true}` で既読に、`{"read": false}` で未読に戻します。これらのエンドポイントと、すべて既読にする操作、削除の操作は [API リファレンス](http://localhost:3000/api-doc)に記載しています。いずれも認証済みユーザーの範囲に閉じているので、ほかのユーザーの通知を読んだり更新したり削除したりすると HTTP 404 が返ります。`q` に `userId` を指定してもこの範囲を狭められるだけで、外へは出られません。通知は、受信者のユーザーと、紐づく `WorkflowExecution` または `Workflow` と一緒にカスケードで削除されます。

## メール配信 {#email-delivery}

`super_admin` が[システム設定](./system-settings.md)で SMTP サーバーを設定すると、同じ 4 つのイベントが宛先に**メールでも**届きます。承認依頼が、誰かがアプリを開くのを待たずに済むようにするためです。

メッセージは、通知のタイトルを件名に、本文をテキストに、そして対象へのリンクを持ちます。リンク先は `approval_request` と `execution_completed` なら実行、`workflow_draft_ready` と `workflow_generation_failed` ならワークフローで、設定した**アプリケーションのベース URL** から組み立てます。ベース URL が未設定の場合はリンクなしで送信します。

届けようのない宛先は、リレーに接続する前に除かれます。内部のシステムユーザー、無効化または論理削除されたアカウント、アドレスが未確認のアカウント、アドレスを持たないアカウントです。ユーザー単位の配信停止はありません。メール配信はプラットフォーム全体でオンかオフかのどちらかです。

### 配信キュー {#the-delivery-queue}

ワークフローの処理中に送信することはありません。通知の行と、`outbound_emails` の行(完全に組み立て済みのメッセージと宛先など一式)は**1 つのトランザクション**で書かれます。そのためクラッシュしても、メールがキューに入っていない通知が残ることはありません。そのキューはワーカーが順に処理します。

- **ペースを保ちます。** トークンバケットがリレーへの持続レートを抑え(既定は毎秒 5 通、バースト 10 通)、1 バッチ分は再利用した 1 本の SMTP 接続で送ります。
- **再試行します。** 一時的な失敗(リレーが落ちている、4xx を返す、認証情報を拒否する)には、指数バックオフとジッターを付けて次の試行を予約します。15 秒、30 秒、1 分、2 分と倍にしていき、上限は 1 時間です。既定の 9 回という試行回数で、おおよそ 1 時間の停止を乗り切ります。
- **見込みがなければ打ち切ります。** リレーが恒久的と報告した失敗(宛先が存在しないなど)は再試行しません。試行回数を使い切るか恒久的に失敗したメッセージは `status=failed` のまま残り、行には最後のエラーが載ります。黙って失われるのではなく、確認すべきデッドレターとして残ります。配信済みのメッセージは 30 日後に消えますが、デッドレターは残ります。

送信するプロセスは**常にちょうど 1 つ**で、PostgreSQL のアドバイザリロックで選ばれます。レート制限がおおよそではなく正確なのはこのためです。ワーカーを 2 レプリカ以上にしても、得られるのはフェイルオーバーであってスループットではありません。バッチの途中で送信プロセスが落ちると、確保したぶんはリースが残った状態になり、次の巡回が試行回数を消費せずに回収します。

既定では API のプロセス自身がワーカーを動かすので、`uvicorn main:app` だけでメールは届きます。`compose.yml` では代わりに専用の `worker` サービスを動かし、API 側には `EMAIL_WORKER_IN_PROCESS=false` を設定して、リクエストを処理するプロセスから SMTP の作業を外しています。調整できる項目は [`backend/.env.example`](https://github.com/kaitoy/a2flow/blob/master/backend/.env.example) の **Outgoing email queue** にすべて並んでいます。

滞留やリレーの詰まりの兆候は、[メトリクスのエンドポイント](../operations/metrics.md)で `a2flow_email_queue_depth{tenant,status}` と `a2flow_email_queue_oldest_pending_age_seconds{tenant}` として見られます。
