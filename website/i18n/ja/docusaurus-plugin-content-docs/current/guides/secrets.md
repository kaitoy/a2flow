# シークレット

[http://localhost:3000/admin/secrets](http://localhost:3000/admin/secrets) で、アプリの各所の認証に使う名前つきの認証情報を管理します。

シークレットは**キーと値のエントリを束ねた名前つきのまとまり**で、形は [HashiCorp Vault の KV エンジン](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2)と同じです。1 つのパスがキーから値へのマップを持ちます。ほかのレジストリと同じく、シークレットにも[タグ](./tags.md)を付けられます。組で使う認証情報(たとえば AWS のアクセスキー ID とシークレットアクセスキー)は、2 つのシークレットに分けるのではなく、1 つのシークレットの 2 エントリとして入れます。

個々のエントリは `name/key` で参照します。

- **MCP サーバーのヘッダーと環境変数** — ヘッダーの値(ストリーマブル HTTP)や環境変数の値(stdio)には `${secret:name/key}` のプレースホルダーを埋め込めます。接続時に展開されます([MCP サーバー](./mcp-servers.md)を参照)。
- **エージェントスキルのリポジトリのクローン** — スキルの**認証パスワード**は、git のベーシック認証のパスワードに使うエントリへの `name/key` 参照です。打ち込むのではなくドロップダウンから選びます([エージェントスキル](./agent-skills.md)を参照)。

キーは**常に必須**です。シークレットのエントリが 1 つだけでも同じです。名前だけではマップを指すことになり、値を指したことになりません。キーのない `${secret:name}` は、文字列としてそのまま通されるのではなく `SECRET_RESOLUTION_FAILED` で失敗します。

| 操作 | パス |
|-----------|------|
| シークレットの一覧 | `GET /admin/secrets` |
| シークレットの新規登録 | `GET /admin/secrets/new` |
| シークレットの詳細ページ(編集・削除) | `GET /admin/secrets/{id}` |

シークレットには 2 つのタイプがあります。

- **ローカル(暗号化)** — エントリは一度だけ送信され、各値を [Fernet](https://cryptography.io/en/latest/fernet/)(AES-128-CBC + HMAC)で暗号化して `a2flow.db` に保存します。キーは平文で保存するので、何も復号せずに一覧できます。API は**書き込み専用**です。レスポンスにエントリのキーは載りますが、値は平文でも暗号文でも載りません。そのため詳細ページには保存済みのキーがすべて、値を空にした状態で並びます。空のままにすれば保存済みの値が保たれ、打ち直せば置き換わり、行を削除すればそのエントリが消えます。
- **HashiCorp Vault** — 保存するのは KV v2 の参照(マウントとパス)だけです。そのパスにあるすべてのキーが読め、各値は解決のたびに Vault からその場で取得します。

`GET /api/v1/secrets/{id}/keys` は、シークレット 1 件のエントリのキー(キーだけ)を、どちらのタイプでも同じように返します。`local` なら保存されたマップから、`vault` なら KV v2 のライブ読み取りから取ります(Vault に到達できない、または未設定の場合は HTTP 502 `SECRET_RESOLUTION_FAILED` になります)。エージェントスキルの認証パスワードのピッカーはこれを使います。シークレットの読み取りにある `keys` フィールドではこの用途を果たせません。`vault` タイプでは常に空だからです。

シークレットは**名前で**参照され、遅延して解決されます。まだ参照されているシークレットの名前を変えたり削除したりしても編集時には失敗しませんが、次に使うときに、見つからないシークレット名を添えた HTTP 502(`SECRET_RESOLUTION_FAILED`)で失敗します。

## 暗号化キー

ローカルシークレットの Fernet キーは、最初の使用時に次の優先順位で解決されます。

1. `SECRET_ENCRYPTION_KEY` 環境変数(有効な Fernet キーであること。生成は `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` で行えます)。
2. `SECRET_KEY_FILE` にあるキーファイル(既定は SQLite のデータベースファイルの隣の `.secret_key`。ほかのデータベースの場合は作業ディレクトリ)。
3. 新しいキーを生成してそのファイルに保存し、WARNING をログに出します。

⚠️ キーはバックアップしてください。失うと、保存済みのローカルシークレットはすべて復号できなくなります。

## HashiCorp Vault への接続

Vault への接続はグローバルに 1 つだけで、環境変数で設定します(`backend/.env.example` を参照)。`VAULT_ADDR` でサーバーを指定し、認証は静的な `VAULT_TOKEN` か **AppRole** の認証情報(`VAULT_ROLE_ID` と `VAULT_SECRET_ID`。ログインのマウントは `VAULT_APPROLE_MOUNT` で変更でき、既定は `approle`)のどちらかです。両方設定されている場合は AppRole が優先されます。そのクライアントトークンはキャッシュされ、リースが切れると自動で更新されます。対応しているのは KV v2 のシークレットエンジンだけです。Vault が未設定の場合、`vault` タイプのシークレットは `SECRET_RESOLUTION_FAILED` で解決に失敗します。
