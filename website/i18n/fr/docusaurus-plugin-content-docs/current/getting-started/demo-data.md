# Données de démonstration

Lorsque `DEMO_DATA=true` est défini sur le backend, tout ce dont ont besoin trois exemples soumis à approbation et qui modifient l'état — « lancer une instance EC2 », « redémarrer un pod GKE » et « effectuer la rotation d'un secret Azure Key Vault » — est enregistré dans le tenant **Default** créé à l'initialisation : vous avez ainsi de quoi exécuter quelque chose sans enregistrer chaque élément à la main. Le [workflow](../guides/workflows.md) lui-même n'est volontairement pas créé : ces enregistrements sont les ingrédients à partir desquels vous en générez un, et la [Visite guidée](./walkthrough.mdx) est le parcours qui s'en charge.

## Activation {#enabling-it}

Ajoutez l'option à `backend/.env` et redémarrez le backend. Avec [Docker Compose](./docker-compose.md), elle est déjà activée : `compose.yml` définit `DEMO_DATA: ${DEMO_DATA:-true}`.

```env
DEMO_DATA=true
DEMO_PASSWORD=change-me-now-123
DEMO_AWS_ACCESS_KEY_ID=AKIA...
DEMO_AWS_SECRET_ACCESS_KEY=...
DEMO_AWS_REGION=us-east-1
DEMO_GCP_CREDENTIALS_JSON='{"type":"service_account",...}'
DEMO_AZURE_TENANT_ID=...
DEMO_AZURE_CLIENT_ID=...
DEMO_AZURE_CLIENT_SECRET=...
```

- `DEMO_PASSWORD` est partagé par les onze utilisateurs de démonstration et bénéficie de la même solution de repli que `ROOT_PASSWORD` / `ADMIN_PASSWORD` : une valeur générée et consignée une seule fois dans les journaux. Il n'est consulté que tant que l'un des comptes manque.
- Les identifiants AWS, l'identifiant Google Cloud et les identifiants Azure sont facultatifs. S'ils ne sont pas définis, un substitut `REPLACE_ME` est enregistré à leur place : la démonstration est complète dans sa forme, et vous renseignez les vraies valeurs depuis la page [Secrets](../guides/secrets.md).
- `DEMO_AWS_REGION` est la région sur laquelle agissent les outils du serveur MCP AWS de démonstration. Sa valeur par défaut est `us-east-1`.
- `DEMO_GCP_CREDENTIALS_JSON` est un identifiant Google Cloud au format JSON, sur une seule ligne : une clé de compte de service, ou le JSON d'utilisateur autorisé écrit par `gcloud` après une connexion ponctuelle avec un ID et un secret de client OAuth. Le serveur MCP GKE en tire son jeton d'accès ; les serveurs MCP de Google n'acceptent pas les clés d'API. Consultez [Serveurs MCP Google Cloud](../guides/mcp-servers.md#google-cloud-mcp-servers) pour savoir comment obtenir l'un ou l'autre.
- `DEMO_AZURE_TENANT_ID`, `DEMO_AZURE_CLIENT_ID` et `DEMO_AZURE_CLIENT_SECRET` décrivent un principal de service Azure : le tenant, l'ID client de l'application et l'un de ses secrets client, tels que les affiche `az ad sp create-for-rbac`. Sur le coffre dans lequel la démonstration doit effectuer la rotation des secrets, attribuez-lui un rôle personnalisé limité aux actions de données `Microsoft.KeyVault/vaults/secrets/readMetadata/action` et `Microsoft.KeyVault/vaults/secrets/setSecret/action` ou, sur un coffre qui utilise des stratégies d'accès, limité aux autorisations de secret **List** et **Set**. Le rôle intégré **Key Vault Secrets Officer** convient aussi, mais il peut également lire la valeur de tous les secrets.

⚠️ Les serveurs MCP AWS, GKE et Azure peuvent exécuter des opérations **en écriture**, pas seulement des lectures. Les identifiants du serveur MCP AWS peuvent créer et supprimer de vraies ressources AWS, l'identité du serveur MCP GKE peut lancer le redémarrage progressif d'une charge de travail ou supprimer un pod sur un vrai cluster, et le principal de service du serveur MCP Azure peut écrire des secrets Key Vault : utilisez des comptes jetables ou des identifiants aux droits strictement limités pour les trois. Pour essayer l'un d'eux sans toucher à aucun vrai fournisseur, consultez [Essayer](#trying-it-out) ci-dessous.

## Ce qui est enregistré {#what-gets-registered}

- **[Compétence d'agent](../guides/agent-skills.md) `Demo AWS EC2 Launch`** — recueille la configuration de l'instance, obtient l'approbation explicite d'un responsable, puis lance l'instance au moyen d'un outil MCP. Son dépôt est cloné en arrière-plan après le démarrage : la compétence s'affiche donc comme `Clonage` pendant un moment avant de pouvoir être utilisée.
- **[Compétence d'agent](../guides/agent-skills.md) `Demo GKE Pod Restart`** — convient avec l'utilisateur de la cible exacte (projet, cluster, namespace et soit un nom de Deployment/StatefulSet, soit le nom d'un seul pod), obtient l'approbation explicite d'un responsable pour cette cible précise, puis, par défaut, redémarre progressivement la charge de travail au moyen du GKE MCP Server — ou, si l'utilisateur veut seulement se débarrasser d'un pod, supprime ce pod pour que son contrôleur propriétaire le recrée — et rend compte du résultat. Son dépôt est cloné de la même façon : elle s'affiche donc elle aussi comme `Clonage` au début.
- **[Compétence d'agent](../guides/agent-skills.md) `Demo Azure Key Vault Secret Rotation`** — convient avec l'utilisateur du Key Vault et d'un secret existant qu'il contient, obtient l'approbation explicite d'un responsable pour ce secret précis, puis écrit une valeur aléatoire fraîchement générée comme nouvelle version du secret au moyen de l'Azure MCP Server et indique quand la nouvelle version a été créée. Elle n'affiche jamais la valeur dans la discussion. Son dépôt est cloné de la même façon : elle s'affiche donc elle aussi comme `Clonage` au début.
- **[Serveur MCP](../guides/mcp-servers.md) `AWS MCP Server`** — un serveur `stdio` qui se connecte à l'AWS MCP Server géré par AWS, d'où proviennent les outils EC2.
- **[Serveur MCP](../guides/mcp-servers.md) `GKE MCP Server`** — un serveur `streamable_http` qui se connecte au serveur MCP GKE (Google Kubernetes Engine) géré par Google Cloud, sur le point de terminaison complet. Son en-tête `Authorization` est `Bearer ${gcp-token:demo-gcp-credentials/GOOGLE_CREDENTIALS_JSON}` : chaque connexion envoie donc un nouveau jeton d'accès tiré du secret `demo-gcp-credentials`, et ses outils peuvent gérer les clusters et leurs ressources Kubernetes, y compris redémarrer progressivement une charge de travail ou supprimer un pod.
- **[Serveur MCP](../guides/mcp-servers.md) `Azure MCP Server`** — un serveur `stdio` qui exécute l'Azure MCP Server de Microsoft, limité à ses outils Key Vault. Il se connecte avec le principal de service du secret `demo-azure-credentials`, et ses outils peuvent lister et écrire les secrets, clés et certificats de Key Vault. Avant chaque opération sur un secret, il demande un consentement, et cette question est adressée au demandeur de l'exécution sous forme de [confirmation dans la discussion](../guides/workflow-executions.md#mcp-server-confirmations), en plus de l'approbation de la rotation par le responsable. La compétence de démonstration indique à l'agent de conception de marquer ses outils comme posant des questions : chaque tâche qui en utilise un attend donc que le demandeur la reprenne. La nouvelle valeur du secret transite par la conversation de l'agent avant d'arriver dans Key Vault : traitez donc la discussion d'une exécution comme vous traiteriez le secret.
- **[Serveur MCP](../guides/mcp-servers.md) `EC2 Cost Estimator`** — un [serveur de script](../guides/mcp-servers.md#writing-a-script) Python dont les outils estiment le coût mensuel à la demande d'un type d'instance EC2 (`estimate_monthly_cost`) et en classent plusieurs par coût (`compare_instance_types`), à partir de prix récupérés en direct dans l'AWS Price List pour la région demandée. Il installe `boto3` sous **Paquets** et lit le même secret `demo-aws-credentials` : pour l'essayer dans **Exécution de test**, il faut donc des identifiants autorisés à lire l'AWS Price List (`pricing:GetProducts`). Il ne fait que lire.
- **[Serveur MCP](../guides/mcp-servers.md) `Kubernetes Manifest Toolkit`** — un serveur de script JavaScript dont les outils vérifient qu'il ne manque aucun champ obligatoire dans un manifeste Kubernetes (`validate_manifest`) et construisent le correctif qui redémarre progressivement un Deployment, un StatefulSet ou un DaemonSet (`build_restart_patch`). Il installe `js-yaml` sous **Paquets**, n'a besoin d'aucun identifiant et ne contacte jamais de cluster : il fonctionne donc immédiatement dans **Exécution de test**.
- **[Serveur MCP](../guides/mcp-servers.md) `Secret Value Generator`** — un serveur de script JavaScript dont l'unique outil génère une valeur de secret aléatoire cryptographiquement sûre (`generate_secret_value`). Il n'installe aucun paquet, n'a besoin d'aucun identifiant et ne contacte jamais Azure : il fonctionne donc immédiatement dans **Exécution de test**.
- **[Base de connaissances](../guides/knowledge-bases.md) `AWS EC2 Pricing`** — contient une seule source, `ec2-on-demand-pricing.pdf` : une grille tarifaire indiquant le coût à la demande horaire et mensuel, les vCPU et la mémoire des dix types d'instance proposés par la [Visite guidée](./walkthrough.mdx), dans `us-east-1`, `us-east-2` et `us-west-2`, ainsi que les frais de stockage et d'adresse IP publique. Les chiffres sont des valeurs de référence pour la démonstration. La source est enregistrée comme **Non lue** : la base de connaissances n'a donc aucune page tant que personne n'a cliqué sur **Lire** pour cette source ; dans la Visite guidée, c'est le développeur AWS qui s'en charge. Liée à un workflow de lancement EC2, elle permet à l'agent de répondre sur le coût de l'instance demandée.
- **[Secret](../guides/secrets.md) `demo-aws-credentials`** — l'ID de clé d'accès AWS et la clé d'accès secrète que lit l'AWS MCP Server.
- **[Secret](../guides/secrets.md) `demo-gcp-credentials`** — l'identifiant Google Cloud au format JSON dont le GKE MCP Server tire son jeton d'accès.
- **[Secret](../guides/secrets.md) `demo-azure-credentials`** — l'ID de tenant, l'ID client et le secret client du principal de service Azure avec lesquels l'Azure MCP Server se connecte.
- **[Simulacres d'outils](../guides/tool-mocks.md)** — des simulacres pour les outils à effets de bord de l'exécution de démonstration : `aws___call_aws` et `aws___run_script` sur l'AWS MCP Server, qui renvoient chacun un lancement réussi ; `patch_k8s_resource` et `delete_k8s_resource` sur le GKE MCP Server, qui renvoient respectivement un redémarrage progressif réussi et une suppression de pod réussie ; `keyvault_secret_get` et `keyvault_secret_create` sur l'Azure MCP Server, qui renvoient respectivement une liste des secrets du coffre et une nouvelle version de secret ; et le `request_approval` intégré, qui renvoie une approbation. Les sélectionner dans la boîte de dialogue **Exécuter** d'un brouillon permet à n'importe lequel des trois workflows d'aller jusqu'au bout sans toucher à AWS, à un vrai cluster GKE ni à un vrai Key Vault, et sans attendre un responsable.
- **[Étiquettes](../guides/tags.md)** `AWS`, `GCP` et `Azure` — chacune est une [étiquette de contrôle d'accès](../guides/tags.md#access-control-tags) : seuls les membres de `Demo AWS Group` / `Demo GCP Group` / `Demo Azure Group` (ainsi qu'`admin` ou un super administrateur) peuvent voir les enregistrements ci-dessus portant l'étiquette de ce fournisseur. `EC2 Cost Estimator` et la base de connaissances `AWS EC2 Pricing` portent `AWS`, `Kubernetes Manifest Toolkit` porte `GCP` et `Secret Value Generator` porte `Azure`, comme les enregistrements du fournisseur qu'ils complètent. `Approval Required` est une simple étiquette posée sur les trois compétences d'agent, et ne restreint rien.
- **Utilisateurs et groupes de démonstration :**

| Utilisateur | Rôle | Groupe de contrôle d'accès | Ce qu'il fait |
|---|---|---|---|
| `demo-aws-developer` | Développeur | `Demo AWS Group` | Génère le workflow de lancement EC2 |
| `demo-aws-reviewer` | Relecteur | `Demo AWS Group` | Publie le workflow de lancement EC2 |
| `demo-aws-requester` | Demandeur | `Demo AWS Group` | Exécute le workflow de lancement EC2 |
| `demo-gcp-developer` | Développeur | `Demo GCP Group` | Génère le workflow de redémarrage de pod GKE |
| `demo-gcp-reviewer` | Relecteur | `Demo GCP Group` | Publie le workflow de redémarrage de pod GKE |
| `demo-gcp-requester` | Demandeur | `Demo GCP Group` | Exécute le workflow de redémarrage de pod GKE |
| `demo-azure-developer` | Développeur | `Demo Azure Group` | Génère le workflow de rotation de secret |
| `demo-azure-reviewer` | Relecteur | `Demo Azure Group` | Publie le workflow de rotation de secret |
| `demo-azure-requester` | Demandeur | `Demo Azure Group` | Exécute le workflow de rotation de secret |
| `demo-approver-1`, `demo-approver-2` | Approbateur | `Demo Approvers` (les trois étiquettes) | Approuve le lancement, le redémarrage de pod ou la rotation |

Aucun d'eux ne détient son rôle directement : chacun en hérite d'un [groupe d'utilisateurs](../guides/users-and-groups.md#user-groups), à savoir `Demo Developers`, `Demo Reviewers`, `Demo Requesters` et `Demo Approvers`. Les trios AWS, GCP et Azure appartiennent en outre chacun à un second groupe, `Demo AWS Group`, `Demo GCP Group` ou `Demo Azure Group`, qui n'accorde aucun rôle : il sert uniquement à détenir l'étiquette de contrôle d'accès correspondante, de sorte que ce trio peut voir les enregistrements portant l'étiquette de ce fournisseur, et que personne d'autre ne le peut, sauf `admin` (ou un super administrateur), qui [ignore totalement les étiquettes de contrôle d'accès](../guides/tags.md#access-control-tags) et n'a besoin d'appartenir à aucun groupe pour cela. `Demo Approvers` porte lui-même directement les étiquettes de contrôle d'accès `AWS`, `GCP` et `Azure`, car un approbateur n'est pas limité à un seul fournisseur ; c'est aussi ce qui fait de chacun des deux approbateurs de démonstration un destinataire possible d'une demande qui lui est adressée, quel que soit le workflow de démonstration dont elle provient.

## Essayer {#trying-it-out}

La [Visite guidée](./walkthrough.mdx) déroule n'importe lequel de ces exemples de bout en bout — génération, publication, exécution, approbation, confirmation — à partir d'une seule connexion en tant que `root`, en [agissant en tant que](../concepts/impersonation.md) chaque compte de démonstration tour à tour. Vous connecter à chaque compte avec `DEMO_PASSWORD` fonctionne tout aussi bien ; le tableau ci-dessus indique qui fait quoi.

`Demo AWS Group`, `Demo GCP Group` et `Demo Azure Group` ne voient chacun que les enregistrements de leur propre fournisseur : `demo-aws-developer` ne peut donc pas ouvrir `Demo GKE Pod Restart`, et `demo-gcp-developer` ne peut pas ouvrir `Demo Azure Key Vault Secret Rotation`. N'importe lequel des deux comptes approbateurs convient pour tous les exemples, puisque `Demo Approvers` porte directement les trois étiquettes de contrôle d'accès. Une véritable exécution GKE nécessite que `DEMO_GCP_CREDENTIALS_JSON` contienne un identifiant dont l'identité peut accéder à un vrai cluster GKE, et une véritable rotation nécessite que le principal de service `DEMO_AZURE_*` dispose d'un accès en écriture aux secrets d'un vrai coffre.

**Pas de compte AWS, de cluster GKE ni de Key Vault ?** Ne publiez pas : exécutez le workflow tant qu'il est encore à l'état `brouillon`. En tant que développeur, le compte développeur du fournisseur (`demo-aws-developer`, `demo-gcp-developer` ou `demo-azure-developer`) peut le faire, et seule la boîte de dialogue d'exécution d'un brouillon propose les [simulacres d'outils](../guides/tool-mocks.md) du tenant. Sous **Outils simulés**, cochez les simulacres fournis qui y sont listés (`aws___call_aws` ou `aws___run_script` pour le lancement, `patch_k8s_resource` ou `delete_k8s_resource` pour le redémarrage du pod, `keyvault_secret_get` et `keyvault_secret_create` pour la rotation, ainsi que `request_approval`) : le workflow se déroule alors entièrement sans contacter de vrai fournisseur ni attendre personne. Avec les simulacres de la rotation cochés, la liste des secrets du coffre est elle aussi fictive : choisissez-y `db-password`.

## Suppression {#removing-it}

Définir `DEMO_DATA=false` (ou retirer la ligne) **supprime de nouveau ces enregistrements** au démarrage suivant : l'option est déclarative dans les deux sens.

Deux choses subsistent à dessein : un enregistrement de démonstration dont quelque chose d'autre en est venu à dépendre — un workflow construit sur la compétence de démonstration, par exemple — est conservé et journalisé au lieu d'être supprimé, et un utilisateur de démonstration qui a créé des enregistrements est supprimé de façon logique, afin que son nom continue de s'afficher sur ces enregistrements.
